# Method and Algorithm for Web Content Analysis Based on Computer Vision for Contrast Evaluation

- **Year:** 2025
- **Venue/Source:** 2025 15th International Conference on Advanced Computer Information Technologies (ACIT), IEEE
- **DOI:** 10.1109/ACIT65614.2025.11185908

## Metadata

- **se_area:** testing (automated accessibility/UI testing); also touches maintenance (accessibility auditing/monitoring of deployed web resources)
- **se_task:** Automated web accessibility/contrast evaluation, detecting WCAG 2.1 text/background contrast violations on rendered web pages without access to source code, HTML, or CSS
- **cv_technique:** OpenCV-based image processing (screenshot segmentation, pixel/region color sampling, BGR/RGB-to-luminance conversion for WCAG contrast-ratio computation); Tesseract OCR (text-block/bounding-box detection and localization on rendered page images); combined OCR+CV pipeline with optimization steps (image pre-scaling/downsampling, restricting analysis to detected text regions, parallel/batch processing, OCR result caching, on-the-fly RGB thresholding)
- **platform:** web
- **rationale:** Context-driven and robustness-motivated: existing DOM-based accessibility tools (Axe-core, WAVE, Lighthouse) only work with HTML/CSS and fail on dynamically rendered content (Canvas/WebGL, JS-styled text), text embedded in images, PDFs, screenshots, or third-party/SaaS systems without source access. The authors adopt a "what-you-see-is-what-you-get" screenshot-based CV+OCR approach specifically to analyze the page as the end user visually perceives it, independent of underlying code structure, trading higher computational cost for broader applicability and more realistic (pixel-level) contrast assessment.
- **artifact_type:** full-interface (operates on full-page/region screenshots of rendered web UIs, analyzing text elements, buttons, links, and headings across the captured interface)
- **eval_method:** No formal dataset, baseline comparison, or quantitative metrics were used. Evaluation consisted of a single case study: the module (Python, Selenium for screenshot capture, OpenCV for image processing, Tesseract OCR for text detection) was applied to a real web page (the Medium blog listing page) containing headings, buttons, links, and other UI elements. Results were reported qualitatively/descriptively via annotated output images (Figs. 1-3) showing flagged low-contrast elements, with one specific numeric example given (word "Perspective" measured at contrast ratio 3.01, below the WCAG 4.5:1 threshold) and general observations that several buttons had contrast near 2:1. Output is saved as annotated images plus a CSV of detailed contrast results. No comparison against Axe/WAVE/Lighthouse outputs, no accuracy/precision metrics for OCR text detection, and no human user study were conducted.
- **challenges:** Authors explicitly state: (1) the OpenCV+Tesseract pipeline is resource-intensive/computationally heavy compared to DOM-based tools, requiring optimizations (pre-scaling, region-limiting, parallelization, caching) to achieve adequate performance; (2) implementation complexity is rated "Medium/High" versus "Low" for existing DOM-based tools; (3) compliance determination is not purely contrast-ratio-based, font size/weight must also be considered, adding nuance the tool must handle; (4) future work is needed on performance improvement, more thorough testing, and comparison with commercial solutions, implying current testing/validation is limited. (Inferred from experimental setup:) OCR accuracy/robustness across diverse fonts, languages, low-resolution screenshots, and complex backgrounds (gradients, overlays) is not evaluated and likely a practical limitation; single-page-type testing (only Medium) raises generalizability concerns; no ground-truth validation of detected contrast violations against manual/expert accessibility audits.

## Scope note

this is a short (5-page) conference paper with a single qualitative case study on one website (Medium) and no quantitative evaluation metrics, baselines, dataset, or statistical results. Findings are reported narratively ("the algorithm marked various elements," "several such buttons had a contrast close to 2:1") rather than measured. The CV usage (OpenCV pixel/color analysis plus Tesseract OCR text-block localization) is real and central to the method, and the SE connection (automated accessibility/UI testing without source-code access) is solid, but the empirical rigor is weak for a full evaluation. Treat the results as illustrative or proof-of-concept rather than validated.

## Summary

This paper proposes a computer-vision method for automatically checking text-and-background contrast on web pages against WCAG 2.1, without needing access to a page's HTML or CSS. The approach captures a screenshot of the rendered page through Selenium, uses Tesseract OCR to localize text blocks, then applies OpenCV to sample text and surrounding background colors within those regions, converts RGB values to relative luminance, and computes WCAG contrast ratios, flagging anything below the 4.5:1 threshold (or 3:1 for large or bold text). The main pitch is a "what you see is what you get" alternative to DOM-based accessibility tools like Axe-core, WAVE, and Lighthouse, positioned as more versatile since it works on any visual representation, including Canvas or WebGL content, text embedded in images, PDFs, and third-party systems without source access, at the cost of higher computational overhead. The authors mitigate that cost through image pre-scaling, limiting analysis to text regions, parallel processing, and OCR-result caching. The system was demonstrated on the Medium website, producing annotated output images that flag non-compliant elements, one specific example being the word "Perspective" at a 3.01 contrast ratio against the 4.5 threshold, plus a CSV export of results, and it found that many buttons, links, and some headings failed accessibility contrast standards. The paper stays exploratory: there's no formal dataset, baseline comparison, or quantitative accuracy evaluation.
