# DeltaNN: Assessing the Impact of Computational Environment Parameters on the Performance of Image Recognition Models

- **Year:** 2023
- **Venue/Source:** 2023 IEEE International Conference on Software Maintenance and Evolution (ICSME)
- **DOI:** 10.1109/ICSME58846.2023.00054

## Metadata

- **se_area:** maintenance
- **se_task:** Differential testing of image recognition models to assess robustness of output labels and inference time across variations in the computational deployment environment (deep learning framework conversions, compiler optimization levels, and hardware devices), post-training.
- **cv_technique:** MobileNetV2 (image classification); ResNet101/ResNet101V2 (image classification); InceptionV3 (image classification). All are CNN-based image classifiers evaluated as native and cross-framework-converted implementations (Keras, PyTorch, TensorFlow, TensorFlow Lite), compiled/executed via the Apache TVM compiler stack.
- **platform:** general (deployment targets span server, embedded/edge board, laptop, and mobile-class GPU hardware; not a mobile-app or web-app SE artifact)
- **rationale:** Robustness. The CV models are the system under test, and DeltaNN evaluates whether their output labels and inference latency remain consistent ("robust") when only computational-environment factors (DL framework, compiler optimization, hardware device) change post-training, independent of the input data itself. This is framed as important for maintenance/evolution of safety-critical DNN deployments (e.g., autonomous driving, medical imaging) where environment-induced errors and timing uncertainty must be caught.
- **artifact_type:** natural input (the same real-world dataset images, unmodified, are re-run through different model implementations/environments; DeltaNN does not perturb or generate new inputs; it varies the deployment configuration, not the input)
- **eval_method:** Empirical study using DeltaNN (a 3-stage framework: Model Variant Generator, Differential Execution, Analysis) on three pretrained CNNs (MobileNetV2, ResNet101V2, InceptionV3) sourced from 4 DL frameworks (Keras, PyTorch, TensorFlow, TFLite), evaluated on the ImageNet object-detection test dataset (ILSVRC2017, 5,500 RGB images, 1000 classes). Combinations tested: 3 models x 12 DL-framework conversion pairs x 4 hardware devices (server w/ Nvidia Tesla K40c; Nvidia AGX Xavier; laptop w/ Intel GEN9 GPU; Hikey 970 board w/ Arm Mali-G72) x 3 TVM compiler optimization levels (Basic/o0, Default/o2, Extended/o4). Metrics: pairwise top-1 (and top-K rank-biased overlap) output-label agreement between model variants (measuring % dissimilarity/misclassification divergence), and average inference time (10 repeated runs per image) compared across configurations, with statistical significance assessed via one-way ANOVA (5% level). Fault localization used debug traces (per-layer activations, weights/biases, tensor outputs) and cross-checks against ONNXRuntime intermediate representations. No human study; no external baseline tool. DeltaNN's own differential-execution outputs serve as the comparison basis (source vs. converted/optimized model).
- **challenges:** Authors' own stated threats to validity: (1) results are model-dependent, limited to 3 widely used models and may not generalize to other architectures; (2) only the ImageNet test dataset was used, other datasets may yield different robustness results; (3) model pre-processing (resizing, normalization) matters a great deal, and doing it suboptimally could affect results, though recommended pre-processing per model/framework was used; (4) importing models into Apache TVM is itself a "hidden" conversion step that could introduce undetected errors, only partially mitigated by spot-checking outputs on a sample of images; (5) inference-time measurements are subject to variance (e.g., medium-term cache effects), mitigated by averaging 10 runs but not fully eliminated. Additional reported limitations: 10 of 36 DL-framework conversion attempts crashed outright (tool incompatibility, e.g., no Keras-to-TensorFlow conversion possible via tf2onnx), MobileNetV2 could not be evaluated on the Xavier device due to a CUDA error, and ResNet101 from PyTorch required substituting the V1 architecture since V2 weights were unavailable, all reducing the completeness of the cross-configuration comparison matrix.

## Summary

This paper introduces DeltaNN, a differential-testing framework that treats deployed image recognition models as the system under test and probes their robustness to changes in the "computational environment," meaning the deep learning framework (Keras, PyTorch, TensorFlow, TFLite), compiler optimization level (via Apache TVM), and hardware accelerator (server GPU, embedded/edge boards, laptop GPU), rather than to changes in input data, which prior CV robustness work has focused on. DeltaNN generates equivalent model variants across these parameters (using ONNX as an intermediate conversion format), executes them on the same ImageNet test images, and statistically compares output labels and inference times, with a debug-execution mode that captures per-layer activations and weights to localize discrepancy sources. Applied to MobileNetV2, ResNet101V2, and InceptionV3, the study found that DL-framework conversion can cause up to 72% output-label disagreement (traced in one case to a bug in TensorFlow Lite's converter incorrectly copying model weights, not the more commonly blamed tf2onnx/ONNX intermediate step), while compiler optimizations did not change output labels but caused up to 81% unexpected inference-time degradation on low-end hardware. The notable contribution is the fault-localization capability: by diffing per-layer parameters and activations between source and converted models, the authors pinpoint the exact conversion tool responsible for label-changing errors, arguing such computational-environment sensitivity deserves regulatory/testing attention for safety-critical DNN deployment analogous to dataset- and model-level robustness testing.
