# Intelligent Software Testing based on Visual Feedback

- **Year:** 2022
- **Venue/Source:** 2022 9th International Conference on Dependable Systems and Their Applications (DSA)
- **DOI:** 10.1109/DSA56465.2022.00109

## Metadata

- **se_area:** testing
- **se_task:** GUI-driven automated software testing with a closed-loop perception-drive-feedback mechanism (GUI element/mouse recognition, script/behavior/GUI-driven test execution, and behavioral/event feedback verification)
- **cv_technique:** YOLOv5 (improved) object detection for GUI element and mouse-pointer recognition/classification; OCR for reading on-screen text (e.g., status/prompt messages) to drive event feedback
- **platform:** desktop (validated on the FileZilla desktop client; C/S architecture with a camera-based intelligent terminal, generally applicable to any GUI-based system under test)
- **rationale:** Context-driven and robustness-oriented: traditional GUI automated testing is API-dependent, limited in scope, and inflexible, and simple linear script execution is error-prone without inspection. Computer-vision-based recognition plus a perception-drive-feedback closed loop lets the framework detect actual on-screen state (element positions, mouse position, pop-ups/status text) and correct wrong behaviors in real time, improving correctness and robustness of test execution. Ease of use is also cited (no need to embed code or understand internal framework logic; scripts separate test behavior from test objects to ease maintenance).
- **artifact_type:** full-interface (GUI elements are detected/classified across the whole screen/active window) combined with localized artifacts (bounding boxes for individual GUI elements and mouse pointer, with position/class/confidence) and temporal feedback (event-triggered/behavior-triggered feedback loops that monitor GUI state changes over time, e.g., waiting for a page to load or a pop-up to appear)
- **eval_method:** Single case-study validation, not a benchmark dataset comparison. A high-definition camera captures the active window of the system under test (FileZilla FTP client); the improved YOLOv5 model recognizes GUI elements (classes: ComboBox, Button, MenuBars, Toolbar, TextArea, TreeView, TableViews, TextFields, Toggle Button, Adjustment Button, Scroll Bar) and the mouse pointer (classes: Common white, Input), each reported with a confidence score (e.g., Host TextField 0.90, QuickConnect Button 0.86, mouse positions with confidence 0.83-0.90). A test script (host/username/password input, QuickConnect, file transfer, disconnect/exit) is executed and the paper qualitatively shows recognition result tables/figures (Table IV/V, Figs. 6-8) and describes correct behavioral feedback (mouse-movement/click/keyboard feedback) and event feedback (e.g., detecting "Connection established" vs. "Error: Unable to connect to the server" text via OCR). No quantitative benchmark against baseline tools, no formal metrics (precision/recall/F1) beyond the raw per-detection confidence values, and no human user study.
- **challenges:** Authors explicitly state that recognition accuracy is still problematic for GUI elements of small size, and that the element-recognition model needs further optimization; they also note that only one example (FileZilla) was validated and that more example validations are needed to further demonstrate the framework's effectiveness/generality. (Inferred from experimental setup:) The approach depends on camera positioning/angle and image quality for stable capture, appears tied to a single-window/single-application C/S setup with serial or network-based intelligent terminal, uses fixed polling/waiting intervals for event feedback (paper itself flags the difficulty of tuning wait time, too short misses GUI loads, too long causes invalid waits/crashes), and has not been evaluated for scalability, cross-platform generalization, or performance under diverse or dynamic GUI layouts beyond the single desktop application tested.

## Summary

This paper proposes a three-layer framework, perception, driver, and feedback, for GUI software testing driven by computer vision rather than API-based control identification. The perception layer uses an improved YOLOv5 model to detect and classify GUI elements (buttons, text fields, menus, and so on) and the mouse pointer from screen captures, producing standardized position, class, and confidence records. The driver layer simulates mouse and keyboard operations at three levels of abstraction, script-driven, behavior-driven, and GUI-driven, breaking high-level actions like "Input" or "Touch" into combinations of primitive mouse and keyboard behaviors to improve script reuse and cut maintenance cost. The feedback layer closes the loop by comparing expected against actual visual state: behavioral feedback checks that mouse movements, clicks, and keyboard input executed correctly, while event feedback watches for GUI changes, like a new page loading or a pop-up appearing, using OCR to read status text. The main contribution is this modular perception-drive-feedback closed-loop architecture, meant to be reusable across GUI applications regardless of implementation. The demonstration is a single practical example: automating a login, connect, and file-transfer workflow in the FileZilla FTP client, showing recognition outputs and correct error handling, such as distinguishing "Connection established" from a connection error through OCR. The evaluation stays a single-case qualitative demonstration rather than a controlled benchmark comparison, with the authors noting that recognition accuracy still struggles on small GUI elements.
