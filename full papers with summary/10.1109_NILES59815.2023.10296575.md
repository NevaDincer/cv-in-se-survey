# Owl Eye: An AI-Driven Visual Testing Tool

- **Year:** 2023
- **Venue/Source:** 2023 5th Novel Intelligent and Leading Emerging Sciences Conference (NILES)
- **DOI:** 10.1109/NILES59815.2023.10296575

## Metadata

- **se_area:** testing
- **se_task:** visual regression/GUI testing, automatically comparing a reference screenshot against an updated ("test") screenshot of the same application screen to detect visual defects (object shifting, scaling, color changes, missing/new elements) without relying on the application's source code, DOM, or pixel-by-pixel comparison, across mobile, web, and desktop platforms
- **cv_technique:** a multi-stage classical + deep-learning pipeline: image registration/preprocessing for scale/zoom normalization; classical (non-learned) GUI object detection using Sobel-edge-based text/detail detection, convolution + binarization + morphological closing + flood-fill for large-element boundary detection, and non-maximum suppression via Intersection-over-Union (IoU) for redundant-box removal; a deep-learning object-detection alternative using transfer learning on the RICO UI dataset, comparing Faster R-CNN against YOLOv8 (single-class "ui-element" vs. background); YOLOv8 was selected for higher accuracy (mAP50 0.52 vs. 0.31) and faster training; object matching via a tree-structured representation of detected elements, template matching, and a weighted combination of SIFT and KAZE feature-matching algorithms; and change classification using Structural Similarity Index (SSIM) and image-hash comparison against threshold values to distinguish scaling from genuine content change
- **platform:** general (explicitly designed to be platform-independent, demonstrated conceptually across mobile, web, and desktop applications, working purely from screenshots)
- **rationale:** robustness (motivated by known weaknesses of prior visual-testing paradigms, manual testing is slow and error-prone, pixel-by-pixel comparison produces excessive false positives, and DOM-based comparison can yield both false positives and false negatives when identical code renders differently or different code renders identically, so the tool is designed to be source-code- and platform-independent) and ease of use (aims to reduce the complexity, data requirements, and change-resistance issues that the authors identify as adoption barriers for existing AI-driven commercial visual-testing tools like Applitools, Percy, and SmartBear VisualTest)
- **artifact_type:** localized (the entire pipeline centers on detecting, matching, and classifying changes to individual GUI object bounding boxes/elements within a full screen, rather than treating the screen as a single undifferentiated image or extracting temporal/sequential information)
- **eval_method:** informal, small-scale qualitative demonstration rather than a systematic benchmark. The deep-learning object detector is quantitatively evaluated only on model-selection metrics (YOLOv8: mAP50 0.52 in ~51 min training vs. Faster R-CNN: mAP50 0.31 in ~80 min, both trained on 1,000 RICO images for 40 epochs with an 80/20 train/validation split) and reported to reach a maximum 72% F1-score at 0.315 confidence on in-domain test images; the end-to-end visual-testing pipeline itself is illustrated only through a small number of manually-curated example test cases (two input pairs shown in the paper) with qualitative discussion of correctly detected changes (photo scaling, text color change, missing icon/word) and explicitly acknowledged false positives/negatives on a harder multi-error test case. The authors state there is "no automated way of assessing the results and reporting the false positives and false negatives" at the whole-pipeline level.
- **challenges:** the authors explicitly list several limitations: similarity measures perform poorly on low-resolution images; page/content scaling must not exceed roughly 20% of the reference image size or the comparison breaks down; hyperparameters likely need re-tuning for different domain-specific UIs; the deep-learning object detector needs additional web/desktop-specific training data (beyond RICO, which is mobile-only) to generalize well; classic (non-learned) object detection has more consistent cross-domain performance than the deep-learning detector, which performs well mainly in-domain, so the two are not yet combined and users must manually choose one; and the harder multi-error test case demonstrates concrete false positives (an unchanged paragraph flagged as changed) and false negatives (an actual color change not detected) once multiple simultaneous visual changes are present, indicating the matching/classification stage's error rate grows with scene complexity, all explicitly identified as future work (combining classic and deep-learning detection, improving low-resolution matching, more accurate bounding-box generation, runtime optimization, and bug-tracker integrations).

## Summary

This short conference paper presents Owl Eye, a prototype AI-driven visual testing tool aimed at automatically detecting visual regressions in application GUIs, bugs like a hidden button, a shifted icon, or a color change that functional tests do not catch, without depending on source code, the DOM, or fragile pixel-by-pixel image diffing. The tool takes a reference screenshot and an updated "test" screenshot as input and runs them through a four-stage pipeline: image preprocessing/registration to normalize scale and alignment differences (including handling zoom-in/zoom-out cases common in cross-browser testing); object detection performed by either a classical computer-vision method (a multi-stage process using edge detection, morphological operations, flood-fill, and IoU-based non-maximum suppression to localize both fine text/detail elements and larger UI components) or a deep-learning method (YOLOv8, transfer-learned on the RICO mobile-UI dataset, chosen over Faster R-CNN for better accuracy and training speed); object matching, which represents detected elements as tree structures and uses template matching plus a combined SIFT+KAZE feature-matching score to link corresponding elements between the two screenshots; and change classification, which uses SSIM and perceptual-hash similarity thresholds to distinguish benign scaling from genuine content changes (color shifts, translations, removals, additions), while also flagging likely dynamic content that appears in place of a missing element. A particularly interesting design choice is the tool's explicit two-track object-detection strategy, offering both a classical and a deep-learning detector rather than committing to one, motivated by the authors' finding that the classical approach generalizes more consistently across visually diverse domains while the deep-learning detector performs better but only within its training distribution, a trade-off the authors are candid about and leave for future combination. The paper is honest about its preliminary, prototype-stage status: evaluation is limited to a handful of manually illustrated example cases and per-component metrics (e.g., detector mAP50/F1) rather than any systematic quantitative evaluation of the end-to-end tool's precision/recall on a labeled test corpus, and the authors explicitly acknowledge both concrete failure cases (false positives/negatives) and the current lack of an automated way to measure the whole system's accuracy.
