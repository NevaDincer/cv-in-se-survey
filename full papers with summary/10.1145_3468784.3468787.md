# Web Components Template Generation from Web Screenshot

- **Year:** 2021
- **Venue/Source:** The 12th International Conference on Advances in Information Technology (IAIT2021), ACM
- **DOI:** 10.1145/3468784.3468787

## Metadata

- **se_area:** development
- **se_task:** UI code generation (automatic generation of Web Components/React templates from a screenshot of an existing website; reverse-engineering a rendered web page into modular front-end code)
- **cv_technique:** RetinaNet (one-stage object detection model) with Focal Loss and a Feature Pyramid Network (FPN); ResNet-based backbone typical of RetinaNet, trained via TensorFlow object detection framework; dataset labeled with the labelImg annotation tool (PASCAL VOC XML converted to TFRecord)
- **platform:** web
- **rationale:** context-driven. CV is used to visually recognize which web-UI element (button, card, navbar, form, etc.) is present at each screen location purely from pixel appearance, since no structured/DOM information is used as input, only a rendered screenshot. Ease of use is also a factor, since using an existing pretrained-style object detector (RetinaNet) removes the need to parse or reverse-engineer HTML/CSS/JS source, letting non-technical inputs (a screenshot) drive template generation directly
- **artifact_type:** full-interface (whole-page web screenshots are given as input; the model detects and localizes multiple web-component objects with bounding boxes across the entire captured page, then reconstructs a full page template from all detections)
- **eval_method:** Custom, self-collected dataset of 140 full-page web screenshots of Thai business-information websites (captured via the Chrome "FireShot" extension), manually annotated with labelImg into 34 object classes (8 native HTML5 tags, 13 Bootstrap 5 components, 13 custom/complex components), yielding 3,433 labeled objects total, with a strong class imbalance (e.g., "paragraphs" 1,118 instances vs. "dropdown" 2 instances, shown in a class-count table). Data split 120/10/10 (train/validate/test). Model trained for over 1,000 epochs; performance tracked via validation loss across selected epochs (a table/figure compares loss and number of predicted objects at epochs 32, 105, 215, 265, 477, 762, 1002), with the best model selected at epoch 762 (validation loss = 1.873). A confidence threshold of 0.5 is used to filter low-confidence detections, and IOU-based comparison resolves overlapping predictions (keeping the higher-confidence class when one image region matches multiple classes). Evaluation is qualitative/quantitative on the held-out test screenshots. Visual comparison figures show original screenshot vs. predicted bounding boxes vs. generated Web Components template (desktop and mobile responsive versions), but there is no standard object-detection metric (e.g., mAP) reported, no comparison against other detectors/baselines, and no user or human study of the generated templates' quality or usability.
- **challenges:** Authors explicitly note: (1) no public dataset of web-object screenshots exists, forcing manual dataset creation, which limited the dataset to only 140 screenshots/3,433 objects; (2) severe class imbalance across the 34 component categories (partially mitigated with Focal Loss); (3) the model is imperfect: some elements (e.g., "Navbar") are still not reliably recognized; (4) scope was deliberately restricted to Thai business-information websites to control the number/variety of component classes, limiting generalizability to other website genres or design systems; (5) the current template generator supports only one React component per detected object class (a stated preliminary/simplification limitation), constraining more complex or nested layouts; (6) no formal accuracy metric such as mAP is reported, only validation loss, making it hard to benchmark against other object-detection or UI-code-generation approaches (inferred from experimental setup).

## Summary

This paper presents a pipeline that automatically reverse-engineers a static screenshot of a rendered website into a modular front-end codebase built on the W3C Web Components standard (implemented via React). The approach treats each visual UI element (buttons, navbars, cards, forms, carousels, custom widgets like Facebook cards or QR codes, etc.) as an object-detection target: a RetinaNet model, chosen for its one-stage speed/accuracy balance and its Focal Loss (to handle severe class imbalance) and Feature Pyramid Network (to handle multi-scale UI elements), is trained to predict a class label and bounding box for each of 34 web-component categories drawn from HTML5, Bootstrap 5, and custom/complex components. A self-built dataset of 140 full-page screenshots of Thai business websites, manually annotated with labelImg, was used for training (120/10/10 train/validate/test split, 3,433 labeled objects). A separate generator module then maps the model's JSON output (class + bounding box) onto corresponding React component templates, using bounding-box row/column heuristics (based on ymin/ymax and IOU) to reconstruct the page's Bootstrap-5 grid layout, enabling automatic generation of both desktop and mobile-responsive versions of the reconstructed page. The best model, at epoch 762, achieved a validation loss of 1.873. A notable detail is the explicit contrast the authors draw between web screenshots and prior GUI-mockup/hand-drawn-mockup datasets: unlike mockups, real screenshots offer no control over element shape, scale, or color, making the recognition task intrinsically harder and motivating the deliberate narrowing of website domain to keep the class space tractable.
