# Image-based Bug Oracle Automation for Bug Report Reproduction Using Widget Detection

- **Year:** 2021
- **Venue/Source:** SEAI 2021
- **DOI:** 10.1109/SEAI52285.2021.9477528

## Metadata

- **se_area:** Bug Reproduction (maintenance)
- **se_task:** Automated bug oracle verification during bug report reproduction: given an oracle error screenshot from a bug report and a runtime screenshot, determine whether they depict semantically equivalent GUI screens (i.e., whether the target bug has been triggered), covering both crash and non-crash bugs
- **cv_technique:** Object detection for GUI widget localization/classification via UIED (two-stage: traditional region detection for layout blocks + fine-tuned ResNet50 for GUI-type classification); EAST scene-text detector for GUI text elements; Tesseract OCR for extracting dialogue-box error-message text; structural comparison via a custom 'dummy hierarchy tree' construction (top-down, based on relative widget coordinates) plus a 51-dimensional tree-shape vector compared by cosine similarity, combined with a node-mapping ratio into a weighted similarity score
- **platform:** Mobile (Android)
- **rationale:** Robustness (structural/object-detection-based comparison is explicitly designed to be noise-tolerant to the pixel-level differences pixel-diff tools are sensitive to: cross-device scaling/shifting, tester-edited images for privacy, and dynamic/user-specific data)
- **artifact_type:** Bug report error screenshot (oracle) paired with a runtime screenshot
- **eval_method:** Empirical study (RQ1-RQ3) on 52 image pairs from 52 real-world bug reports across 12 open-source Android apps (crawled from GitHub, cross-referenced with a prior work's repository list); RQ1 accuracy of SegStec vs. the pixel-level state-of-the-art tool PID on detecting Semantically Equivalent GUI Screens (SEGS); RQ2 image-processing execution-time overhead per app; RQ3 end-to-end applicability by integrating SegStec as the oracle for the existing crash-reproduction tool RecDroid and manually checking correct YES/NO output
- **challenges:** Cannot differentiate GUI screens that differ only in background color/theme (predicts different-themed screens as the same); shows reduced accuracy on screens containing many text or image blocks; cannot distinguish images depicting genuinely different app 'states' beyond structural/tree similarity; the deep-learning-based widget detection stage dominates total processing time (~5.7-9.7s per pair) versus <1s for the structural comparison itself

## Summary

Targets a specific gap in automated bug reproduction: existing trace-generation approaches (stack-trace-based, or step-to-reproduce NLP-based) all fall back on comparing crash stack traces to verify a reproduced failure matches the target bug, so none of them can verify **non-crash** bugs, which lack a stack trace altogether. The paper's insight is that bug reports commonly already include an error screenshot, which can serve as a self-descriptive, easy-to-obtain "bug oracle" for both crash and non-crash bugs. Naive pixel-level image comparison (e.g., prior tools like PID) fails in practice because oracle and runtime screenshots are typically captured on different machines (causing scaling/shifting pixel noise), may be manually edited by testers for privacy, or contain dynamic/user-specific content (usernames, dates, battery/WiFi status icons).

The proposed tool, **SegStec** (Semantically Equivalent GUI Screen deTECtion), reframes oracle verification as a *structural* rather than pixel-level comparison problem. After header/footer cropping (to strip device-specific chrome like battery/WiFi icons), both oracle and runtime screenshots go through widget detection (UIED, itself a hybrid of traditional region detection + fine-tuned ResNet50 classification, plus the EAST scene-text detector) to produce a JSON widget list. SegStec branches based on whether a dialogue box is detected (heuristically, by widget size and screen-centered position): if so, OCR (Tesseract) extracts and string-compares the error-message text directly; if not (non-error/non-crash bugs), SegStec builds a "dummy hierarchy tree" from the widget layout (rows compared horizontally to assign tree levels/siblings), encodes each tree's shape as a 51-dimensional vector, computes cosine similarity between oracle/runtime tree-shape vectors, then, if that passes a threshold, attempts to map ≥70% of individual nodes between the two trees and computes a final weighted similarity score (0.7×shape-cosine-similarity + 0.3×node-match-ratio) against an empirically tuned threshold (0.84).

Evaluated on 52 real Android bug reports (12 apps), SegStec detects SEGS pairs correctly in 80.8% of cases versus only 32.7% for the pixel-diff baseline PID. The paper attributes PID's poor performance to its high sensitivity to exactly the cross-device pixel noise SegStec is designed to ignore. Average per-pair image-processing time ranges 5.7-9.7 seconds, dominated by the deep-learning widget-detection stage rather than the lightweight structural comparison. When plugged into the existing crash-reproduction tool RecDroid as its oracle, the combined pipeline successfully automates end-to-end reproduction for 51.9% of bug reports (27/52). The gap between SegStec's 80.8% oracle-verification rate and the 51.9% end-to-end rate is attributed to limitations in RecDroid's upstream reproduction-trace generation (some interaction patterns or concrete input values it cannot generate automatically), not to SegStec itself. The authors are candid about three concrete failure modes as future work: color/theme-only differences aren't detected, dense text/image-heavy screens reduce accuracy, and the approach cannot distinguish different "states" of visually similar screens.
