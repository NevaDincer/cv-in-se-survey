# MLLM-Based UI2Code Automation Guided by UI Layout Information

- **Year:** 2025
- **Venue/Source:** Proceedings of the ACM on Software Engineering (PACMSE), Vol. 2, ISSTA, Article ISSTA050
- **DOI:** 10.1145/3728925

## Metadata

- **se_area:** development
- **se_task:** UI-to-code (UI2Code) automation, specifically Screenshot2Code for web applications: converting a real-world webpage screenshot into HTML+CSS code that visually and structurally reproduces the original page, including its complex, deeply-nested layout
- **cv_technique:** UIED (UI Element Detection, a hybrid CV tool) for extracting bounding boxes of text/non-text UI elements from the webpage screenshot; a custom graph-based spatial-relationship analysis (element relation graph + BFS-based UI Group Search) built on top of detected element boxes to merge visually/structurally repetitive regions; a custom 2D block-projection and recursive-division algorithm (inspired by Gestalt proximity principles) to segment the image into a hierarchical UI layout tree, explicitly compared against and shown superior to Segment Anything Model (SAM) for this task; Multimodal Large Language Models (GPT-4o used internally for atomic-region code generation; GPT-4o, Claude 3.5 Sonnet, DeepSeek VL-7B, WebSight VLM-8B, pix2code (CNN+LSTM) evaluated as end-to-end baselines); CLIP (ViT-B/32) used as an automated visual-similarity evaluation metric (CLIP score)
- **platform:** web
- **rationale:** robustness (addresses two specific documented MLLM failure modes: inability to comprehend complex real-world layouts, and inaccurate layout preservation when generating code directly from a full-page image by decomposing the problem into element/layout structure extraction handled by classical CV/graph algorithms, with MLLMs used only for small, bounded atomic-region code generation) and context-driven (a non-MLLM, decoupled code-fusion algorithm is used specifically to bypass MLLM context-window/token-length limits on very large, complex real pages, which is the dataset-derived motivation for the whole 3-module design)
- **artifact_type:** full-interface, decomposed hierarchically into localized atomic image blocks (the whole webpage screenshot is recursively segmented into a tree of nested "row"/"column" containers down to "atomic" leaf regions, each of which is independently rendered to code and then reassembled/fused back into the full page via a deterministic tree-traversal algorithm rather than further MLLM calls)
- **eval_method:** four-RQ empirical evaluation: RQ1: comparison against 9 baseline configurations (pix2code, WebSight VLM-8B, DeepSeek VL-7B, GPT-4o and Claude 3.5 Sonnet each under Direct/CoT/Self-Refine prompting) on BLEU (code/text similarity) and CLIP score (visual similarity) across three datasets: the existing Design2Code benchmark (250 sampled real pages, images replaced with placeholders) and a newly constructed Snap2Code benchmark (250 "Seen" pages from the global top-500 most-visited sites, 100 "Unseen" pages from newly registered domains verified via the Wayback Machine to postdate the MLLMs' training cutoffs, both retaining real images), LayoutCoder wins in 5/6 dataset×metric combinations, with the largest gain (+24% BLEU) on the complex Snap2Code(Seen) set; RQ2: ablation removing UI Group Search, gap-sorted Recursive Division, and the custom code-generation prompt, each shown to measurably contribute (recursive-division gap-sorting and the full prompt contributing most); RQ3: performance stratified by four website-complexity proxies (DOM depth, tag count, HTML token length, image aspect ratio) via equal-frequency binning, showing LayoutCoder's advantage over the strongest baseline (Claude 3.5 Sonnet + Self-Refine) grows and remains stable as complexity increases; RQ4: human evaluation (4 participants with SE/UI-design experience, 120 questions each = 1,920 ratings total) on Layout Accuracy, Visual Fidelity, Content Alignment, and Code Usability via 1–5 Likert scales, blinded and order-randomized, showing especially large gaps on Snap2Code(Seen) (e.g., Visual Fidelity 4.13 vs. 1.64 for Claude(SR)); additionally a head-to-head efficiency comparison against the closest prior MLLM-based competitor DCGen on time, token usage, dollar cost, and generation success rate (LayoutCoder: 100% success rate vs. DCGen's 60% on Snap2Code(Seen), at roughly 1/3 the time and cost).
- **challenges:** the paper's own preliminary case study (Figure 1) documents that GPT-4o outright refuses to fully reconstruct complex real-world page layouts, providing only simplified code, the core problem motivating the work; the authors acknowledge a limited baseline set (compute constraints prevented testing against other MLLMs such as LLaVA-1.5); reliance on BLEU and CLIP score as the primary automated metrics is explicitly flagged as a threat to validity since neither metric was designed for or fully captures UI2Code-specific quality (structural correctness, code usability), which is why a human evaluation was added as a supplement; dataset size for Snap2Code(Seen)/Design2Code was capped at 250 samples specifically to control the cost of querying expensive closed-source MLLMs (GPT-4o, Claude 3.5 Sonnet) during evaluation; the competing DCGen approach was found to fail entirely on ~40% of high-aspect-ratio Snap2Code(Seen) pages due to MLLM context-window limits during its MLLM-based code-fusion step, a failure mode LayoutCoder's algorithmic (non-MLLM) code fusion was specifically designed to avoid.

## Summary

This paper tackles UI2Code automation for real-world web pages, where converting a UI design or screenshot into working HTML+CSS is a routine but labor-intensive step in web development. Prior approaches either use brittle rule-based image processing (REMAUI: edge detection + OCR + heuristics) or deep-learning models needing large labeled datasets that generalize poorly to unseen designs (pix2code: CNN+LSTM, limited to five component types). Modern Multimodal LLMs (GPT-4o, Claude 3.5 Sonnet) reduce the data dependency but the authors empirically show, via a motivating case study, that they still struggle in two specific ways on complex real pages: they can outright refuse to reproduce complicated layouts, and when they do generate code, the resulting layout visibly diverges from the reference. The proposed system, LayoutCoder, addresses this by explicitly separating layout understanding from code generation rather than asking an MLLM to do both end-to-end. It first runs UIED (an existing hybrid CV element-detector) to get bounding boxes of all UI elements, then builds a spatial relationship graph and a breadth-first "UI Group Search" to merge repetitive same-structure regions (e.g., a row of six video thumbnails) that would otherwise be redundantly and inconsistently coded if treated separately. It then performs a Gestalt-proximity-inspired recursive 2D block-projection to segment the page into a hierarchical layout tree of row/column containers down to indivisible "atomic" leaf regions, explicitly shown via a Taobao.com case study to outperform Segment Anything Model (SAM), which fails to preserve small components, is overly sensitive to individual objects, and cannot cluster repeated identical components. Finally, each atomic region is independently converted to a code snippet by an MLLM (GPT-4o) under a constrained prompt (no fixed sizes, preserved aspect ratio, no margin/padding conflicts), and notably the snippets are reassembled into the final page via a deterministic, non-MLLM tree-traversal algorithm rather than another LLM call, which the authors identify as the main mechanism letting LayoutCoder scale to arbitrarily long/complex pages without hitting MLLM context-window limits (unlike the closest competing method, DCGen, which fails on 40% of long, high-aspect-ratio pages for exactly this reason). Evaluated on the existing Design2Code benchmark and a newly built, more realistic Snap2Code benchmark (real images retained; split into "Seen" top-500 sites and "Unseen" freshly-registered domains to rule out training data leakage), LayoutCoder outperforms nine strong baselines including GPT-4o and Claude 3.5 Sonnet variants, with gains growing as page complexity increases, and is corroborated by a blinded four-rater human evaluation showing especially dramatic quality gaps on the hardest, most realistic dataset.
