# Fill in the Blank: Context-aware Automated Text Input Generation for Mobile GUI Testing

> **SCOPE WARNING**: This paper does not use computer vision techniques to understand the GUI. QTypist extracts GUI context entirely from the Android **view hierarchy XML file** (obtained via UIAutomator), specifically the text/resource-id/hint-text fields of widgets, and feeds this structured, non-visual information into a prompt-tuned GPT-3 language model to generate text input. No screenshot analysis, OCR, object/widget detection from pixels, or any image-based model is used anywhere in the pipeline (confirmed by full read of Sections III–VI). It is included here only because it is closely related to the mobile GUI testing literature that CV-based approaches (e.g., screenshot-based widget detection) also target; it likely falls outside the strict scope of "Computer Vision in Software Engineering" and should be excluded or flagged during screening.

- **Year:** 2023
- **Venue/Source:** 2023 IEEE/ACM 45th International Conference on Software Engineering (ICSE 2023)
- **DOI:** 10.1109/ICSE48619.2023.00119

## Metadata

- **se_area:** testing
- **se_task:** Automated context-aware text input generation for mobile GUI testing (to help automated GUI testing tools pass text-input pages and reach more app activities/pages)
- **cv_technique:** None used. The approach (QTypist) relies on: (1) parsing the Android view hierarchy XML (accessibility tree) obtained via UIAutomator to extract widget attributes (hint-text, resource-id, text fields) and page/app metadata; (2) NLP techniques, including the Stanford NLP parser for POS tagging, tokenization/Camel-case splitting, and keyword-based glossary matching, to build linguistic prompt patterns; (3) the GPT-3 (Curie) large language model, prompt-tuned on an automatically constructed prompt-answer dataset, to generate the actual input text. No pixel/screenshot-based visual model (no OCR, no CNN/object detection, no image classifier) is used to perceive or understand the GUI screen.
- **platform:** mobile (Android; authors report a small-scale generalization experiment to iOS and Web with 20 apps each, but the core approach and evaluation are Android-based)
- **rationale:** Context-driven: the central idea is that correct, semantically valid text input requires understanding the surrounding GUI/app context (widget hint text, nearby widgets, activity name, app name, input category) rather than using fixed/random strings or hand-written heuristic rules, so text input generation is reframed as a cloze-style fill-in-the-blank question answering task for an LLM conditioned on this context.
- **artifact_type:** natural input (the system's output is a piece of natural-language/semantic text entered into an EditText widget to satisfy a GUI page's input requirement; it does not produce a full-interface, localized visual annotation, or temporal artifact)
- **eval_method:** Effectiveness evaluation (RQ1): 168 text-input widgets (EditText) from 106 popular Android apps crawled from Google Play (12 categories, apps updated after Mar. 2022), explored via DroidBot to locate input pages; metric is "passing rate" (whether generated text lets the UI transition past the input page), each baseline run 3x on an Android x64 emulator. Compared against 11 baselines grouped as random-/rule-based (Stoat, DroidBot, Ape, Fastbot, ComboDroid, TimeMachine, Humanoid, Q-testing), constraint-based (Mobolic, TextExerciser), and learning-based (RNNInput/Liu et al.), plus an ablation QTypist(-T) without prompt-tuning. Result: QTypist passing rate 0.87 vs. best baseline RNNInput 0.45 (93% relative improvement); QTypist(-T) 0.61, showing tuning contributes ~43% relative gain. Quality evaluation (RQ2): user study with 20 recruited software testers (CS majors, 3+ years testing experience) rating generated text on a 5-point Likert scale for agreement/correctness; inter-rater agreement measured with Kendall's W (0.8, high agreement); average score 4.2–4.4 for QTypist vs. lower scores for baselines. Usefulness evaluation (Section V): QTypist integrated into 3 widely used automated GUI testing tools (Monkey, DroidBot, Ape) and run on 30 additional non-overlapping Google Play apps on an Android 6.0 emulator (Xeon E5-2650 v4, 4 CPU/4GB RAM/4GB storage each); metrics = number of triggered activities, triggered UI pages, and number of revealed bugs, compared with/without QTypist integration (activity coverage +28–42%, page coverage +30–52%, bugs +106–122%). A further bug-finding study on 113 top-downloaded apps with Ape+QTypist found 28 previously unreported bugs (11 confirmed, 6 fixed by developers). Additional generalization checks: 20 apps each on iOS and Web (90%/85% pass rate) and 50 apps in 5 non-English languages (86% pass rate).
- **challenges:** Authors explicitly report: (1) QTypist fails when GUI pages lack contextual widgets or the text input itself carries no semantic information, and suggest incorporating nearby/adjacent UI page context could help; (2) apps requiring highly specific/unique inputs (e.g., server address, database connection strings) are not well handled; (3) reliance on UIAutomator to obtain the view hierarchy means apps whose accessibility tree cannot be extracted, or that crash on the emulator, had to be filtered out of the evaluation set (637 apps reduced to 106 due to this and baseline-compatibility constraints), an inherent limitation of the non-visual, accessibility-tree-dependent design; (4) threats to validity acknowledged include representativeness/generality of the sampled apps (mitigated via practitioner interviews) and subjectivity in manual inspection/tagging during dataset construction and labeling; (5) generalization to iOS/Web and non-English languages was only lightly tested (20–50 apps) and authors state "more thorough experiments" are left for future work. (inferred from experimental setup) Because context extraction depends entirely on structured view-hierarchy metadata rather than rendered pixels, the approach would be expected to fail on GUI elements that are visually present but missing meaningful accessibility metadata (e.g., custom-rendered/canvas-based widgets, WebView content, or icon-only inputs without hint text), a limitation not directly discussed by the authors but implied by the method's design.

## Summary

This paper proposes QTypist, an approach for automatically generating semantically valid text inputs to overcome a major bottleneck in automated mobile GUI testing: many app screens require specific, meaningful text (e.g., a flight departure city or a movie title) before testing tools can proceed past that page. Motivated by a pilot study of 2,600 apps that identifies five common text-input categories (identity, geography, numeric, query, comment), the authors reframe text-input generation as a cloze-style fill-in-the-blank task for a large language model. QTypist extracts context information purely from the Android view hierarchy XML (widget hint-text/resource-id/text fields, nearby widgets, activity and app names), applies linguistic pattern templates (derived via card sorting from human-authored prompt seeds) to turn this context into natural-language prompts, and feeds these into a prompt-tuned GPT-3 (Curie) model. A main contribution is an automatic, unsupervised method for constructing a prompt-answer tuning dataset by mining pre-filled/candidate content from search-list widgets, popup menus, and crowd-collected Rico UI data, avoiding costly manual labeling. Evaluated on 106 Google Play apps, QTypist achieves an 87% passing rate, 93% higher than the strongest of 11 baselines, and when integrated into Monkey, DroidBot, and Ape it increases activity/page coverage by up to 42%/52% and bug discovery by up to 122%, including 28 previously unreported bugs later confirmed by developers. Notably, the approach is entirely metadata/NLP-driven rather than vision-based; it never analyzes rendered screenshots.
