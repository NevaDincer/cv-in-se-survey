# image2emmet: Automatic code generation from web user interface image

- **Year:** 2021
- **Venue/Source:** Journal of Software: Evolution and Process (Wiley), Vol. 33, Issue 8, Article e2369
- **DOI:** 10.1002/smr.2369

## Metadata

- **se_area:** development (front-end web development / UI-to-code generation)
- **se_task:** automatically generating real-world HTML-CSS front-end code directly from a web UI prototype/mock-up image, addressing the tedious and time-consuming manual step in which front-end developers must translate a visual UI design into implemented markup
- **cv_technique:** a two-stage deep-learning pipeline. (1) A Faster R-CNN object detector (ResNet-50 backbone, Region Proposal Network + Fast R-CNN classifier/regressor, trained from scratch rather than using VOC/ILSVRC pretrained weights) used to localize and classify UI components (their bounding-box coordinates and component type) within a whole UI screenshot. (2) A custom CNN+LSTM "UI component code generator," built from a CNN image-encoder branch (three repeated conv+ReLU+max-pool+dropout blocks followed by dense layers) that extracts visual features from each cropped UI component image, fused with an LSTM-based sequence branch that models the target code token sequence, jointly decoded through further LSTM layers and a softmax to autoregressively generate the component's Emmet/HTML-CSS code. Classical CV techniques (Canny/Sobel/Laplacian edge detection with contour-based bounding-box inference) are discussed as a rejected alternative UI-component-detection approach, considered too domain-/design-tool-specific compared to the learned Faster R-CNN approach ultimately adopted.
- **platform:** web
- **rationale:** ease of use (explicitly aimed at reducing the tedious, cumbersome, time-consuming manual effort of implementing a UI prototype in code, offering an end-to-end trainable approach that developers can retrain for new component sets rather than hand-writing new detection rules or DSL grammars) and robustness/generality (motivated by the observation that prior heuristic/rule-based or mock-up-metadata-parsing approaches to UI-component detection are tightly coupled to one specific design tool [e.g., Photoshop vs. Sketch] or one specific CV algorithm per domain and must be re-engineered whenever the input source changes, whereas the learned detector generalizes by simply retraining on a new dataset)
- **artifact_type:** localized (the pipeline explicitly separates whole-screen UI component detection/localization from per-component code generation, operating on individually cropped component images rather than the full interface or any temporal sequence)
- **eval_method:** constructs and publicly releases a fully synthetic dataset (9,000 UI component images spanning 9 Semantic-UI component types: Button, Divider, Flag, Header, Icon, Image, Input, Label, List, each auto-generated via a randomized HTML-CSS class-attribute-combination algorithm and rendered to PNG via an automated HTML-to-image ("html2png") pipeline built on wkhtmltopdf, plus 10,000 samples with JSON component-location metadata for detector training); evaluates dataset-collection efficiency across [1,2,5,10,15,20,30,40,50] concurrent threads versus manual collection (RQ1: automated collection takes ~954s at 50 threads vs. an estimated multi-day manual effort); evaluates the UI component detector using precision, recall, and Average Precision (AP) at IoU thresholds of 0.5/0.6/0.7/0.75 per component type (RQ2: AP@0.5 ranges from 0.85-0.97 across the 9 component types, degrading sharply at higher IoU thresholds, attributed to labeling-quality limitations and the small size of many UI components); and evaluates the code generator using TF-IDF-based cosine similarity between generated and ground-truth HTML-CSS token sequences (RQ3: mean similarity exceeds 60% for Button, Divider, Header, Image, Label, and List, but is markedly lower for Flag and Icon, attributed to those component images being much smaller than the model's 128x128 input resolution, limiting the CNN's feature-extraction ability).
- **challenges:** detector AP degrades quickly as the IoU threshold increases, attributed by the authors to imperfect dataset labeling and to the generally small physical size of many UI components (making prediction/ground-truth bounding-box overlap inherently harder to achieve); code-similarity scores are markedly lower for small-sized component types (Flag, Icon) specifically because their images are much smaller than the 128x128 resolution the CNN branch expects, degrading feature extraction; the TF-IDF-based similarity metric used to evaluate code generation is explicitly flagged, in the paper's own threats-to-validity section, as insensitive to HTML hierarchical/structural correctness, since an inverted tag-nesting structure could still score a high similarity due to this metric's bag-of-tokens nature; there may be coordinate offsets between the synthetically-generated ground-truth component locations and what the detector learns, potentially causing detection inaccuracy independent of model capacity; the approach's generalization was validated on only one UI component library (Semantic UI), with the authors noting that other popular libraries (Bootstrap, Bulma, Layui) use different class-naming conventions and would require the entire dataset-generation and retraining process to be redone; and the current pipeline generates code per-component only, with automatically assembling per-component code into one coherent whole-page UI code file left as explicit future work.

## Summary

Front-end developers still lose real time to the design-to-code step: a UI gets designed in Photoshop or Sketch, then someone has to hand-translate it into HTML and CSS. image2emmet targets that gap with an end-to-end pipeline that takes a full web UI screenshot and outputs real HTML-CSS in Emmet notation, rather than the abstract DSLs earlier tools like pix2code produced. Since no public dataset paired web UI images with ground-truth HTML-CSS, the authors built one themselves. By exploiting the class-naming rules of the Semantic UI library, they generated 9,000 labeled component images automatically, with no manual annotation, in a fraction of the time manual collection would have taken. The pipeline itself has two stages. A Faster R-CNN detector, trained from scratch since standard pretrained weights are tuned for natural images rather than UI screenshots, locates and classifies components in the full page. A CNN+LSTM model then converts each cropped component into its HTML-CSS. The results are honest about their limits. Detection precision (AP@0.5 of 0.85 to 0.97) drops fast at stricter IoU thresholds, and code-similarity scores, measured with TF-IDF cosine similarity, sit around 60% for most components but fall noticeably for small ones like icons and flags. The authors are upfront that their similarity metric can't catch structurally inverted HTML, and that the approach hasn't been tested beyond the one UI library used here.
