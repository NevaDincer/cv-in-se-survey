# Make LLM a Testing Expert: Bringing Human-like Interaction to Mobile GUI Testing via Functionality-aware Decisions

- **Year:** 2024
- **Venue/Source:** IEEE/ACM 46th International Conference on Software Engineering (ICSE 2024), Lisbon, Portugal
- **DOI:** 10.1145/3597503.3639180

## Metadata

- **se_area:** Testing
- **se_task:** Fully automated black-box GUI testing of Android mobile apps, formulated as an interactive Question & Answering task between an LLM (acting as a human tester) and the app under test, aimed at maximizing activity/code coverage and detecting crash bugs (GPTDroid tool).
- **cv_technique:** None (genuine computer vision is not used). GUI "perception" is entirely text/structure-based: the tool parses the Android view-hierarchy XML (via UIAutomator) and AndroidManifest.xml to extract app info, activity/page info, and per-widget attributes (text, hint-text, resource-id, class, clickable, nearby-widget text), plus coordinate-derived coarse "upper/lower" screen-position labels (inspired by screen-reader techniques). These are encoded into natural-language prompts (linguistic patterns/templates) fed to GPT-3.5-turbo, which returns operation commands (click/double-click/long-press/scroll/input) mapped back to widgets. No screenshots, pixel data, image classifiers, object detectors, OCR, or vision-language models are involved.
- **platform:** Mobile
- **rationale:** Context-driven (the approach explicitly aims to give the LLM the full app/page/widget semantic and functional context, via GUI-context prompts and a functionality-aware memory prompt, so operations are grounded in the app's actual state and business logic rather than generic random exploration); Ease of use (few-shot/in-context learning with output templates lets a general-purpose LLM be applied to testing without any model training or fine-tuning).
- **artifact_type:** Full-interface (each iteration reasons over the entire current GUI page (all visible widgets, activity name, and app-wide activity list) plus a temporal component in the functionality-aware memory, which tracks the sequence/history of prior pages, widgets, and functions tested across the whole testing trace to guide long-horizon, function-level exploration).
- **eval_method:** Two-part empirical evaluation. (1) Effectiveness: 93 Android apps (20 from the Themis benchmark + 73 newly collected from Google Play, 1,398 activities, 143 known crash bugs) compared against 10 baselines (random/rule-based: Monkey, Droidbot, TimeMachine; model-based: WCTester, Stoat, Ape, Fastbot, ComboDroid; learning-based: Humanoid, Q-testing; plus 5 enhancement-tool combinations e.g. Droidbot+QTypist), measuring activity coverage, code coverage, widgets/activities covered, coverage-over-time, and bug-detection speed/count; plus an ablation study removing GUI-context and functionality-memory modules (and finer-grained sub-module/pattern removal, and sweeping the "k recent steps" memory window). (2) Usefulness: field study on 223 real Google Play apps to detect previously unknown crash bugs, reported to developers and tracked for confirmation/fix status, compared against the three strongest baselines from part 1. (3) Qualitative analysis of representative testing traces to explain four observed capabilities (long meaningful traces, functionality-aware prioritization, valid multi-field text input, compound actions).
- **challenges:** Authors report: (1) local dilemma: LLM struggles to remember long historical exploration context, tending to rely only on recent interactions, risking entrapment in exploration loops (motivated the memory mechanism); (2) low-level dilemma: LLM naturally focuses on low-level widget/activity semantics rather than higher-level app functionality; (3) residual uncovered cases due to widgets/inputs lacking meaningful text or resource-id fields, hindering understanding; (4) some required operations (e.g., database connection setup, drag-to-location, specific long-press sequences) are difficult or impossible to automate; (5) reliance on ChatGPT (gpt-3.5-turbo) as a closed, evolving external service; (6) only five standard operation primitives supported, excluding custom gestures; (7) cost/scale of LLM API calls and running time not deeply discussed as a limitation despite iterative per-step querying.

## Scope note

GPTDroid perceives the GUI purely through the Android accessibility/view-hierarchy XML (obtained via UIAutomator) and the AndroidManifest.xml: text fields, resource-IDs, classes, and coordinate-derived "upper/lower" position labels, which are converted into natural-language prompts for an LLM (GPT-3.5). No pixel/image input, screenshot, or learned visual-perception model (classifier, detector, OCR, VLM) is used anywhere in the pipeline. This is an LLM-driven, structured-data GUI testing approach, not a computer-vision technique; its inclusion in a CV-in-SE review is questionable.

## Summary

This paper reframes automated mobile GUI testing as an interactive question-and-answering dialogue between a large language model and the app under test. The proposed tool, GPTDroid, repeatedly extracts structured GUI context (app metadata, current activity/page details, and widget-level attributes such as text, resource-id, class, clickability, nearby-widget text, and coarse screen position) from the Android view hierarchy, encodes it via hand-designed linguistic prompt patterns, and queries GPT-3.5-turbo for the next action, which is decoded into an executable command (click, double-click, long press, scroll, or input) and applied to the app, with error feedback looped back for retries. To address the LLM's tendency to lose long-range context and focus only on low-level widget semantics, the authors add a functionality-aware memory mechanism that tracks explored functions, visited activities, and recent operations, and periodically queries the LLM about which app functionality is currently being tested. Evaluated on 93 Google Play apps against ten established GUI-testing baselines, GPTDroid improved activity coverage by 32% and code coverage by 20% over the best baseline, and detected 31% more bugs faster; ablations confirmed both the GUI-context extraction and the functionality memory are essential. In a follow-up usefulness study on 223 apps, it found 53 previously unknown crash bugs, 35 confirmed or fixed by developers. Notably, the system's "perception" of the GUI is entirely text-based (view-hierarchy XML), not visual/pixel-based, so its relevance to a computer-vision-in-SE review is limited despite its strong human-like, functionality-driven testing results.
