# Win GUI Crawler: A tool prototype for desktop GUI image and metadata collection

- **Year:** 2022
- **Venue/Source:** 2022 IEEE International Conference on Software Testing, Verification and Validation Workshops (ICSTW 2022)
- **DOI:** 10.1109/ICSTW55395.2022.00046

## Metadata

- **se_area:** testing (GUI test automation), with a secondary data-engineering/tooling purpose (dataset construction to support future machine-vision-based testing/RPA research)
- **se_task:** Automated desktop GUI crawling and dataset collection: depth-first traversal of Windows desktop application GUIs to automatically capture screenshots, bounding-box annotations, and XML/JSON metadata for each GUI element, for later use in training GUI-element-identification machine learning/computer vision models.
- **cv_technique:** None applied within the tool itself. The paper is explicitly a data-collection tool, not a CV model. No image classification, object detection, or deep learning is performed by Win GUI Crawler. Screenshots and bounding boxes are obtained via the WinAppDriver accessibility API (UI Automation tree), not via pixel/image analysis; a rule-based (non-learned) geometric filtering algorithm (bounding-box overlap ratio thresholding, Eq. 1: intersection-over-min-area > threshold) is used to remove non-visible/duplicate/overlapping element annotations. The paper frames the resulting dataset as intended to support future supervised machine learning / machine vision models (e.g., CNN-based GUI element identification, template matching) for desktop GUI test automation, citing prior CV-based GUI work (e.g., pix2code, Rico-based classifiers) as motivation but not implementing such models itself.
- **platform:** desktop (Microsoft Windows GUI applications; UWP, WinForms, WPF, and Win32 apps supported via WinAppDriver, explicitly contrasted with the more mature mobile/web GUI-image dataset literature)
- **rationale:** Context-driven / infrastructure-driven: the tool exists to solve the "robust identification of GUI widgets" problem identified as a leading cause of GUI test automation fragility, by enabling future machine-vision approaches (which the authors argue generalize better than brittle locator-based identification), but the immediate rationale for this specific tool is ease of large-scale, low-cost automated data collection (vs. costly manual/crowdsourced annotation) to fill the gap of no publicly available desktop GUI image database, rather than robustness or ease-of-use of a CV technique per se.
- **artifact_type:** full-interface (captures entire application screens/screenshots) combined with localized (per-element cropped images and bounding-box annotations for each individual GUI element extracted per screen)
- **eval_method:** No quantitative CV evaluation (no accuracy/precision/recall metrics, no baselines, no benchmark dataset comparison, no human study). Evaluation is qualitative/exploratory: the tool was run on 8 popular Windows 10 applications (Calculator, MS Paint, MS Word, TeamViewer, XnConvert, VirtualBox, Adobe Acrobat Reader, GIMP) to test traversal and metadata/screenshot extraction. Success/failure was assessed by visual inspection of output bounding boxes (Figures 2–5): the crawler worked well on native Win32 apps but failed to extract metadata for GIMP (GTK-based UI) and partially failed for Adobe Acrobat Reader (HTML-based UI components). The authors explicitly state this is a prototype-stage debugging exercise, with "extensive validation" and large-scale data collection deferred to future work once the tool matures.
- **challenges:** Explicitly reported by authors: (1) incompatibility with non-native Win32 API applications (e.g., GTK-based apps like GIMP, or HTML-based UI components as in Adobe Acrobat Reader) because WinAppDriver cannot access their metadata; (2) no access to metadata for GUI elements belonging to a different Windows process/window than the main application, since WinAppDriver attaches to one specific process/window; (3) dynamic GUI elements (e.g., logout buttons) that change application state cut the crawler off from further traversal paths it can no longer reach; (4) the crawler is limited to clicking only; it cannot perform other actions such as editing fields or entering credentials, limiting exploration coverage; (5) bounding boxes derived from metadata are sometimes inaccurate (poor fit, too small/wide) or correspond to non-visible elements indistinguishable from visible ones using metadata alone, and the geometric overlap filter cannot achieve 100% accuracy since each application has idiosyncrasies; (6) resulting annotations are described as "noisy," requiring human inspection/correction for high-quality labels.

## Scope note

This paper does not itself apply computer vision to solve an SE problem. Win GUI Crawler is a data-collection prototype that traverses Windows desktop applications via Microsoft's WinAppDriver (an accessibility/UI-automation API, akin to Selenium for desktop apps) and extracts screenshots plus XML/JSON metadata (bounding boxes, element hierarchy) directly from the OS accessibility tree, not from pixel analysis. No image classifier, object detector, or other CV model is trained or applied in the tool itself; the explicit motivation is to build a labeled image dataset so that *future* machine-vision-based GUI element identification research (by others) becomes possible. It is included here as a borderline/infrastructure paper relevant to the CV-in-SE literature (dataset creation for GUI-image ML) rather than as an applied-CV paper.

## Summary

Win GUI Crawler is a prototype tool designed to address the shortage of publicly available labeled GUI datasets for the Windows desktop domain, in contrast to the many existing GUI-image datasets for mobile and web platforms. Built on Microsoft's WinAppDriver (a Selenium-like UI Automation Test framework for Windows apps), the tool performs a depth-first traversal of an application's GUI element tree, restarting from the root whenever it hits a dead end, and prioritizing less-visited nodes to encourage uniform, efficient exploration. At each new screen it captures a screenshot and extracts XML metadata (element hierarchy, bounding boxes, XPath-based element identity across screens). A post-hoc, rule-based filtering algorithm then cleans the noisy raw annotations: it discards off-screen or tiny elements, and for elements whose bounding boxes overlap beyond an area-ratio threshold, decides which is genuinely visible using traversal-order recency and element-type heuristics (e.g., preferring "Button" over "Pane"), outputting cropped per-element images and structured JSON metadata. The tool was tested (not rigorously benchmarked) on 8 common Windows applications, succeeding on native Win32 apps but failing on GIMP (GTK) and partially on Adobe Reader (HTML components) due to WinAppDriver's metadata-access limitations. The main contribution is infrastructural: an open-source (GitHub-hosted) crawler intended to eventually compile a large-scale desktop GUI database to enable future machine-vision-based, more robust GUI element identification for test automation and RPA, and to assist template-matching automation via automatically cropped element images. The tool itself performs no learned visual recognition.
