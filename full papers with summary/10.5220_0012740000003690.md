# Optical Character Recognition Based-On System for Automated Software Testing

- **Year:** 2024
- **Venue/Source:** Proceedings of the 26th International Conference on Enterprise Information Systems (ICEIS 2024), Volume 1, pp. 894–906
- **DOI:** 10.5220/0012740000003690

## Metadata

- **se_area:** Testing
- **se_task:** Automated GUI/regression testing; visual validation testing; element localization for test automation (as an alternative/complement to brittle CSS/XPath locators and page-object model maintenance)
- **cv_technique:** Template matching (OpenCV, pixel-by-pixel matching of a template image within a source screenshot); Optical Character Recognition (OCR) via PyTesseract/Tesseract engine
- **platform:** Web (Selenium WebDriver-driven, tested on Google Chrome)
- **rationale:** Robustness (locators built on DOM/CSS/XPath break when webpages are updated or elements move; visual matching survives such changes); Ease of use (removes the tedious, long-winded effort of building and maintaining page-object models and meaningful element tags)
- **artifact_type:** Localized (operates on cropped screenshots of individual web elements, not the full interface or a temporal sequence)
- **eval_method:** Small-scale case-study/demo evaluation on a single running example (an Amazon "add to cart" shopping scenario) with processing-time measurements pulled from framework logging; no formal benchmark dataset, precision/recall study, or statistical comparison against baselines
- **challenges:** Template-matching processing time varies heavily (sub-second to ~7 seconds) depending on how far the target element is from the pixel search origin (0,0), since matching proceeds pixel-by-pixel; OCR robustness is explicitly limited to clean, typed on-screen text (authors note it would likely fail on handwriting or scanned/newspaper-style text); evaluation is a single illustrative example rather than a broad dataset, so generalizability/robustness claims are not statistically validated; the approach is additive to (not a replacement for) traditional DOM-level testing, so it doesn't eliminate the underlying locator-maintenance problem, only mitigates it.

## Summary

This paper presents an open-source, Python-based AI-assisted test automation framework that augments traditional Selenium/PyTest/BDD-style web testing with two computer-vision capabilities: template matching and OCR. The core motivation is that conventional test automation relies on CSS/XPath locators captured in page-object models, which silently break when a webpage's structure or layout changes, requiring costly re-authoring. The framework instead lets an engineer locate and validate elements visually, either by matching a screenshot template against the live page (template matching, via OpenCV) to obtain click/interaction coordinates, or by extracting on-screen text via Tesseract OCR and comparing it against the expected DOM `text`/`value` attribute (dual DOM+visual validation). The system is organized into five layered "test managers" (manager base, logging, input, validation, visual) built atop Selenium WebDriver, PyTest, and PyTest-BDD/Gherkin feature files, and integrates the CV layer specifically into the Visual Manager class. The paper walks through the full authoring workflow (feature file → page-object model → step definitions) and reports processing-time measurements from a single running example: template matching took between under 1 second and ~7 seconds depending on target element position, while OCR consistently took only a few hundred milliseconds (310ms in the example) and achieved 100% recognition success in the reported instances, attributed to the clean, typed nature of web UI text. The authors argue the combined DOM+visual approach increases tester confidence and better mirrors how human testers actually perceive a page.
