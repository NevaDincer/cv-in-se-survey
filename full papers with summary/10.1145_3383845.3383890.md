# Integrating Traversal and Visual-based Techniques to Initiate UI Exploration Scripting

- **Year:** 2020
- **Venue/Source:** ICCMB 2020
- **DOI:** 10.1145/3383845.3383890

## Metadata

- **se_area:** Development
- **se_task:** Automated generation of initial UI test exploration scripts (SikuliX-format) by combining Accessibility-API-based graph traversal with a computer-vision fallback for extracting interactable GUI elements when the Accessibility API is unavailable
- **cv_technique:** Linear Time MSER (Maximally Stable Extremal Regions) feature/region detection on grayscale screenshots, via OpenCV, to identify bounding rectangles of GUI elements
- **platform:** Desktop
- **rationale:** Ease of use (scriptless generation of the initial test script, output editable in SikuliX IDE); Robustness (visual fallback keeps the framework working on apps/OSes without a usable Accessibility API)
- **artifact_type:** Component (bounding-rectangle element images captured from full-interface screenshots)
- **eval_method:** Demonstration on two open-source desktop applications: Google Calculator (simple, all elements at first container level) and OpenShot video editor (complex, nested containers, tiny icon-based elements); qualitative comparison of elements found via Accessibility API vs. via MSER detection
- **challenges:** MSER cannot guarantee extraction of all interactable elements while excluding non-interactable ones (missed the 'Edit' menu entirely in OpenShot); framework is not fully scriptless since the 'Execute Actions' step still requires scripting; visual approach struggles more on GUIs with tiny, detailed, icon-dense elements than on simple flat layouts

## Summary

Presents a two-condition framework for bootstrapping UI test automation scripts without requiring a human to manually record interactions. Under Condition 1 (Accessibility API available), a "Path Traversal Processor" pulls widget tree information (bounding rectangle, name, control type) directly from the OS Accessibility API (Windows UIA). Under Condition 2 (API unavailable), a "Visual Path Traversal Processor" instead captures an initial screenshot and applies Linear Time MSER, a faster variant of the classic MSER algorithm, on the grayscaled image to detect candidate interactable regions. Both conditions converge on a common pipeline: build a widget tree, traverse it depth-first using Click as the primary action to discover all reachable GUI terminal states, and emit both cropped element images (.png) and a Python automation script (.py) in SikuliX's native format, viewable/editable in the SikuliX IDE.

The paper frames its contribution against four existing GUI-automation paradigms (Capture & Replay, Scripting, Visual/SikuliX-style, and pure API Traversal), arguing each has a distinct weakness (maintenance burden, required programming skill, look-and-feel brittleness, or total dependence on API availability) and that combining Traversal + Visual gets the benefits of automatic script generation while degrading gracefully when the API is missing. The demonstration on Google Calculator (flat, all elements top-level) succeeds cleanly, while the more complex OpenShot video editor exposes MSER's core limitation: one non-obvious element (the "Edit" menu) was missed by the vision-based detector, and some detected elements include non-clickable areas. The authors position this as future work for improvement via additional techniques (Object Recognition, OCR, Machine Learning) and potential integration with TESTAR's more mature Accessibility-API tooling.
