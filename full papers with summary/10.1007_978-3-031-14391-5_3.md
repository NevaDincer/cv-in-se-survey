# GUI Element Detection from Mobile UI Images Using YOLOv5

- **Year:** 2022
- **Venue/Source:** Mobile Web and Intelligent Information Systems (MobiWIS 2022), Lecture Notes in Computer Science, vol. 13475, pp. 32-45 (Springer)
- **DOI:** 10.1007/978-3-031-14391-5_3

## Metadata

- **se_area:** design
- **se_task:** GUI element detection in mobile UI screenshots/wireframes: automatically identifying and localizing (bounding boxes) the type and position of standard GUI components (buttons, icons, input fields, etc.) within a UI image, as a foundational step supporting downstream automated GUI generation/reverse-engineering tools that must first recognize what elements exist and where
- **cv_technique:** YOLOv5 (specifically the YOLOv5s pretrained variant, fine-tuned) object detection, trained as a custom 12-class GUI element detector; benchmarked directly against a prior SSD (Single Shot MultiBox Detector) baseline model from the VINS study; related prior CV pipelines discussed (ResNet50 classification, EAST text detector, flood-filling/Sklansky's/connected-component labeling, Canny edge detection) for context
- **platform:** mobile (Android and iOS UI images, via the VINS dataset combining Rico-derived Android screenshots and Uplabs iOS/Android wireframe designs)
- **rationale:** robustness/accuracy improvement (the explicit motivation is that GUI element detection is a "domain-specific object detection task" where prior CV methods and older object-detection algorithms (SSD) were found inadequate at extracting the unique characteristics of GUI elements with high accuracy, particularly small elements like icons and switches, so a newer, unevaluated-for-this-domain algorithm, YOLOv5, is applied to test for accuracy gains) and ease of use/efficiency (YOLO-family models are noted as fast to deploy with minimal dependency setup and support real-time inference, an advantage over slower two-stage detectors like R-CNN)
- **artifact_type:** localized (individual GUI element bounding boxes and class labels within a whole UI screenshot, not a full-interface holistic representation)
- **eval_method:** direct replication-style benchmark against a prior published baseline (Bunian et al.'s SSD-based VINS study), using an identical dataset (VINS, 4,543 of 4,800 images after removing wireframes), identical class taxonomy (12 GUI element classes), and identical train/validation/test split (3,643/450/450, matching the 80/10/10 ratio) to ensure a fair, controlled comparison. Trained YOLOv5s for 100 epochs, batch size 16 (38h33m total training time on a local Mac mini after cloud/Colab training proved impractical due to 12-hour session limits). Evaluated using standard object-detection metrics: PASCAL VOC mAP at IoU=0.5, MS COCO mAP averaged over IoU thresholds 0.5-0.95, per-class Average Precision (AP), and a confusion matrix at IoU=0.5. Reported an overall test-set mAP of 92.08% for YOLOv5 vs. 76.39% for the SSD baseline (a 15.69-percentage-point improvement), with YOLOv5 outperforming on 10 of 12 classes (only slightly worse on Background Image and Sliding Menu).
- **challenges:** smaller GUI elements (Checked View, Switch) remain harder to detect accurately regardless of algorithm, which the authors attribute to their small size relative to the overall image, an intrinsic small-object-detection limitation the paper explicitly flags as needing future work (e.g., dataset tiling or a YOLO variant specialized for small objects); visually similar element types are confused with each other (18% of Icons misclassified as Images, 9% of Images misclassified as Icons per the confusion matrix); training on a local machine (Mac mini) was required because cloud-based training (Google Colab) was impractical due to its 12-hour session time limit forcing repeated checkpoint reconfiguration for long training runs; the study's class distribution in the training set is uneven across the 12 categories, which the authors note likely limited overall accuracy and could be improved with more balanced data; the work only evaluates the detection sub-task in isolation and does not extend to full downstream UI code/file generation, which is left as future work.

## Summary

This workshop paper tackles a narrow but useful problem in mobile GUI tooling: detecting and classifying individual elements (buttons, icons, text fields, switches) in a static screenshot or wireframe, a step several downstream tools for GUI reverse engineering and cross-platform code generation depend on. Prior work in this space, a hybrid CV pipeline from Chen et al., UIED's flood-fill/ResNet50/EAST approach, and an SSD-based detector from the VINS framework, had not tried the newer YOLOv5 detector, so the authors trained a custom YOLOv5s model on the same VINS dataset, same 12-class taxonomy, and same train/validation/test split used in the earlier SSD-based study, so the comparison would be direct. After converting the annotations to YOLO format and training for 100 epochs (38.5 hours on a local Mac mini, since Colab's 12-hour session cap ruled out cloud training), YOLOv5 reached an overall mAP of 92.08% against the SSD baseline's 76.39%, beating it on 10 of 12 classes, with the biggest gains on harder classes like Icon, Text, and Page Indicator. The confusion matrix tells an honest story too. The model still mixes up visually similar elements, confusing 18% of Icons for Images, and still struggles with small elements like Checked View and Switch. The authors point to dataset tiling or a small-object-optimized YOLO variant as the obvious next step.
