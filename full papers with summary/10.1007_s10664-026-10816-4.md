# VLM-Fuzz: Vision language model assisted recursive depth-first search exploration for effective GUI testing of android apps

- **Year:** 2026
- **Venue/Source:** Empirical Software Engineering, 31:76 (Springer)
- **DOI:** 10.1007/s10664-026-10816-4

## Metadata

- **se_area:** testing
- **se_task:** Automated black-box GUI fuzz testing of Android apps: state-space exploration for code-coverage maximization and crash/bug detection
- **cv_technique:** Vision Language Model (VLM) reasoning, primarily OpenAI GPT-4o Vision, over full-screen screenshots with interactive widgets overlaid with numeric labels, to jointly (a) semantically interpret ambiguous/complex GUI layouts (e.g., recognizing a command-line-style widget, or that an ISBN field expects a specific data format) and (b) generate a structured, ordered sequence of GUI actions (tap/long-press/swipe/input/scroll) as text output parsed by the tool; a preliminary VLM-selection study also benchmarked Claude 3.5 Sonnet, Gemini 1.5 Flash, Qwen2-VL-7B, Pixtral-12b, and minicpm-llama3-v on a 'Task Completion Rate' metric before choosing GPT-4o
- **platform:** mobile (Android)
- **rationale:** context-driven (VLM reasons about the semantic meaning of screen content, e.g., musical notation, symbols, expected field formats, that plain widget-property heuristics cannot interpret); robustness (hybrid design falls back to a cheaper non-VLM heuristic action-performer when VLM output is ambiguous, imperfect, or the screen lacks text-input widgets, cross-checking VLM-suggested actions against static widget properties); ease of use / generality (fully black-box: requires no source code, app instrumentation, or OS/device modification, unlike model-based or code-coverage-guided baselines)
- **artifact_type:** full-interface (the VLM is given the entire current screenshot, with all currently interactive widgets numerically labeled directly on the image, and reasons/generates an action plan over the whole screen at once, rather than over isolated per-widget crops)
- **eval_method:** RQ1: benchmarked against state-of-the-art fuzzers APE and DeepGUI on the pre-instrumented AndroTest suite (59 apps after exclusions), measuring class/method/line coverage via the Emma coverage tool, 60-minute time-box per app, 5 repeated runs, with Shapiro-Wilk normality tests followed by paired t-tests for significance. RQ2 (ablation): ablated the VLM component (VLM vs. non-VLM-assisted variant on 5 apps) and the multi-entry launching strategy (single-entry variant VLM-Fuzz_s vs. APE) to isolate which architectural choices drive coverage gains. RQ3 (bug detection): ran on 80 recent official Google Play apps (crashes manually triaged by two authors, cross-checked against APE, and re-validated on updated app versions 8 months later) and on the 79-app Themis benchmark of documented real-world bugs.
- **challenges:** Monetary/latency cost of proprietary VLM API calls, mitigated via on-demand invocation only for screens classified as 'complex' (containing text-input widgets); dependence on a proprietary, evolving model (GPT-4o) raises reproducibility concerns due to potential LLM drift, which the authors mitigate only by keeping the experiment window short; VLM output can be syntactically/semantically imperfect and is not blindly trusted, actions are cross-checked against the GUI's static properties and a non-VLM fallback is triggered on failure; the current implementation supports only 7 GUI event types (vs. Android Monkey's 33, e.g., no drag/pinch/multi-touch), which the authors identify as an implementation limitation (not a limitation of the approach itself) that causes underperformance on apps like divideandconquer and multismssender that require swipe/drag interactions; VLMs were also observed to be weaker at inferring non-visible interaction patterns (long-press, scroll, hidden menu activation) than at reasoning about visually apparent elements; on the Themis benchmark, many of the benchmark's own official bug-reproduction scripts were themselves not reproducible due to stale GUI selectors, permission pop-ups, and dead backend services, limiting the evaluation's coverage of documented bugs.

The core technical contribution is the strategic, on-demand use of vision-language reasoning over GUI screenshots to drive a software testing (fuzzing) task, with an explicit ablation study (RQ2) isolating and quantifying the VLM's specific contribution to code coverage, which supports the visual/vision-language component being substantive rather than incidental. ## Summary

VLM-Fuzz is a black-box Android GUI fuzzing tool that pairs a heuristic-guided, state-aware recursive depth-first search with on-demand vision-language-model reasoning, aimed at three gaps the authors see in prior fuzzers: reasoning about complex or dynamic layouts, generating semantically valid human-like inputs (recognizing that a screen expects a bash command or an ISBN number, for example), and avoiding redundant re-exploration of states already visited. The tool parses the AndroidManifest to enumerate every app component, not just those reachable from the main launcher, allocates a per-component time budget weighted toward menu-rich, widget-dense screens, and explores each component's GUI recursively. A screen counts as "complex" if it has text-input widgets, and only then does GPT-4o Vision get invoked: given a screenshot with widgets numerically labeled, it produces a structured action sequence. Simpler screens run on cheaper heuristics instead, clickable-widget sentiment ordering, progress-bar-aware waiting, transient-state handling for pop-ups and drop-downs, and a transition-record backtracking mechanism that revisits missed widgets. Benchmarked against APE and DeepGUI on the AndroTest suite, VLM-Fuzz reached statistically significant gains in class and method coverage, plus line coverage over APE, and separately proved useful for real bug-finding, turning up 52 confirmed unique crashes across 12 recent Google Play apps and 140 previously undocumented crashes on the Themis benchmark. Ablations show both the VLM component and the non-VLM algorithmic changes, multi-entry launching, per-activity recursive exploration, budget-aware prioritization, contribute to the coverage gains independently.
