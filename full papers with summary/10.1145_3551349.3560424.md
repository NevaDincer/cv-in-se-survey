# Too Much Accessibility is Harmful! Automated Detection and Analysis of Overly Accessible Elements in Mobile Apps

- **Year:** 2022
- **Venue/Source:** 37th IEEE/ACM International Conference on Automated Software Engineering (ASE '22)
- **DOI:** 10.1145/3551349.3560424

## Metadata

- **se_area:** testing (accessibility and security testing of mobile apps)
- **se_task:** automated detection of "over-access": Android UI elements that expose more information or functionality to Assistive Technology (AT) users (e.g., TalkBack screen reader) than is available to sighted/touch users, with associated security, privacy, and workflow-violation implications
- **cv_technique:** minimal/incidental: a pixel-uniformity check on a screenshot crop (verifying all pixels within a node's bounding box are the same color) used only to detect "camouflaged" empty placeholder nodes (condition A3); everything else in the pipeline (P1–P6, A1–A2 conditions; reachability/actionability verification) operates on the accessibility-node XML tree and live AT interaction, not on image/pixel analysis.
- **platform:** mobile (Android)
- **rationale:** robustness (detecting overly-permissive AT exposure that developers did not intend, across arbitrary apps); the pixel-check specifically exists because no other node attribute (e.g., color) is available to detect a camouflaged/placeholder element, so a lightweight, model-free check was chosen deliberately over "advanced computer vision and machine learning algorithms" for screenshot structure inference.
- **artifact_type:** localized (the pixel check operates on an individual, tightly-cropped UI element's bounding box, not the whole screen)
- **eval_method:** multi-RQ empirical evaluation: RQ1 accuracy of the OA Detector (rule-based static checker) and OA Verifier (dynamic AT-based confirmation) on 60 screens from 30 real apps, reporting per-app-state precision/recall (84.23% average detector precision; 100% verifier precision, 83.27% verifier recall) with manual TP/FP/FN labeling by the authors; RQ2 prevalence study applying the tool to 15 real-world app lockers (most-popular, random, and least-popular tiers) to check for bypassable lock protections, with manual confirmation and developer disclosure; RQ3 qualitative categorization of all detected OA elements by real-world impact (accessibility degradation, security exposure, workflow/logic violation); RQ4 runtime performance measurement (~54s per verified action, ~571s average total per app).
- **challenges:** the pixel-uniformity heuristic for camouflaged elements requires a screenshot, which is unavailable for apps that block screen capture (e.g., apps showing copyrighted content), causing missed detections in those cases; the detector's "covered" rule produces false positives on transparent/partially-covered layouts since node color information is not exposed in the accessibility tree; the verifier can produce false negatives when an AT gets stuck in navigation loops on complex scrollable/dynamically-loading widgets (e.g., a map widget, or a web app that refetches a different DOM/XPath structure on each scroll); the empirical study's OA-condition taxonomy was derived from manually coding only 100 states from 20 apps, an authors-acknowledged external-validity limitation.

## Scope note

Computer vision plays only a superficial, minor role in this paper. The core detection/verification pipeline (OverSight) works entirely on the Android accessibility-node tree (XML attributes: bounds, visibility, drawing order, package name, action list, etc.) and dynamic AT interaction; no image analysis is involved there. The only CV-adjacent step is one of six detection rules (A3, "Camouflaged" elements): to find empty placeholder nodes, the tool crops the screenshot region at a node's bounding box and checks whether all pixels in that crop are a single uniform color, a trivial pixel-uniformity check and not a learned or sophisticated CV technique. The paper explicitly notes that "advanced computer vision and machine learning algorithms" for inferring UI structure from screenshots exist (citing Screen Parsing and similar work) but says it deliberately avoided them in favor of this simple heuristic. Please confirm this paper should count as "CV-in-SE"; it may be better classified as an accessibility/security testing paper with only incidental image processing.

## Summary

This paper introduces the "over-access" problem in mobile app accessibility: the dual of the well-studied "under-access" problem, where an Assistive Technology (AT) such as Android's TalkBack screen reader can reach information or trigger actions that are not actually available to sighted, touch-based users. The authors first conduct an empirical study coding 100 UI states from 20 Android apps to derive a taxonomy of conditions that produce "Overly Accessible" (OA) elements, split into Overly Perceivable conditions (out-of-boundary, covered by another element, zero-area bounding box, invalid bounds, marked Android-invisible, or belonging to a different app's package, as seen when one locked app's lock screen accidentally exposes another app's UI tree) and Overly Actionable conditions (hidden-but-clickable, disabled-but-still-triggerable, or camouflaged empty placeholder elements). They then build OverSight, an automated two-stage tool: an OA Detector statically analyzes the accessibility-node XML tree of a captured app state to flag "Over Accessibility Smells" matching these conditions (with one of the six checks, detecting camouflaged placeholders, additionally cropping the screenshot at the node's bounds and testing pixel-color uniformity, since no color attribute exists in the node tree itself), and an OA Verifier dynamically confirms each flagged smell is actually reachable and actionable using both the standard TalkBack screen reader and a custom "Super AT" that exercises the full Accessibility API. Evaluated on 60 screens across 30 real apps, the detector achieves 84.23% average precision and the verifier achieves 100% precision / 83.27% recall, while pruning 84% of nodes that would otherwise need expensive dynamic verification. Applying the tool to 15 real-world app lockers surfaces serious real-world security findings: 13 of 30 tested app-lock states could be bypassed via TalkBack, including several belonging to apps with over 100 million installs, allowing an AT user to disable a security lock without entering a PIN, findings the authors manually confirmed and reported to the affected developers. Beyond app lockers, the qualitative analysis (RQ3) surfaces accessibility-degradation cases (screen readers forced through irrelevant hidden content), security exposures, and workflow-violation bugs (e.g., an AT user decrementing a passenger counter below zero in the Airbnb app, or bypassing a paywall to read premium content in a meditation/news app that a sighted touch user could not access).
