# GUing: A Mobile GUI Search Engine using a Vision-Language Model

- **Year:** 2025
- **Venue/Source:** ACM Transactions on Software Engineering and Methodology (TOSEM), Vol. 34, No. 4, Article 88
- **DOI:** 10.1145/3702993

## Metadata

- **se_area:** design
- **se_task:** text-to-GUI (and sketch-to-GUI) retrieval for design search: given a natural-language app-feature description (or a hand-drawn sketch), retrieve relevant real GUI screenshots to support rapid prototyping, design inspiration, and requirements elicitation/refinement (e.g., during interviews or workshops); also evaluated for GUI screen classification
- **cv_technique:** a custom vision-language model "GUIClip," created by fine-tuning CLIP (ViT-based image encoder + transformer text encoder, contrastive learning) on a large screenshot-caption dataset; Vision Transformer (ViT) used for a three-way image classifier (screenshot / surrounded-screenshot / irrelevant) during dataset construction; DEtection TRansformer (DETR, CNN backbone + encoder-decoder transformer) used as an object detector to localize and crop screenshot regions out of "surrounded screenshot" marketing images; PaddleOCR used to extract on-image caption text; a "Dual GUIClip ViT" (two GUIClip image-encoder towers, one frozen) built for sketch-to-GUI retrieval; approximate nearest-neighbor search (via Faiss, Voronoi-cell partitioning) used to accelerate embedding retrieval at scale
- **platform:** mobile (Android, plus iOS-relevant Google-Play-wide marketing images)
- **rationale:** robustness (screenshots collected via automated/crowdsourced runtime exploration, as prior datasets like Rico do, miss features requiring authorization or specific input data (e.g., dashboards with charts), so the paper instead mines developer/vendor-curated Google Play "app introduction images," a richer and more representative visual source) and context-driven design (combining visual and textual modality closes the "semantic gap" that pure text-only or pure image-similarity retrieval approaches suffer from, since prior text-based engines like GUIGLE/RaWi ignore icons, backgrounds, and other visual information)
- **artifact_type:** full-interface (whole screenshots, cropped from marketing images or taken directly, are embedded and retrieved as complete screens; the sketch-to-GUI variant also operates at the level of a whole hand-drawn screen sketch, not individual widgets)
- **eval_method:** four experiments across multiple RQs: Exp1 (RQ1) benchmarks GUIClip against CLIP, an OCR+BGE text-only baseline, and a "GUIClip-CS" ablation (trained without the paper's own SCapRepo dataset) on three screenshot-caption datasets (SCapRepo, Screen2Words, Clarity) using Recall@1/3/5/10/50/100; Exp2 (RQ2) is a manual human evaluation with 4 expert evaluators (5+ years SE experience) comparing GUing, GUing-CS, and the prior RaWi search engine on 188 real-world app-feature queries derived from industry articles, using P@k, MRR, and HITS@k with a blinded, shuffled results interface to reduce evaluator bias; Exp3 (RQ3a) evaluates GUIClip on GUI classification (zero-shot and linear-probe) using the Enrico dataset (1,460 screenshots, 20 categories) against CLIP and OCR+BGE; Exp4 (RQ3b) evaluates a Dual GUIClip ViT model on sketch-to-GUI retrieval using the Swire dataset (3,551 sketch-screenshot pairs) against a reimplemented Swire baseline and Dual CLIP ViT, in both zero-shot and fine-tuned settings.
- **challenges:** the DETR-based screenshot classifier/cropper and OCR caption-extraction pipeline both required substantial manual annotation effort to bootstrap training data (3,615 hand-labeled images for classification, 1,768 hand-annotated bounding boxes for cropping) and depend on high-precision thresholds (0.9 confidence) to keep the automatically constructed 303k/135k-pair dataset clean; GUIClip's advantage over text-only retrieval reverses on the Clarity dataset, whose captions are unusually long and detailed (near-transcriptions of on-screen text), showing the vision-language approach loses to text-only matching when captions are essentially verbose UI-element descriptions rather than feature-level summaries; the reimplemented Swire baseline could not match the original paper's reported numbers because Swire's implementation and exact training/test split were never released, forcing the authors to approximate settings and acknowledge this as a threat to validity; query selection for the human evaluation (Exp2) was drawn from marketing-company blog articles rather than a validated gold-standard query set, a self-acknowledged external-validity limitation; the retrieved screenshots from the authors' own ScreenRepo dataset have irregular (non-rectangular/non-uniform) crop shapes since they originate from stylized marketing images rather than clean runtime screenshots.

## Summary

This paper addresses the "text-to-GUI" retrieval problem for app design: given only a textual feature description (common in early requirements/ideation phases before any mockup exists), retrieve relevant real-world GUI screenshots that can serve as design inspiration or rapid-prototyping references. Existing approaches were limited either to keyword or BERT-based textual matching over GUI metadata (GUIGLE, RaWi), ignoring visual information like icons, colors, and backgrounds, or required an existing sketch/wireframe/screenshot as the query, which is unavailable in the earliest ideation stage; moreover, the underlying datasets (Rico, ReDraw) are built via crowdsourced or automated runtime exploration, which systematically misses app features that require authorization or specific input configurations. The authors instead mine Google Play "app introduction images," marketing screenshots curated and captioned by the app vendors themselves to highlight their best features, building an automated pipeline (ViT-based three-way image classifier, DETR-based screenshot-region detector/cropper, PaddleOCR caption extraction, language filtering, and deduplication) that produces two new public datasets: ScreenRepo (303k screenshots) and SCapRepo (135k screenshot-caption pairs). These are used to fine-tune OpenAI's CLIP model into "GUIClip," a GUI-domain vision-language model, which then powers "GUing," a search engine that embeds both screenshots and text queries into a shared space and retrieves via cosine similarity with Faiss-accelerated approximate nearest-neighbor search. GUIClip substantially outperforms vanilla CLIP and a text-only OCR+BGE baseline on text-to-GUI retrieval (Recall@10 up to 0.687 on SCapRepo vs. 0.392 for CLIP), and the full GUing engine beats the prior state-of-the-art RaWi search engine in a blinded human evaluation (HIT@10 of 0.914 vs. 0.701). A particularly interesting result is the ablation showing that removing the authors' own vendor-curated SCapRepo/ScreenRepo data ("GUIClip-CS," trained only on prior academic caption datasets) causes a dramatic performance collapse, demonstrating that the value of the contribution lies as much in the novel, developer-curated dataset itself as in the model architecture. The paper further shows GUIClip transfers well to two auxiliary tasks without being designed for them: GUI screen classification (Enrico dataset, beating CLIP by ~20 F1 points) and sketch-to-GUI retrieval via a derived "Dual GUIClip ViT," outperforming the original Swire sketch-retrieval model even using Swire's own self-reported numbers.
