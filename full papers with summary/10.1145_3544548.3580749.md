# BAGEL: An Approach to Automatically Detect Navigation-Based Web Accessibility Barriers for Keyboard Users

- **Year:** 2023
- **Venue/Source:** CHI 2023 (ACM Conference on Human Factors in Computing Systems), April 23–28, 2023, Hamburg, Germany
- **DOI:** 10.1145/3544548.3580749

## Metadata

- **se_area:** testing
- **se_task:** Automated web accessibility testing for keyboard navigation, detecting and localizing "Keyboard Navigation Failures" (KNFs): unintuitive navigation order, unintuitive change-of-context, and unapparent keyboard focus, as defined by WCAG success criteria.
- **cv_technique:** Perceptual image differencing (PID) for comparing before/after-focus screenshots of UI elements; color-contrast analysis (WCAG relative-luminance contrast ratio formula) applied to pixels in the detected difference region; Median Cut Quantization / Modified Median Cut Quantization (MMCQ) color quantization to extract dominant colors from focus/adjacent image regions and reduce color noise; pixel-region/area-based thresholding of screenshot crops to determine minimum focus-indicator area.
- **platform:** web
- **rationale:** Robustness / ease of use: static analysis of HTML/CSS/DOM source cannot reliably determine whether a keyboard focus indicator is visually perceivable, since focus styling can be implemented in many different, dynamically-generated ways (CSS outlines, background/color changes, JS-driven transitions, overlapping elements, anti-aliasing, etc.). The authors explicitly argue traditional static program analysis is insufficient and adopt image-based (CV) comparison of rendered screenshots as a robust, implementation-agnostic way to determine actual visual appearance/contrast as a keyboard user would perceive it, mirroring how WCAG "sufficient contrast"/visibility criteria are defined in terms of rendered color rather than source code.
- **artifact_type:** localized: the CV pixel-diff/contrast analysis is applied per-element, on cropped screenshot regions (before/after focus) of individual interactive elements, to localize the specific faulty element responsible for a KNF (not full-page classification, and not a purely temporal/video technique, though it does compare two states, focused vs. unfocused, of the same element).
- **eval_method:** Empirical evaluation on 20 real-world web pages (10 from Moz's Top 500 sites, 10 from a curated list of government/education/e-commerce/service sites, filtered down via manual keyboard interaction to pages containing at least one KNF type; final set excluded gov/edu sites since none showed KNFs). Ground truth was established by the authors manually interacting with each page via keyboard, following WCAG Success Criteria/Techniques. Pages were captured/frozen via mitmproxy (and a web-scraping fallback) for reproducibility. Compared against 5 industry/research accessibility tools (WAVE, ARC Toolkit, Axe DevTools Pro, Tenon Check, QualWeb) using precision/recall/F1 per KNF type, plus run-time (RQ2). Results: BAGEL achieved F1 of 93% (Unintuitive-Nav-Order), 83% (Change-of-Context), 95% (Unapparent-Focus), versus other tools' average F1 of 15–43%; average run-time ~7.5 minutes/subject (dominated by screenshot capture, 59% of time). The study also included qualitative validation: outreach to developers of the 20 subject sites (12 reached, 5 acknowledged, 3 partially fixed reported issues) and a small user study with two keyboard-dependent users with disabilities (one blind screen-reader user, one sighted user with motor disability) who interacted with 6 subject pages and gave qualitative feedback confirming BAGEL's detections matched real usability problems. Implemented in Java using Selenium WebDriver/FirefoxDriver, DBSCAN clustering (iFix), and aShot for screenshots; run on Firefox 92.0 at 1920×1080.
- **challenges:** Authors explicitly report: (1) approach only analyzes a single web page's initial UI state; it cannot find KNFs in dynamically revealed content (e.g., hidden panels/modals in SPAs) that appear only after further interaction; (2) evaluation used only one page per website, though selection followed WCAG-EM sampling guidance for representativeness; (3) tool is built on Selenium's FirefoxDriver only, so results may not generalize across browsers since default focus-ring styling differs (Firefox has the least visible default focus, used deliberately as a lower-bound baseline); (4) run-time is significantly slower than other scanners (~7.5 min/subject, 98% spent building the KFFG model, especially screenshot capture); authors argue this is acceptable relative to other SE testing tasks but note distributed/parallelized crawling or improved screenshot capture as future work; (5) reported false positives/negatives from inaccurate FuncSet clustering (e.g., visually similar but functionally distinct button groups misclustered), imperfect screenshot capture (blank/black images, extraneous pixels bleeding into crops), and inability to focus certain non-natively-focusable custom elements (<div>/<h2> without proper ARIA/tabindex) with Selenium.

## Summary

This paper presents BAGEL, a fully automated technique for detecting "Keyboard Navigation Failures" (KNFs), accessibility barriers defined under WCAG Success Criteria 2.4.3, 2.4.7, 3.2.1, and 3.2.2, that prevent or hinder keyboard-only users (e.g., blind users on screen readers, users with motor impairments) from intuitively and predictably navigating web page UIs. The approach dynamically crawls a page by simulating keyboard interactions via Selenium/FirefoxDriver to build a Keyboard Focus Flow Graph (KFFG) capturing both the navigation order (via DBSCAN-based semantic clustering of visually/structurally related "FuncSets") and the visual appearance of focus indicators. To detect "Unapparent Keyboard Focus" failures, BAGEL captures before/after-focus screenshots of each interactive element and applies computer-vision techniques: perceptual image differencing to locate the visually changed region, WCAG contrast-ratio math on the corresponding pixels, and Modified Median Cut Quantization to extract dominant colors for robust, noise-tolerant contrast comparison, since static analysis of CSS/DOM alone cannot reliably determine whether a focus indicator is actually perceivable to a user. The main contribution is the first formalization of KNFs plus a fully automated, DOM-agnostic detection technique that substantially outperforms five state-of-the-art accessibility scanners (average F1 90% for BAGEL vs. 15–43% for competitors) across 20 real-world websites, validated further through developer outreach and a small qualitative study with two users with disabilities. A notable detail is the run-time/accuracy trade-off: BAGEL takes ~7.5 minutes per page (dominated by screenshot capture), far slower than lightweight DOM scanners, but its authors argue this cost is justified given its markedly higher precision and recall.
