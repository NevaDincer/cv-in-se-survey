# Model-based GUI automation

- **Year:** 2025/2026 (received 27 Oct 2023; published online 25 Oct 2025; journal issue dated 2026, vol. 25, pp. 871-908)
- **Venue/Source:** Software and Systems Modeling (Springer), Regular Paper
- **DOI:** 10.1007/s10270-025-01319-9

## Metadata

- **se_area:** testing (GUI testing, integration/unit testing of automation code) and, more broadly, software/process automation and maintenance (script fragility, code complexity over time)
- **se_task:** visual GUI test automation and general GUI process automation; specifically: reducing script fragility, enabling integration/unit testing of automation code via mocking, and (as a secondary application) automated dataset generation and game/RL agent interfacing
- **cv_technique:** classical pattern matching via OpenCV's `matchTemplate` (deterministic template matching against a reference image), used as the perception layer underlying both traditional "process-based" visual GUI automation and the paper's own "model-based" approach; no learned/deep CV technique is introduced or evaluated
- **platform:** general framework, demonstrated on a desktop-emulated mobile game (*Dawn of Titans*, via the "DoT" app / Brobot framework); explicitly claimed to generalize to web, desktop, and enterprise (ERP/CRM) GUIs
- **rationale:** robustness (primary motivation: countering script fragility and the stochasticity of GUI environments via explicit state tracking and dynamic pathfinding); ease of use / maintainability (decoupling environment knowledge, the "State Structure," from automation business logic, reducing code-complexity growth from exponential to polynomial); context-driven (explicit state-management system reasons over combinations of currently active states rather than a fixed script position)
- **artifact_type:** full-interface, the model treats the entire visible GUI/scene (Ξ) as ground truth and reasons over sets of co-occurring elements grouped into "states," rather than localizing a single detection or tracking temporal video sequences
- **eval_method:** primarily analytical/mathematical (closed-form and simulated path-count growth analysis comparing process-based vs. model-based code complexity; a probabilistic model of process-based automation reliability given per-action success rates) supplemented by one small illustrative case study (the DoT app automating an island-image-collection task in a mobile game) and a small empirical stochasticity demonstration (OCR text-recognition variation on the word "Lakes" across ~18,600 samples); no controlled comparative user study or benchmark suite is run
- **challenges:** single-author, unfunded, independent-researcher work with the Brobot framework as the only implementation; empirical validation limited to one simple three-to-four-state toy application rather than production-scale or multi-application (ERP/CRM) systems as claimed possible; the underlying CV/perception mechanism (template matching) inherits known pattern-matching brittleness (sensitivity to resolution, scaling, contrast) that the paper's architecture works around procedurally rather than solving perceptually; claims about scalability to hundreds of states are analytical projections, not measured

## Scope note

, review before including in the survey.** The CV technique here is classical, deterministic template and pattern matching (OpenCV's `matchTemplate`), described only briefly as the existing mechanism visual GUI automation already relies on. It isn't a novel or learned CV method the paper develops or evaluates. The paper's real contribution is a theoretical and architectural framework, a formal mathematical model plus the Brobot implementation, for making GUI automation state-based instead of script-based. Testing (GUI testing and integration/unit testing of the automation code itself) is only one of several downstream applications discussed, alongside RPA, ML dataset generation, and game or RL automation. Empirical validation is a single toy case study, a mobile-game automation bot, with no experiments evaluating the CV component itself. This one is borderline: the CV usage is superficial next to a strong theoretical SE contribution.

## Summary

This paper introduces model-based GUI automation, reframing conventional visual GUI automation tools like SikuliX (which lean on OpenCV template matching) as inherently process-based: built from rigid, sequential scripts that break down under the ordinary unpredictability of real GUI environments. The author proposes an alternative formal model where a GUI environment is represented as an explicit graph of states, cohesive, sometimes simultaneously active, groupings of GUI elements, connected by transitions, with a path-traversal component that dynamically finds and re-plans routes between states, similar to A*-style heuristic search. The paper works out a full mathematical formalization of state management, actions, transitions, and path traversal, along with a complexity analysis showing that process-based robustness needs geometrically many hand-coded fallback paths while the model-based approach scales polynomially. It also describes the open-source Brobot framework that implements all of this, including a mocking mechanism that lets developers write integration and unit tests for the automation code itself, something the author says has mostly been missing from GUI automation tooling. A running example, an app that farms island images from the mobile game Dawn of Titans, shows states, transitions, and dynamic path re-selection in action when a transition fails. The paper closes with broader applications in mind, RPA across enterprise systems, resilient CI/CD GUI testing, ML training-data generation, and a "Visual API" linking GUI automation to reinforcement-learning agents, though these stay conceptual rather than empirically tested.
