# PSDoodle: Fast App Screen Search via Partial Screen Doodle

- **Year:** 2022
- **Venue/Source:** Proceedings of the IEEE/ACM 9th International Conference on Mobile Software Engineering and Systems (MOBILESoft 2022), pp. 89–99
- **DOI:** 10.1145/3524613.3527816

## Metadata

- **se_area:** Requirements and design (UI/UX design-example search and prototyping-inspiration retrieval), a design-support/requirements-elicitation tool and not a testing, development, or maintenance tool
- **se_task:** Interactive, iterative sketch-based (partial-doodle) search of an existing mobile-app-screen repository, intended to help developers without formal UI/UX training quickly find design inspiration, gather requirements, or benchmark against existing designs, without needing to formulate keyword queries or complete a full-screen sketch before getting feedback
- **cv_technique:** Two-part deep-learning + custom-scoring pipeline. **(1) UI Element Doodle Recognition**: a stroke-sequence classifier following Google QuickDraw's architecture (three stacked 1-D CNN layers with 48/64/96 filters, kernel sizes 5/5/3, followed by 3 Bi-LSTM layers and a fully-connected layer) that recognizes a *single* UI-element doodle incrementally, stroke by stroke, rather than only after the doodle is finished. Trained via transfer learning: pretrained on 23 QuickDraw categories, then fine-tuned/tested on the authors' own **DoodleUINet** (≈600 "correct" doodles per class × 16 stylized Android UI-element classes, crowd-collected) plus a hand-picked set of 7 QuickDraw categories repurposed as UI placeholders (e.g., "jailwindow"→arbitrary image, "square"→container, "cloud"→default/unsupported icon), following SWIRE's convention of using a squiggly line for text. Achieves 94.5% test accuracy (later 94.9% after a retraining round addressing outer-boundary-shape confusion). **(2) Screen Similarity/Retrieval**: a custom multi-scale spatial-overlap scoring algorithm (Algorithm 1) operating over a precomputed dictionary mapping each of PSDoodle's 24 UI-element types to per-tile area/count statistics for all 58,126 usable Rico screens; three granularity levels (scale-1: 24 tiles / scale-2: 6 tiles / scale-3: whole screen) let a doodle match a screen even if its exact position/size differs from the sketch, with IDF-style rarity weighting boosting the score contribution of less-common UI-element types; five hyperparameters (p1,p2,p3 per scale level, plus Δw and Cw for weight/count differences) were tuned via exhaustive GridSearchCV on a separate 30-sketch tuning set (5 CS grad students), yielding p1=39, p2=8, p3=9, Δw=0.4, Cw=11.
- **platform:** Mobile (Android; built on the Rico dataset, 72k raw screens, 66,261 with hierarchy data, filtered down to 58,126 "usable" screens after excluding screens dominated by a single text area/image/webview)
- **rationale:** Ease of use (the paper's central motivating comparison is against keyword search, which requires vocabulary novice users may lack, and against SWIRE-style full-screen sketch retrieval, which requires completing an entire screen sketch, often via a paper-and-camera workflow involving fiducial markers and offline processing, before receiving any feedback; PSDoodle's main contribution is *interactivity*: the top-N result screens update live after every stroke/element, letting the user stop sketching the moment the target appears); the design explicitly targets developers "with little to no UI/UX/design background" as the intended user population
- **artifact_type:** Localized (individual, incrementally-recognized UI-element doodle strokes as the query input) matched against Full-interface screen layouts (whole-screen Rico hierarchy structures as the search index), a partial/interactive sketch query evaluated against full-screen search targets
- **eval_method:** A 10-participant (CS students, no formal UI/UX training, ages <30) user study after a ~9-minute interactive tutorial, addressing 4 RQs. **RQ1** (partial-doodle recognition): per-class comparison of average total strokes vs. strokes-to-first-correct-top-1/top-3 prediction (Table 2, full 16+7 class breakdown), plus manual inspection of 35 misclassified test-set doodles identifying 4 recurring failure patterns (outlier stroke counts, unusual stroke sequences, shape deviation, resemblance to another category). **RQ2** (top-10 screen-retrieval accuracy): 34 sketches across 30 randomly-selected target Rico screens (≥2 PSDoodle-supported icons; 26 also present in the SWIRE dataset) yielding 88.2% top-10 accuracy, compared against SWIRE (61%) and a SWIRE follow-up work by Sain et al. (90.1%). **RQ3** (query economy): comparing PSDoodle's average 5.5 UI elements per successful query against the ~21.1-element average a full SWIRE-style sketch would require for the same screens, including a direct experiment converting PSDoodle's own partial sketches into SWIRE-style bitmaps and showing the SWIRE follow-up network fails to retrieve the target screen in the top-10 for any of the 26 convertible sketches. **RQ4** (latency): end-to-end interactive round-trip <2s per query (sketch recognition <0.1s; similarity scoring+ranking <1s), and total session time 30–259s vs. SWIRE's reported 246s sketch-only average. Closed with a post-study System-Usability-Scale-style Likert questionnaire (8/10 respondents) and informal qualitative feedback on preferred sketching devices and interaction style.
- **challenges:** Reported limitations directly stated by the authors: (1) Four UI-element classes with outer-boundary shapes (avatar, cancel, checkbox, plus) were confusingly sketched by several participants (who sometimes omitted the outer ring/border), leading to systematic misclassification; a post-hoc retraining round with boundary-stripped additional samples improved overall accuracy only marginally (94.5%→94.9%) but specifically +9pp for avatar, at the cost of slightly regressing a few other classes (Camera, Search, and to a lesser degree Back/Dropdown/Forward/Menu/Play/Plus/Share/Switch). (2) Doodle-to-screen retrieval failures traced to two concrete cases where the underlying Rico UI-element hierarchy/clustering (inherited from prior work by Liu et al.) simply has no label information for a user-sketched icon (e.g., "Rico has no information about Star Icon" / "Avatar Icon"), a data/label-coverage limitation rather than a PSDoodle algorithmic failure; the authors note this could be reduced by further improving upstream Rico element clustering/classification. (3) The query vocabulary is hard-capped at 16 DoodleUINet + 7 repurposed QuickDraw classes (23 total), so screens requiring unsupported element types cannot be effectively queried. (4) DoodleUINet is deliberately "stylized" (single canonical drawing style per class, obtained by briefly showing crowdworkers a target image before sketching), unlike QuickDraw's flexible multi-style data, which constrains generalization to sketching styles that diverge from the crowd-collected templates, an explicitly acknowledged trade-off versus the authors' stated long-term goal of supporting arbitrary sketching styles. (5) Small tuning set (30 sketches, 5 grad students) for the 5-parameter multi-scale weighting scheme, separate from but methodologically similar in scale to the 10-participant main evaluation. (6) Evaluation participants are CS students without professional UI/UX training, intentionally matching the target novice-developer population, but limiting generalization to expert designers' sketching behavior.

## Summary

PSDoodle is the first tool to support fully interactive, iterative sketch-based search of a large mobile-app-screen repository (Rico, ~58k usable screens), positioned against two existing search paradigms it argues are each too slow or too coarse: traditional keyword search (which fails novice users lacking the right vocabulary) and SWIRE-style full-screen sketch retrieval (which requires completing an entire crossed-out-square-and-squiggly-line screen sketch, traditionally via pen-on-paper with fiducial-marker photo correction, before any search feedback is available, averaging 246 seconds of sketching alone). PSDoodle instead recognizes UI-element doodles *incrementally*, stroke by stroke, via a QuickDraw-architecture CNN+Bi-LSTM stroke-sequence classifier trained on the authors' own crowd-sourced DoodleUINet dataset (16 stylized UI-element classes) supplemented with 7 repurposed Google QuickDraw categories serving as placeholders for containers, arbitrary images, and defaults. Each time a doodle is completed, PSDoodle re-scores all 58k candidate screens using a custom three-level (fine-to-coarse) spatial-overlap algorithm that tolerates position/size mismatch between an abstract sketch and its real-world counterpart, weighted by how rare each UI-element type is across the corpus (IDF-style boosting), and updates the top-N result screens live within under 2 seconds end-to-end. A 10-participant study (novice CS students, no formal design training) shows PSDoodle achieves top-10 retrieval accuracy (88.2%) essentially on par with SWIRE and its most-accurate follow-up (61–90.1%), while requiring roughly a quarter of the UI elements per query (5.5 vs. ~21.1) and cutting total search time by more than half (30–259s vs. SWIRE's 246s sketching-only baseline); and critically, when the authors ran a SWIRE-style network directly on PSDoodle's own *partial* sketches, it failed to retrieve the target screen in the top-10 for every one of 26 test cases, empirically demonstrating that full-screen sketch retrieval methods do not degrade gracefully to partial/interactive queries the way PSDoodle's element-by-element approach does. The paper is transparent about specific failure modes tied to upstream Rico label-coverage gaps and to a handful of UI-element classes whose crowd-collected training doodles didn't match how real users tend to sketch them, prompting a documented post-hoc retraining round.
