# DesignRepair: Dual-Stream Design Guideline-Aware Frontend Repair with Large Language Models

- **Year:** 2025
- **Venue/Source:** 2025 IEEE/ACM 47th International Conference on Software Engineering (ICSE 2025)
- **DOI:** 10.1109/ICSE55347.2025.00109

## Metadata

- **se_area:** development (frontend UI code quality assurance and repair; touches design/maintenance as well)
- **se_task:** Automated detection and repair of frontend UI design-guideline violations (accessibility, contrast, layout, spacing, component usage) in LLM-generated and real-world (GitHub) frontend code, benchmarked against Google Material Design 3 guidelines.
- **cv_technique:** None used directly by DesignRepair itself. The system's own extraction pipeline is (1) GPT-4 (an LLM, not a vision model) prompted over raw frontend source code to extract component types, and (2) Playwright (a browser automation/testing tool) used to render the page and extract DOM-level properties (XPath, computed color values, etc.); this is structured DOM/property extraction, not image/pixel analysis. Retrieval-Augmented Generation (RAG) combined with GPT-4 is then used for repair generation. The paper's RQ1 baseline, UIS-Hunter, is a rule-based/CV method that analyzes static screenshots via image processing and OCR (e.g., detecting colored dividers, icon counts, text via OCR); this is the paper's only substantive contact with classic CV techniques, and it appears only as a comparison baseline, not as part of DesignRepair's architecture.
- **platform:** web (Vercel V0-generated frontend projects and GitHub web frontend projects, built with React, Next.js, Material-UI, TypeScript, Shadcn, Tailwind CSS)
- **rationale:** Context-driven: the goal is to check whether generated/existing frontend UI code and its rendered page conform to established design-system guidelines (Material Design 3), combining source-code-level and rendered-page-level (DOM/property) context to holistically detect and repair design violations rather than relying on visual pattern matching alone.
- **artifact_type:** full-interface (whole rendered web pages/projects are analyzed and repaired, addressing both individual components/properties and overall page-level design coherence)
- **eval_method:** Two evaluation datasets: (1) 20 Vercel V0-generated projects (669 components/property groups, 3,765 applicable guidelines, 196 violations, manually annotated by two authors with a third for disagreement resolution) and (2) 66 files from 6 popular GitHub projects (1,793 components/property groups, 115 violations). RQ1 compares DesignRepair's violation-detection recall/precision against the rule-based baseline UIS-Hunter on hard-constraint violations (127 V0 issues, 48 GitHub issues): DesignRepair achieves 92.1%/87.3% (recall/precision) on V0 vs. UIS-Hunter's 32.3%/55.4%, and 83.3%/90.9% on GitHub vs. 22.9%/47.8%. RQ2 ablates each pipeline stage (component extraction, component mapping, violation detection, component-only vs. property-only repair, soft- vs. hard-constraint repair, overall repair) against manually annotated ground truth, reporting recall/precision for each (overall repair: 89.3%/86.6% on V0, 85.2%/90.7% on GitHub). RQ3 is a user study with 26 participants (12F/14M, researchers/students/developers across Australia, China, US) rating before/after-repair UI videos on a 5-point Likert scale for visual attractiveness; results analyzed via Wilcoxon Signed-Rank test (p ≈ 6.99×10⁻⁹, mean score rising from 3.04 to 3.92, SD narrowing from 1.19 to 0.99), plus follow-up interviews explaining cases where users preferred the original design.
- **challenges:** Authors' stated limitations (Threats to Validity and Discussion): (1) manual annotation of ground-truth design issues is imperfect and may bias the identified violation distribution, especially for soft constraints, which annotators found harder to recognize consistently; (2) evaluation was conducted on a relatively small, non-exhaustive sample (20 V0 projects, 66 GitHub files) and the authors explicitly call for testing on a larger dataset; (3) DesignRepair's LLM-based repair becomes more conservative on complex GitHub pages, avoiding aggressive fixes to prevent introducing new issues, which lowers recall on such pages; (4) soft-constraint repair performs worse than hard-constraint repair, and about 20% of user-study participants preferred the un-repaired version, citing subjectivity of some soft-constraint fixes (e.g., color/theme changes that don't affect usability); (5) the approach still relies on GPT-4 prompting rather than an integrated, trained vision-language model, and (inferred from experimental setup) since component/property extraction depends entirely on code and DOM output rather than rendered pixels, the method cannot catch purely visual rendering glitches that don't manifest in DOM/CSS properties (e.g., font-rendering artifacts, browser-specific rasterization issues), a gap the CV-based baseline UIS-Hunter was partly designed for, even though it performed worse overall.

## Scope note

DesignRepair's own pipeline does not employ a computer-vision model or pixel/image-based analysis. Component and property extraction is done via GPT-4 reasoning over source code plus Playwright-based DOM/property extraction (XPath, computed CSS/color values, etc.), a code/DOM-level, not a visual/pixel-level, analysis. The only CV-flavored element in the paper is indirect: the RQ1 baseline it compares against, UIS-Hunter (Yang et al. 2021), uses image-processing/OCR-based visual analysis of screenshots, and the paper's Threats-to-Validity / limitations discussion notes UIS-Hunter's OCR-driven false positives and its inability to "evaluate active state components" beyond "static screenshots through image processing." Because the paper's own contribution is LLM+DOM-based rather than CV-based, its fit for a CV-in-SE literature review is questionable; it is included here primarily as a contrast/baseline-adjacent data point rather than as a CV technique paper.

## Summary

DesignRepair addresses the problem that LLM-driven frontend-generation tools (e.g., Vercel's V0) produce UIs that often violate established design guidelines (contrast, accessibility, layout consistency), and that existing repair tools are either narrowly scoped, rule-based, or unable to fix issues automatically. The authors first restructure Google's Material Design 3 guidelines into two knowledge bases: a low-level Component Knowledge Base (24 component types, 228 hard "do/don't" constraints, 399 soft recommended constraints) and a high-level System Design Knowledge Base (12 design aspects, 7 properties, 15 mapping relations), distinguishing mandatory ("hard") from optional ("soft") guidelines. Given a page's frontend code and its Playwright-rendered DOM, DesignRepair uses GPT-4 to extract used components and Playwright to extract property groups (spacing, color, labels, etc.), retrieves matching guidelines via LLM-based (rather than rule-based) component-name mapping, and then applies a Retrieval-Augmented Generation repair strategy that follows a "divide and conquer" pattern: individual components/properties are repaired first (with distinct prompting for hard vs. soft constraints), then merged into a holistic final repair. Evaluated on 20 Vercel V0 projects and 66 GitHub files, DesignRepair substantially outperforms the rule-based UIS-Hunter baseline in violation detection and achieves 85–92% recall / 86–91% precision for overall repair; a 26-participant user study found statistically significant improvement in perceived visual attractiveness after repair (Wilcoxon p≈6.99×10⁻⁹), though a notable minority of users preferred original designs for some subjective soft-constraint changes. A main architectural detail is the explicit separation of "hard" vs. "soft" design constraints throughout the whole pipeline, which lets the LLM apply different repair strictness depending on guideline type.
