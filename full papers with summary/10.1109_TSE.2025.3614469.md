# Seeing is Believing: Vision-Driven Non-Crash Functional Bug Detection for Mobile Apps

- **Year:** 2025
- **Venue/Source:** IEEE Transactions on Software Engineering (TSE), Vol. 51, No. 12, December 2025 (published online 26 September 2025)
- **DOI:** 10.1109/TSE.2025.3614469

## Metadata

- **se_area:** testing
- **se_task:** Automated GUI testing of Android apps for non-crash functional bug detection (e.g., visual/logical inconsistencies, missing feedback, data operation failures) that lack explicit crash signals, formulated as an interactive multimodal question-answering task performed during automated exploration.
- **cv_technique:** GPT-4 Vision (gpt-4-vision-preview) as the multimodal LLM (MLLM) backbone; a custom screenshot annotation method that draws color-coded bounding boxes around actionable widgets (extracted via UIAutomator view-hierarchy "bounds" fields) and numbers them for the MLLM to reference; a text-image alignment method combining visual context with extracted textual widget/page/app properties; image-stitching of multiple screenshots into a single composite image to manage token limits; Word2Vec sentence embeddings for retrieval-based (cosine-similarity) selection of in-context bug examples.
- **platform:** mobile (Android primary; small-scale cross-platform extension evaluated on iOS and HarmonyOS)
- **rationale:** Primarily context-driven: the approach relies on the MLLM's visual and semantic understanding of GUI screenshots (combined with aligned textual widget/page information) to infer functional intent, expected behavior, and test oracles across sequences of GUI page transitions, rather than relying on explicit rules, crash signals, or large labeled training sets used by prior view-hierarchy-based or supervised deep-learning bug detectors.
- **artifact_type:** temporal (sequences of annotated GUI screenshots across page transitions/exploration history) combined with full-interface (whole-screen annotated screenshots per page)
- **eval_method:** Three datasets totaling 590 non-crash bugs: (1) baseline dataset from Odin/RegDroid prior work (131 bugs, 5 bug categories), (2) a newly collected GitHub/Google Play dataset (387 bugs across 83 apps, 9 categories, apps updated after June 2024), and (3) an injection dataset (72 bugs across 33 apps) created via code-based bug injection to avoid MLLM data leakage. Compared against 12 baselines: 4 display-issue detectors (OwlEyes, NightHawk, DVermin, DiffDroid) each paired with 5 automated GUI exploration tools (Monkey, APE, Fastbot, Humanoid, GPTDroid); 6 logical-bug detectors (iFixdataloss, SetDroid, Genie, Odin, Android Lint, LiveDroid); and 2 MLLM-based baselines (AppAgent, GPT-4). Metrics: activity coverage, code coverage, precision, recall, F1-score, averaged over 3 runs per app (50-minute time budget each). Ablation study removing 8 sub-modules (screenshot annotation, GUI information, testing history, optimization feedback, image legend, test recording, bug examples, function-aware CoT). Usefulness/field study (RQ3): deployed on 187 real Google Play apps (versions released after GPT-4's training cutoff), detecting 102 bugs (7 false positives), 43 previously unknown, submitted to developers (31 fixed, 12 confirmed, 0 rejected), a form of human/developer validation. Small-scale cross-platform generalization test on 10 iOS and 10 HarmonyOS apps.
- **challenges:** Authors explicitly report: (1) dynamic/asynchronous UI elements (widgets updating asynchronously, conditional pop-ups, state-dependent content) disrupt the MLLM's reasoning and cause mismatches between visual cues and widget IDs; (2) apps with minimal textual labels force reliance on visual features alone, which lack sufficient precision for reasoning; (3) threat to validity: although evaluation apps post-date GPT-4's training cutoff, underlying functionality may have existed in earlier (pre-cutoff) versions, creating possible indirect data leakage, though authors argue impact is limited since target bugs are subtle GUI logic/layout inconsistencies; (4) token/cost constraints of the MLLM API required screenshot compression, history summarization, and prompt merging (Explorer+Monitor) as engineering workarounds; (5) reliance on a single commercial MLLM (GPT-4V) not systematically compared against alternative MLLMs (inferred from experimental setup); (6) cross-platform (iOS/HarmonyOS) evaluation was only small-scale (10 apps each) and described by authors as preliminary, with more thorough experiments left for future work.

## Summary

This paper presents VisionDroid, a vision-driven, multi-agent automated GUI testing framework for detecting non-crash functional bugs in Android apps, bugs that alter visual/logical correctness without triggering crashes and thus evade conventional crash-oracle-based testing. The system comprises three collaborating agents built on a multimodal LLM (GPT-4 Vision): an Explorer Agent that navigates the app using annotated screenshots (color-coded bounding boxes aligned with extracted view-hierarchy text) to decide actions; a Monitor Agent that tracks exploration progress at the functionality level (via textual and image history views) and decides when to trigger bug detection; and a Detector Agent that uses a functionality-driven chain-of-thought prompting strategy plus retrieved in-context bug examples (selected via Word2Vec similarity) to infer expected behavior and flag discrepancies. The main contribution is reframing non-crash bug detection as an interactive multimodal question-answering problem solved through visual-textual alignment, functionality-aware exploration, and oracle inference, without requiring manual rules or large labeled training datasets. Evaluated on 590 bugs across three datasets against 12 baselines, VisionDroid improved recall by 108%-147% and precision by 14%-112% over the best baseline, and in a live field study on 187 Google Play apps it discovered 43 previously unknown bugs, 31 of which were subsequently fixed by developers. A notable detail: ablations show removing the in-context bug examples causes the largest performance drop (up to 92% recall reduction), and a small-scale iOS/HarmonyOS extension suggests the approach generalizes beyond Android.
