# Efficiency Matters: Speeding Up Automated Testing with GUI Rendering Inference

- **Year:** 2023
- **Venue/Source:** ICSE 2023 (45th International Conference on Software Engineering)
- **DOI:** 10.1109/ICSE48619.2023.00084

## Metadata

- **se_area:** testing
- **se_task:** automated GUI testing efficiency; adaptive event scheduling / inter-event throttle optimization for Android UI testing tools
- **cv_technique:** lightweight CNN (MobileNetV2-based, binary classifier for fully vs. partially rendered GUI); Y-Diff (YUV luminance difference) + SSIM used for automatic dataset construction from transiting screencasts
- **platform:** mobile (Android)
- **rationale:** efficiency (the primary motivation, reducing idle waiting time between test events); robustness (avoid executing events on partially rendered/out-of-sync GUIs, which cause missed taps and false crash reports)
- **artifact_type:** full-interface (whole-screen binary classification: fully rendered vs. partially rendered GUI state, not individual element detection)
- **eval_method:** precision/recall/F1/inference time vs. 11 state-of-the-art baselines (SIFT/SURF/ORB + SVM/KNN/RF, and a 3-layer CNN) on 20,125 screenshots from 1,877 apps; crash-bug reproduction study (18 crash bugs across 12 defective apps) comparing fixed throttles, Themis, and ablations; real-world integration with Droidbot on 32 apps measuring activity coverage, GUI count, and crash count
- **challenges:** the 0.99 frame-similarity threshold and 5-frame steady-state threshold used to auto-label the dataset were set empirically via small-scale pilot studies, not derived principledly; the model still misclassifies GUIs with tiny/inconspicuous rendering cues (e.g., thin progress bars) that are hard to see even for human annotators; screens with dynamic assets (video, gifs) are automatically mislabeled as "partially rendered" during dataset construction even when they appear fully rendered in a static frame; generalization beyond Android was only lightly validated (a 50-screenshot small-scale test on iOS/Web, achieving 92%/86% F1); the maximum waiting threshold (1000ms) is another empirically tuned hyperparameter.

## Summary

This ICSE 2023 paper addresses an overlooked efficiency bottleneck in automated Android GUI testing: the fixed "throttle" (wait time) that testing tools insert between events. A pilot study across three widely-used tools (Droidbot, Monkey, Ape) shows that with a short 200ms throttle, 17–32% of test events fire on partially rendered GUIs (categorized into transiting, explicit loading, and implicit loading states), harming effectiveness, while overly long throttles (1000ms) cut executed events by over 50%, harming efficiency. The authors propose AdaT, a lightweight image-based approach that treats throttle-time prediction as a binary run-time image classification task (fully vs. partially rendered), trained on a large auto-collected dataset (66k/46k images) built by applying Y-Diff/SSIM frame-similarity analysis to the Rico screencast dataset. A small MobileNetV2-derived CNN performs the classification (43ms/inference, 99.8% accuracy), and a socket-based streaming framework (built on OpenSTF/Minicap) synchronizes real-time screenshot capture with event scheduling so the testing tool waits only until the GUI is confirmed fully rendered, up to a 1000ms safety cap. Integrated into Droidbot, AdaT-enhanced testing achieves 6.96% higher activity coverage and 13.24% more executed events than the vanilla tool at equal runtime, and is roughly 2x faster than the benchmark method Themis at reproducing known crash bugs while matching its bug-triggering completeness. A notable detail: the approach is purely screenshot-based (no reliance on view-hierarchy/XML), making it framework-agnostic and easy to deploy across different testing tools and, potentially, platforms.
