# Divide-and-Conquer: Generating UI Code from Screenshots

- **Year:** 2025
- **Venue/Source:** Proceedings of the ACM on Software Engineering (Proc. ACM Softw. Eng.), Vol. 2, Issue FSE, Article FSE094 (FSE 2025)
- **DOI:** 10.1145/3729364

## Metadata

- **se_area:** development (automated front-end/UI implementation, i.e., design-to-code)
- **se_task:** automatically generating functional HTML+CSS UI code directly from a website screenshot/design image (the "design-to-code" task), aiming to reduce the manual effort of translating pixel-based visual designs into working front-end implementations
- **cv_technique:** multimodal large language models (MLLMs: GPT-4o, Gemini-1.5-Flash, Gemini-2.0-Flash, Claude-3-Sonnet) used as vision-language code generators; a custom classical-image-processing "separation line detection" algorithm (grayscale conversion, row-wise pixel-brightness variance analysis with a sliding window, dual-threshold blank-space/border detection) used to recursively segment a screenshot into hierarchical visual regions prior to MLLM-based code generation; CLIP (CLIP-ViT-B/32) embeddings used to compute image/visual similarity between original and generated webpage renderings; Intersection-over-Union (IoU) used both as an evaluation metric for the separation algorithm and (via the Jonker-Volgenant assignment algorithm on detected visual element blocks, from prior work by Si et al.) for fine-grained block-matching, text, position, and color similarity metrics; compared against a CNN+LSTM baseline (Pix2Code)
- **platform:** web
- **rationale:** robustness (directly motivated by a documented failure mode of applying MLLMs to whole-screenshot code generation, element omission, distortion, and misarrangement, that the authors show is substantially mitigated by decomposing the image into smaller, focused segments before generation) and ease of use (aims to democratize front-end web development for non-experts and reduce the significant manual, error-prone effort of hand-translating visual designs into code, particularly for large/complex real-world webpages)
- **artifact_type:** full-interface decomposed into a hierarchy of localized sub-regions (the core "divide-and-conquer" design recursively splits a full-screenshot artifact into progressively smaller rectangular visual segments, generates code per segment, and reassembles bottom-up into the full-interface output)
- **eval_method:** constructs and releases a dataset of 348 real-world top-ranked websites (Tranco-listed) plus a 111-webpage sampled test set, and separately incorporates an existing 80-webpage "Design2Code-Hard" dataset of especially complex pages; a "motivating study" using 2 human annotators manually comparing GPT-4o-generated vs. original webpage screenshots via Selenium-extracted bounding boxes across 1,699 HTML elements, categorizing errors into omission/distortion/misarrangement (omission alone: 85.34% of errors; only 40/1,699 elements correctly reproduced) and verifying that cropping to isolate a failing element measurably improves both qualitative regeneration success and CLIP similarity (73.7% → 76.0%); a hyperparameter sensitivity analysis (RQ1) of the separation algorithm using IoU against ground-truth DOM-derived bounding boxes; comparison (RQ2) of DCGen against direct prompting, Chain-of-Thought, self-refine prompting, and Pix2Code using both high-level metrics (CLIP score, Levenshtein-based code similarity) and fine-grained element-matching metrics (Block-Match, Text similarity, Position similarity, Color similarity), where DCGen achieves the best score on every metric (e.g., CLIP 85.62% vs. best baseline 83.96%; Code 15.34% vs. 13.65%); robustness testing (RQ3) on the Design2Code-Hard dataset and across five image-size buckets, showing DCGen's advantage grows for larger/more complex screenshots; generalizability testing (RQ4) across four different backbone MLLMs, all showing improvement with DCGen; and two human evaluations (RQ5): a 5-annotator pairwise preference study (DCGen wins 62% vs. GPT-4o direct prompting, loses only 8%) and a controlled usefulness study with 4 participants (2 using a DCGen demo tool vs. 2 using any preferred tool including plain GPT-4o) measuring completion time (8 vs. 14.5 minutes) and blinded 5-point similarity ratings (3.75 vs. 2.25) with inter-judge Pearson correlation 0.71.
- **challenges:** element misarrangement (incorrect relative positioning/ordering of elements) is only partially addressed by the divide-and-conquer strategy; a documented failure case shows the per-segment ("leaf-solver") MLLM correctly generating a horizontally arranged layout, but the higher-level "assembly" MLLM subsequently and incorrectly converting it to a vertical layout, which the authors attribute to MLLMs' well-documented visual limitations in recognizing simple positional/spatial patterns (though the tool's segment-level regeneration feature allows this to be manually corrected); the manually-set thresholds and heuristics in the classical separation-line-detection algorithm (var_thresh, diff_thresh, diff_portion, window_size, depth) required extensive empirical tuning and represent a potential robustness limitation for atypical page layouts, and the IoU precision of the segmentation itself is only moderate (roughly 0.4-0.6) and explicitly framed as a secondary/reference metric rather than a target to fully optimize, since the segmentation's real goal is aiding MLLM focus, not exact element-boundary recovery; the agent-based assembly variant costs roughly 3x the token/compute cost of direct prompting, a stated efficiency trade-off (mitigated somewhat by a rule-based, CSS-grid alternative that lowers cost to about 2x); evaluation used website screenshots as a proxy for true design files since actual design assets (e.g., Photoshop/Figma documents) were unavailable at scale; only smaller open MLLMs were found unable to perform the more complex assembly reasoning step, limiting backbone generalizability to sufficiently capable models; the human usefulness study was very small (four participants), limiting statistical generalizability despite the promising time and similarity gains.

## Summary

This paper tackles automated "design-to-code" generation, converting a website's visual screenshot into functional HTML/CSS, which remains largely unsolved for real-world, complex websites despite growing interest in leveraging AI for front-end development. The authors first run a diagnostic motivating study showing that directly prompting a strong multimodal LLM (GPT-4o) to generate code from a full webpage screenshot produces poor results (only 40 of 1,699 manually-annotated HTML elements correctly reproduced), with failures falling into three categories: element omission (by far the most common, 85%), distortion, and misarrangement. Critically, they show that when a problematic element is isolated by cropping the screenshot down to just that region, the same MLLM reliably reproduces it correctly, indicating the model is not fundamentally incapable, but rather overwhelmed by scene complexity. This finding motivates DCGen, a divide-and-conquer framework that recursively segments a full webpage screenshot into a hierarchy of smaller, semantically coherent visual regions using a purpose-built classical image-processing algorithm (detecting explicit and implicit horizontal/vertical "separation lines" via row-wise pixel-brightness variance and a sliding-window dual-threshold test, since standard object-vs-background image segmentation techniques are unsuited to webpage layouts), generates code independently for each leaf segment via an MLLM, and then progressively reassembles the code bottom-up (via either an MLLM-based or a rule-based CSS-grid-based assembly strategy) to reconstruct the full page. Evaluated on a newly curated dataset of 348 real-world websites and a harder 80-page benchmark, DCGen consistently outperforms direct prompting, Chain-of-Thought, self-refine prompting, and a prior CNN+LSTM baseline (Pix2Code) across both holistic metrics (CLIP-based visual similarity, Levenshtein code similarity) and fine-grained element-matching metrics (block match, text, position, color), with its advantage growing specifically for larger and more complex input images, directly validating the core "smaller-and-more-focused-helps" hypothesis from the motivating study. A particularly notable aspect of the evaluation is its dual grounding in both automated metrics and real developer behavior: a blinded pairwise human preference study confirms the automated rankings, and a controlled usefulness study shows developers using a DCGen-based demo tool complete UI implementation tasks roughly 1.8x faster with substantially higher blinded similarity ratings than developers using an unaided MLLM, while the paper is candid that its own divide-and-conquer strategy does not fully solve element-misarrangement errors, tracing this specific residual failure mode to a documented, more fundamental visual-reasoning limitation of current MLLMs rather than to the segmentation approach itself.
