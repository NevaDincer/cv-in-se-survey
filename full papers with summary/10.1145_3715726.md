# DeclarUI: Bridging Design and Development with Automated Declarative UI Code Generation

- **Year:** 2025
- **Venue/Source:** Proc. ACM Softw. Eng. (FSE 2025), Vol. 2, No. FSE, Article FSE011
- **DOI:** 10.1145/3715726

## Metadata

- **se_area:** development (design-to-code generation), with a secondary testing component (automated UTG extraction via DroidBot for evaluation)
- **se_task:** generating functional, multi-page declarative UI code (React Native, with generalization to Flutter and ArkUI) directly from static UI designs (Figma mockups and app screenshots), including both visual layout and inter-page navigation logic
- **cv_technique:** Grounding DINO (zero-shot open-vocabulary object detection) to produce bounding boxes for UI components, followed by Segment Anything Model (SAM), prompted with those boxes, for precise instance segmentation of each component; the segmented component crops are then passed to an MLLM (Claude 3.5 Sonnet or GPT-4o) for component-type classification and functional description. A separate MLLM vision pass over full-screen images also constructs the Page Transition Graph (PTG) that encodes navigation logic between pages.
- **platform:** mobile (Android apps built with React Native, Flutter, and ArkUI)
- **rationale:** context-driven (component detection and segmentation give the MLLM explicit, localized visual context about individual UI elements instead of forcing it to parse an entire screenshot unaided, which the paper shows leads to missed components like a bottom navigation bar); robustness (Grounding DINO's zero-shot detection avoids the need for UI-specific training data and generalizes across mockups and real screenshots from 10 app categories, and the DINO+SAM pipeline is reported at 92.3% component recognition accuracy on a sampled check)
- **artifact_type:** full-interface (complete UI screenshots and Figma mockups analyzed as whole images for PTG construction) combined with localized (individual segmented component crops extracted via detection and segmentation, analyzed separately for type and function)
- **eval_method:** Curated dataset of 50 UI design sets (25 Figma mockups, 25 Google Play app screenshots) across 10 app categories, 5 pages each (250 pages total), with ground-truth PTGs built by two authors independently and cross-validated to 100% agreement. Metrics: CLIP score and SSIM for visual fidelity, PTG Coverage Rate (PCR, comparing ground-truth PTG edges against a UTG extracted from the generated app via DroidBot), Compilation Success Rate (CSR) and Average Compilation Iteration Count (ACIC). Compared against GPT-4o and Claude 3.5 Sonnet baselines (unprocessed screenshots, no CV preprocessing) on React Native, with generalization tests on Flutter and ArkUI. Results: 96.8% PCR (vs. 43.3% baseline, a 123% relative gain), 98% CSR (vs. 74% baseline), SSIM 0.68 vs. 0.58 (up to 55% visual similarity improvement is cited across framework variants), CLIP 0.88 vs. 0.65. A user study with five professional React Native developers (avg. 2+ years experience, $50 compensation, 12 apps each) rated DeclarUI-generated code significantly higher on code availability (4.97 vs. 4.15), modification time (4.03 vs. 2.45), readability (4.62 vs. 3.75), and maintainability (4.55 vs. 3.37), all with p < 0.05 via Mann-Whitney U test. Average Manual Correction Time for compilation-failed apps was 48s (React Native, Claude 3.5) versus 62s (Flutter) and 183s (ArkUI).
- **challenges:** Authors report ArkUI performance is notably weaker than React Native and Flutter (86% CSR, ACIC 1.62, AMCT 183s) because the MLLM has limited training exposure to this newer, less mainstream framework; a preliminary retrieval-augmented generation fix using a knowledge graph gave only modest gains due to time constraints on building a more sophisticated KG. CLIP and SSIM scores are noted as imperfect proxies for human-perceived UI similarity. The DINO+SAM component recognition pipeline is only checked at 92.3% accuracy on a small sample of 10 pages, and the authors acknowledge alternative CV approaches might perform differently. The 50-design dataset size is capped by MLLM token cost constraints, limiting coverage of the full variability of mobile UI types. One app failed to compile even after three refinement iterations, due to the MLLM referencing non-existent file resources reflecting gaps in its framework-specific knowledge.

## Summary

DeclarUI targets the gap between MLLM-based UI code generation and the practical demands of declarative mobile frameworks, where direct application of models like GPT-4o and Claude 3.5 to raw screenshots produces missing components, broken navigation, inconsistent behavior across pages, and code that fails to compile. The approach combines computer vision preprocessing with MLLM reasoning in a multi-stage pipeline. Grounding DINO detects UI components in a screenshot and produces bounding boxes, which are fed as prompts to the Segment Anything Model for precise instance segmentation; the segmented crops are then classified by type and inferred function using an MLLM. In parallel, an MLLM analyzes the full set of screens to build a Page Transition Graph, a structured node-and-edge representation of pages and their navigation triggers. Both outputs feed a synthesized prompt (PTG, component analysis, full screenshot) for initial code generation, followed by iterative refinement that checks navigation completeness against the PTG and fixes compiler errors using structured feedback, up to three iterations per stage.

On a 50-app dataset spanning Figma mockups and Google Play screenshots, DeclarUI substantially outperformed unmodified GPT-4o and Claude 3.5 baselines on React Native: PTG coverage rose from 43.3% to 96.8%, SSIM from 0.58 to 0.68, and compilation success from 74% to 98%. The approach generalized to Flutter and ArkUI, with ArkUI trailing due to the MLLM's weaker prior knowledge of that framework. A user study with five professional React Native developers found DeclarUI's code rated significantly higher on availability, modification time, readability, and maintainability than the baseline, all statistically significant.
