# Interpreting Cloud Computer Vision Pain-Points: A Mining Study of Stack Overflow

- **Year:** 2020
- **Venue/Source:** ICSE '20 (42nd International Conference on Software Engineering)
- **DOI:** 10.1145/3377811.3380404

## Metadata

- **se_area:** Maintenance / Development (broadly: API usage and developer support). The paper studies developer questions/issues when integrating third-party CV services into software, which spans development-time API integration and ongoing maintenance/debugging.
- **se_task:** Not applicable in the "CV-for-SE-task" sense. The closest framing: empirical characterization of developer pain points / API usability issues when integrating cloud-based computer vision services into applications (an SE-process/documentation study, not a CV-technique application).
- **cv_technique:** None applied by the authors. The study analyzes developer discourse *about* four commercial CV cloud APIs (Google Cloud Vision, AWS Rekognition, Azure Computer Vision, IBM Watson Visual Recognition); these are the object of study, not techniques used in the paper's own methodology (which is manual/qualitative classification of Stack Overflow posts).
- **platform:** General (cloud/web-service APIs consumed by developers across mobile, web, and desktop applications, not tied to one platform)
- **rationale:** Not applicable (no CV technique is applied by the authors for an SE task). If reframed as a motivational finding for the broader survey, the paper's core insight is that abstracting CV behind conventional-looking REST APIs hides its probabilistic/data-dependent nature from developers, which could motivate "ease of use" as a driver for CV adoption in SE tooling while also flagging risks of shallow developer understanding.
- **artifact_type:** Not applicable (no artifact produced from image/video input; the "artifacts" studied are textual Stack Overflow posts).
- **eval_method:** Manual mining and classification of 1,825 classifications (1,425 unique Stack Overflow posts, Nov 2012–Jun 2019) using two existing SO taxonomies: Aghajani et al.'s documentation-specific taxonomy (Taxonomy A: Information Content-What/How, Process-Related, Tool-Related) and Beyer et al.'s generalized taxonomy (Taxonomy B: API Usage, Discrepancy, Errors, Review, Conceptual, API Change, Learning). Inter-rater reliability assessed via Light's Kappa (slight agreement, κ=0.148, for Taxonomy A; fair agreement, κ=0.295, for Taxonomy B). Distribution differences from prior mobile/web API studies assessed via χ² tests and Cramér's ϕc effect size. Additionally applied Bloom's Taxonomy and the SOLO taxonomy (pedagogical frameworks) to a 50-post sample to interpret findings through a learning-gap lens.
- **challenges:** This is itself a challenges/pain-points study rather than a technique paper reporting its own limitations in applying CV. Main reported findings framed as "challenges for developers using CV services": (1) majority of issues are simple Errors (32.05%) and API Usage (22.29%) questions reflecting shallow/primitive understanding of underlying ML concepts, rather than deeper conceptual or review-level questions; (2) developers frequently confuse basic CV vocabulary (e.g., detection vs. localization vs. recognition); (3) lack of awareness of preprocessing needs (e.g., OCR text-ordering assumptions) and service limitations (e.g., inconsistent feature coverage across providers, non-deterministic/versioned API behavior changing without notice); (4) documentation Completeness (47.87%) and Correctness (22.87%) are the most common complaint types, indicating docs do not adequately convey the "technical domain" (training data assumptions, score/confidence interpretation, model characteristics) behind CV cloud services.

## Summary

This ICSE 2020 paper is an empirical mining study, not a CV-technique paper, that investigates the difficulties application developers face when integrating commercial cloud-based computer vision APIs (Google Cloud Vision, AWS Rekognition, Azure Computer Vision, IBM Watson Visual Recognition) into their software. The authors' central concern is that these "intelligent services" are packaged behind conventional-looking RESTful API interfaces that obscure their underlying probabilistic, data-dependent, and non-deterministic nature, leading developers to reason about them the same way they would reason about a deterministic library or cloud storage service. To study this, the authors extracted and manually classified 1,425 Stack Overflow questions (yielding 1,825 total classifications after reliability sampling) spanning November 2012 to June 2019, applying two existing, previously-validated SO issue taxonomies from mobile/web API research: Aghajani et al.'s documentation-specific taxonomy and Beyer et al.'s more general causal taxonomy. They found that, unlike more mature domains such as mobile or web development (where API Usage questions dominate), CV-service developers most often ask basic Error-related (32.05%) and API Usage (22.29%) questions, with comparatively few deeper Review or Conceptual questions, and statistically significant distributional differences (χ² tests, medium-to-large Cramér's ϕc effect sizes) from prior mobile/web taxonomy studies. To interpret these findings pedagogically, the authors additionally map a sample of posts onto Bloom's Taxonomy and the SOLO taxonomy, finding the bulk of questions cluster at the lowest cognitive/structural levels (Knowledge/Pre-structural and Comprehension/Uni-structural), suggesting many issues are resolvable through better documentation (particularly completeness) while a substantial minority (34.74% by Bloom's, 11.84% by SOLO) require more structured developer education rather than documentation fixes alone. The paper concludes with implications for researchers, educators, software engineers, and CV service providers, arguing for clearer "technical domain" documentation, better error/response-object explanations, and possibly an interactive tutorial-style approach akin to Git-learning tools. While methodologically rigorous, this paper's contribution is about developer experience with CV-as-a-service APIs rather than a CV technique applied to solve a software engineering task, making it a background/motivation reference rather than a core synthesis-matrix entry for a survey on CV applications within SE.
