# Mobile Bug Report Reproduction via Global Search on the App UI Model

> **SCOPE WARNING**: LIKELY OUT OF SCOPE]**: This paper does not use computer vision at all. Widget matching between bug-report steps and UI events (the "match similarity score") is computed purely from **textual** attributes of widgets: label, content description, and resource-ID string, compared via word-embedding cosine similarity (NLP), not from any visual/pixel-based analysis of screenshots. The approach is built on a Markov model over the app's UI Transition Graph (UTG) plus dynamic programming, with no image processing, OCR, or visual feature extraction anywhere in the pipeline. - **se_task:** Automated reproduction of mobile app bug reports (matching textual reproduction steps to sequences of UI events, including handling missing/inaccurate steps)
- **cv_technique:** None. No screenshot/image analysis is performed.
- **platform:** Mobile (Android)
- **rationale:** N/A (not CV-driven); if reframed generally, the motivating rationale is robustness of reproduction under missing/inaccurate bug-report steps, via global (non-greedy) search
- **artifact_type:** N/A (no visual artifact is analyzed; matching is against UTG nodes/widget metadata, not screenshots)
- **eval_method:** Empirical evaluation on 72 real-world Android bug reports from 5 open-source datasets; comparison against 3 state-of-the-art baselines (ReproBot, ReCDroid, Yakusu) and 2 ablation baselines (PRM-Enumeration, Euler-style n-step lookahead); metrics: match accuracy (RQ1), reproduction rate overall and split by presence/count of missing steps (RQ2, RQ4), running time (RQ3), and contribution of sub-scores via ablation variants Roam-Sim/Roam-Dist (RQ5)
- **challenges:** Reported/observed limitations include: (1) reproduction fails when the approach cannot compute a similarity score because developers omitted widget textual attributes (label/desc/resource-ID) in the UI; (2) inability to handle "amalgamated" steps where one bug-report step maps to multiple UI interactions (one-to-many mapping), since the approach assumes a one-to-one step-to-event mapping; (3) missing steps that are not detectable via UTG discontinuity (e.g., steps that require configuration changes rather than new UI states) can be missed even by this approach; (4) global search over a large UTG is computationally more expensive than greedy search absent the dynamic-programming optimization, though amortizable across bug reports for the same app since the UTG is built once.

## Summary

This paper (tool: Roam) targets automated reproduction of mobile bug reports, a task where existing techniques (ReCDroid, Yakusu, ReproBot) struggle when reproduction steps are missing or inaccurately described, because they rely on greedy or reinforcement-learning-guided dynamic search that can get trapped matching the wrong UI event early on. The main idea is to reformulate the problem as global search over a Probabilistic Reproduction Model (PRM), a Markov model whose states are (step, UI-event) pairs built from the app's pre-existing UI Transition Graph (UTG), and whose transition probabilities combine (a) textual similarity between a bug-report step's target description and a UI widget's label/content-description/resource-ID, and (b) inverse shortest-path distance between candidate events in the UTG. A dynamic-programming algorithm finds the top-k globally best-matching event sequences, after which the UTG is traversed again to bridge gaps caused by steps omitted before, between, or after the provided steps. Evaluated on 72 real-world bug reports, Roam achieves 94% overall reproduction rate (93% on the 64% of reports with missing steps), and 93% match accuracy identifying correct UI events, outperforming ReproBot, ReCDroid, and Yakusu by wide margins, especially as the number of missing steps increases (Roam still reproduces 50% of reports with ≥5 missing steps, versus 0% for all baselines). Despite the strong SE-testing/maintenance contribution, the technique is explicitly text/graph-based rather than vision-based, which is the reason for the scope flag above.
