# Automated Fixing of Web UI Tests via Iterative Element Matching

- **Year:** 2023
- **Venue/Source:** 2023 38th IEEE/ACM International Conference on Automated Software Engineering (ASE)
- **DOI:** 10.1109/ASE56229.2023.00048

## Metadata

- **se_area:** Maintenance (regression test maintenance/repair)
- **se_task:** Automated repair of broken web UI (Selenium) test cases via UI element matching between pre- and post-update versions of a web application
- **cv_technique:** None used by the paper's own approach (UITESTFIX), which relies on DOM/attribute/structural similarity metrics (id similarity, TF-IDF property similarity, Levenshtein text similarity, path similarity, region similarity) refined iteratively. CV-based visual matching appears only in compared baselines: VISTA (visual/image-based element matching) and WEBEVO (combined text + image similarity, using a fast perceptual hash, aHash).
- **platform:** Web
- **rationale:** Robustness (higher element-matching accuracy, 84.9% vs. best prior tool's 68.8%, and higher test-repair rate, 68% vs. 44%, especially on complex industrial applications with branching control flow and Page Object patterns); context-driven (uses structural/relational information between DOM elements rather than relying solely on potentially volatile attributes or appearance).
- **artifact_type:** Localized (individual DOM/UI element locators are matched and repaired, rather than whole-screen or temporal sequences).
- **eval_method:** Empirical evaluation on an extended WebEvo dataset (44 web pages, 22 apps, 2,522 labeled changed elements) plus two industrial Huawei applications (FabricInsight, CampusInsight); measures element-matching accuracy and matching time (RQ1/RQ2) and end-to-end test-repair rate (RQ3) against four baselines (WATER, VISTA, WEBEVO, SFTM); manual verification of repairs by two authors; failure-mode analysis via manual categorization of the 53 unrepaired test cases.
- **challenges:** Authors self-report six categories of residual repair failures: Add Action, Delete Action, Modify Assert, Branch Statement, Propagated Breakages, and Incorrect Match (only 7/53, i.e., 13.21%, are attributable to matching errors, the rest require repair strategies beyond locator relocation). Additional constraints: the industrial dataset could not be open-sourced due to Huawei's policy; VISTA-based matching struggles when attributes/visual appearance change drastically even if structure is preserved; the model-based baseline [4] was excluded because its released code failed to compile.

## Scope note

, review before including in the synthesis matrix.** UITESTFIX, the technique this paper proposes and evaluates, is explicitly not computer-vision-based: it matches UI elements using id/attribute similarity, TF-IDF-based property similarity, Levenshtein text similarity, and two novel structural similarity metrics (path similarity and region similarity) computed over the DOM tree, refined through iterative re-matching. Visual/image-based matching is discussed only as prior work and as one of four baseline techniques compared against (VISTA uses visual information; WEBEVO combines text and image similarity). ## Summary

UITESTFIX repairs broken web UI test cases caused by application evolution, tackling the core sub-problem of matching UI elements between an old and a new version of a web page so that outdated locators in Selenium tests can be corrected. The authors argue existing techniques, based on DOM attributes (WATER), visual appearance (VISTA), or a combination of the two (WEBEVO), get low matching accuracy or fail on complex, real-world industrial test suites that use control-flow branches, the Page Object pattern, or custom API wrappers beyond plain Selenium calls. UITESTFIX's main novelty is an iterative matching algorithm built on two structural similarity metrics, path similarity (how close two elements' nearest already-matched ancestors are) and region similarity (how many of two candidate parent elements' child leaf nodes are already matched), recomputed across multiple rounds so high-confidence matches, like unique ids or distinctive text, progressively bootstrap the matching of harder, more ambiguous elements. The pipeline first simplifies the DOM by filtering invisible elements and merging single-child wrappers, computes an initial similarity from TF-IDF properties and Levenshtein text, then runs up to five rounds of structural refinement before greedily selecting one-to-one matches above a threshold. Evaluated on an expanded open-source dataset and two large industrial Huawei applications, UITESTFIX beat four state-of-the-art baselines on both element-matching accuracy (84.9% versus 68.8% for the next-best tool, SFTM) and test-repair rate (68% versus 44% for VISTA), running in under a second per page. The authors also release a relabeled, augmented open-source matching dataset (1,620 labeled elements, extending WebEvo), since the industrial dataset itself couldn't be shared due to company policy.
