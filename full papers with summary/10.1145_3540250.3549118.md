# AccessiText: Automated Detection of Text Accessibility Issues in Android Apps

- **Year:** 2022
- **Venue/Source:** ESEC/FSE '22 (30th ACM Joint European Software Engineering Conference and Symposium on the Foundations of Software Engineering)
- **DOI:** 10.1145/3540250.3549118

## Metadata

- **se_area:** Testing (accessibility testing); also touches maintenance (developer guidance for fixing layout issues)
- **se_task:** Automated detection of text accessibility issues caused by incompatibility between apps and the Text Scaling Assistive Service (TSAS)
- **cv_technique:** OCR (Tesseract, open-source OCR engine) applied to cropped screenshot regions to extract text bounding boxes and measure text height; combined with rule-based comparison against UI metadata (view bounds, XML dump) rather than a learned CV model
- **platform:** Mobile (Android; iOS discussed only as future work)
- **rationale:** Robustness (systematic, repeatable detection across many screens instead of manual inspection); context-driven (screenshots are cropped to individual view bounds derived from the XML hierarchy before OCR is applied, so detection is grounded in UI structure, not raw pixels alone)
- **artifact_type:** Localized (per-view screenshot crops for unresponsive/cropped/truncated view checks) combined with full-interface comparison (whole-screen view-presence comparison for missing/overlapping view checks)
- **eval_method:** Empirical evaluation on 30 real-world Android apps (15 apps known from the empirical study to have issues + 15 randomly sampled); manually verified precision/recall per issue type (overall 88.27% precision, 95.76% recall); running-time measurement per app (avg. ~1 minute)
- **challenges:** OCR inaccuracy on low-contrast text lowers precision for Cropped View and Truncated View detection; approach presumes tests are written with default text size and identify views via resource-id/text (not absolute coordinates); Test Runner can fail to execute steps when a view is missing/inaccessible with TSAS on, requiring fallback to default settings; false positives in Missing View detection can occur when the Appium Accessibility API cannot programmatically scroll to reach a view; Android-only implementation, no iOS support yet.

## Summary

AccessiText targets a specific, underexplored accessibility problem: apps that break when users activate the Text Scaling Assistive Service (TSAS) to enlarge text. The authors first ran an empirical study, manually coding over 600 candidate issues from Android/iOS app reviews and Twitter to derive five recurring issue types: unresponsive views, missing views, overlapping views, cropped views, and truncated views, each tied to a concrete UI failure mode (e.g., density-independent-pixel-sized text that ignores TSAS, or views pushed off-screen as siblings expand). Building on this taxonomy, they implement AccessiText, a two-component Appium-based dynamic testing tool: a Test Runner executes an existing GUI test script twice (default and doubled text size via TSAS), capturing screenshots and XML view hierarchies at each step and performing extra scroll exploration to surface views pushed out of view; a Result Analyzer then applies per-issue heuristics, notably using Tesseract OCR on cropped view images to measure rendered text height and detect views whose text doesn't scale, is cropped, or is truncated, plus geometric bounds comparison for missing/overlapping views. Evaluated on 30 real apps, AccessiText found accessibility issues in every app (avg. 9.5 per app) with strong precision/recall, and the paper discusses causes (hard-coded dp sizing, lack of flexible layout constraints) and a notable finding that developers often dismiss such reports as "just lower your font size" rather than acknowledging them as accessibility bugs.
