# Harnessing LLMs for Document-Guided Fuzzing of OpenCV Library

- **Year:** 2025
- **Venue/Source:** ICSME 2025 (IEEE International Conference on Software Maintenance and Evolution)
- **DOI:** 10.1109/ICSME64153.2025.00017

## Metadata

- **se_area:** Testing (automated fuzz testing of a widely used software library)
- **se_task:** Document-guided fuzzing of the OpenCV-python API to automatically detect implementation bugs (crashes, NaN-value bugs, unexpected exceptions) across 330 OpenCV APIs, including both well-documented and poorly/undocumented APIs
- **cv_technique:** None used as part of the proposed testing technique itself. OpenCV (a computer vision library) is the system under test, not a tool applying CV. The paper's actual technical mechanism (VistaFuzz) uses a Large Language Model (GPT-4) purely for natural-language-style parsing of API documentation text, standardizing input-parameter metadata (type, size, default, description, dependency flags), and inferring plausible parameter constraints for poorly-documented or undocumented APIs by analogy to well-documented ones; generated test-case "images" are simply randomly initialized numeric arrays (e.g., via np.random.randint) matching inferred shape/type constraints, not visually meaningful or CV-processed images
- **platform:** General (Python library / API-level testing infrastructure; not GUI, mobile, web, desktop, or game software in the usual platform sense)
- **rationale:** Not applicable in the CV-rationale sense (context-driven / robustness / ease-of-use categories describe why CV would be chosen for an SE task, but no CV technique is chosen here); the LLM-usage rationale is context-driven only with respect to natural-language documentation text (parsing free-text API docs and inferring missing structured information by pattern-matching against well-documented APIs), not visual context
- **artifact_type:** N/A. No visual/image artifact is analyzed or produced as part of the technique; generated inputs are synthetic numeric arrays used only as function arguments to OpenCV calls, not screenshots, video, or other visually-interpreted SE artifacts
- **eval_method:** Empirical fuzzing evaluation across 330 selected OpenCV-python APIs (out of 679 total, after excluding undocumented/unsupported/dependent/no-output APIs), 600 generated test cases per API, ~3.2 hours total runtime on a 64-core/32GB machine; metrics include code coverage (Python-level via coverage.py and C++-level via GCOV), number of detected/confirmed/fixed bugs (17 detected, 10 newly confirmed, 5 fixed), and comparison against adapted baselines (DocTer's constraint-extraction component, DRONE) since existing DL-library fuzzers (FreeFuzz, TitanFuzz, FuzzGPT, Fuzz4ALL) could not be directly applied to OpenCV; ablation studies disabling individual generation strategies (Type, Size, Value-Range variants) to assess their contribution to coverage and bug detection
- **challenges:** The paper reports 2 false positives caused by errors/ambiguities in OpenCV's own documentation leading to incorrectly inferred constraints; only 330 of 679 total OpenCV-python APIs could be tested (248 fully undocumented APIs excluded, plus stereo/video-related, file-reading, no-output, and highly-dependent APIs excluded for methodological reasons), limiting coverage completeness; existing deep-learning-library fuzzing baselines were largely inapplicable to OpenCV (closed-source, incompatible constraint models, or unable to satisfy OpenCV's parameter constraints), so comparisons rely on adapted/partial baselines rather than true state-of-the-art head-to-head evaluation; the technique depends on GPT-4's documentation-parsing and analogical-inference quality, which is unverified/unvalidated as a standalone accuracy metric separate from downstream bug-detection outcomes

## Summary

VistaFuzz is a fuzz-testing technique for the OpenCV-python library that uses a Large Language Model (GPT-4) to parse and standardize the library's often inconsistent API documentation, ranging from well-documented APIs with full parameter descriptions, to poorly-documented APIs with only function signatures, to entirely undocumented APIs, into a uniform structured representation (parameter flags, default values, types, sizes, and free-text descriptions) from which constraints and inter-parameter dependencies can be automatically extracted. For undocumented or under-documented APIs, GPT-4 is used to infer plausible parameter semantics by pattern-matching against structurally similar, well-documented APIs elsewhere in the library. These extracted constraints then drive a systematic input-generation and fuzzing loop that manipulates each parameter's type, size, and value (including noise injection, random masking, and value-scaling perturbations) to probe for three categories of bugs: crashes, unexpected NaN values, and unhandled exceptions. Evaluated on 330 of OpenCV-python's 679 total APIs, VistaFuzz detected 17 bugs, of which 10 were newly confirmed by OpenCV maintainers and 5 have since been fixed in the library, with poorly-documented APIs, only 9.7% of tested APIs, disproportionately accounting for 29.4% of all detected bugs, supporting the authors' motivating claim that documentation quality correlates with defect risk. While methodologically solid as a software-testing/fuzzing contribution and notable for being (per the authors) the first work to systematically fuzz-test the OpenCV library itself, this paper's relationship to computer vision is inverted relative to the survey's typical scope: OpenCV functions here purely as the software artifact being tested (the system under test), and no computer-vision algorithm, model, or technique is actually employed anywhere in VistaFuzz's own pipeline. The "images" it generates are simply randomly-valued numeric arrays satisfying inferred shape/type constraints, and the sole AI component (GPT-4) operates exclusively on natural-language documentation text, not on visual data, as flagged above.
