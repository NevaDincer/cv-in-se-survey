# Automatically recognizing the semantic elements from UML class diagram images

- **Year:** 2022
- **Venue/Source:** The Journal of Systems & Software (JSS), Vol. 193, Article 111431
- **DOI:** 10.1016/j.jss.2022.111431

## Metadata

- **se_area:** Design / Maintenance (recovering semantically analyzable design models to support consistency checking, code generation, and design-to-code tracing, i.e., reverse-engineering design artifacts that exist only as images back into a usable, analyzable form)
- **se_task:** Automated recognition of semantic elements (classes with names/attributes/operations; and generalization, realization, dependency, and aggregation relationships) from raster images of UML class diagrams, producing a semantic model file usable by downstream design-source-code consistency-checking tools
- **cv_technique:** Classical (non-deep-learning) image-processing pipeline built on OpenCV: grayscale conversion, Gaussian sharpening, and morphological erosion/dilation for pre-processing; polygon-approximation-based contour/rectangle detection plus a custom rectangle-clustering ("rectangle merging") heuristic for class recognition; Hough-transform-based straight-line detection combined with a novel polygonal-line-merging algorithm (point-polygon-test-based) for relationship-line recognition; a novel "double-recognition-approximation" method (shape stretching + delicate polygon approximation via AForge.NET/Point-Polygon shape checkers) for classifying relationship-type symbols (triangle, arrow, diamond) under noise/low resolution; Tesseract-OCR for text recognition of class names/attributes/operations
- **platform:** Desktop (UML modeling tool output / diagram images embedded in software documentation, not mobile, web, or game)
- **rationale:** Context-driven (motivated by an empirical survey of 18,054 GitHub projects and 44 industry practitioners showing UML class diagrams are the dominant design-model type and are usually stored as unstructured images, which is exactly the artifact type the approach targets); robustness (explicitly engineered to handle four identified real-world challenges: varying graphical presentation of the same semantic element, differing tool-specific rendering styles across StarUML/EA/Rational Rose, varying image resolutions, and gradient-colored backgrounds); ease of use (aims to recover a machine-analyzable model from documentation images without needing the original editable model file, which the authors' survey found is "easily lost" in practice)
- **artifact_type:** Full-interface analogue for diagrams, full-diagram (whole class-diagram image is processed end-to-end to recover all classes and relationships as a complete semantic model)
- **eval_method:** Precision and Recall computed against manually annotated ground truth, separately for classes and for each of the 4 relationship types, across two experiments. (RQ1) 30 diagrams re-drawn in the 3 most popular UML tools (StarUML, EA, Rational Rose) from a base set of 10 diagrams (97 classes, 86 relationships), compared directly against previously published Img2UML results on the same base diagrams. (RQ2) 50 diagrams randomly sampled from open-source GitHub projects (598 classes, 533 relationships total, spanning 9 different UML editors) to test generality beyond controlled/popular-tool-only conditions. Also includes a qualitative failure analysis of ~7 recurring error-inducing situations found across the 50 open-source cases.
- **challenges:** Authors explicitly enumerate multiple recognition-error sources found in practice: blurred/broken oblique lines causing false dashed-line detection (16/50 cases); lines with too-light color that go undetected (8/50); relationship lines crossing over class rectangles, corrupting both class and relationship recognition (4/50); gradient/gradually-changing background colors causing a single class rectangle to be misrecognized as two separate rectangles (4/50); relationship lines too short to pass length thresholds (2/50); classes positioned too close together and merged into one (2/50); text overlapping relationship lines and breaking them into segments (2/50); aggregation-relationship recognition is consistently the weakest across all tool styles because its diamond symbols have more edges and both solid/hollow variants, making them prone to corner loss under low resolution; generalization recognition is weakest specifically on open-source images because overlapping polygonal lines from multiple generalizations are hard to disambiguate into distinct source/target class pairs; approach does not attempt to recover element location/coordinate information, only semantic content

## Summary

This paper recovers machine-analyzable UML class diagrams from raster images, a genuinely common problem the authors first establish empirically through a two-part survey: mining 18,054 GitHub projects with 68,313 UML diagram links, plus a 44-respondent industry questionnaire. They find design models usually exist only as images (73.72% of cases) and that class diagrams are the most-used diagram type in both open-source and industry settings, with consistency checking mostly done by hand as a result. To fix that, they propose ReSECDI, a fully classical, non-deep-learning computer-vision pipeline built on image pre-processing (grayscale, Gaussian sharpening, morphological erosion/dilation) plus three custom algorithms: a rectangle-clustering method that merges OpenCV-detected rectangle fragments into complete UML classes despite varying numbers of constituent rectangles, a polygonal-line-merging method based on point-polygon testing that stitches together oblique, multi-segment relationship lines Hough-transform detection alone can't handle, and a "double-recognition-approximation" method that stretches then tightly re-approximates noisy relationship symbols (triangles, arrows, diamonds) to their canonical shapes before classification. Tesseract-OCR handles text recognition once the rectangle structure is resolved. Tested on 30 diagrams redrawn in the three most popular UML tools, the approach reaches roughly 90 to 100% recall and precision for classes and 84 to 100% for individual relationship types, beating the only comparable prior system, Img2UML, on the same base diagrams. On 50 diagrams sampled from real open-source projects across 9 different editors, performance drops only slightly, class F1 around 97 to 99%, relationship F1 around 90 to 94%, showing solid generalization beyond controlled, single-tool conditions. The authors lay out a detailed taxonomy of remaining failure modes, blurred lines, gradient backgrounds, text overlapping relationship lines, aggregation-symbol ambiguity, and release their implementation and evaluation diagrams as open artifacts.
