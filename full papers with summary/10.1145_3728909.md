# GUIPilot: A Consistency-Based Mobile GUI Testing Approach for Detecting Application-Specific Bugs

- **Year:** 2025
- **Venue/Source:** Proc. ACM Softw. Eng., Vol. 2, No. ISSTA, Article ISSTA034 (ISSTA 2025)
- **DOI:** 10.1145/3728909

## Metadata

- **se_area:** testing
- **se_task:** mobile GUI design-mock-up-conformance testing: detecting both screen inconsistencies (layout/widget deviations from a design mock-up) and process inconsistencies (deviations in screen-transition/navigation behavior from the specified design flow)
- **cv_technique:** YOLOv8 (object detection for widget/UI-element localization and classification, benchmarked against YOLOv9/v10, RetinaNet, Faster R-CNN, RT-DETR); OCR (text extraction from text-bearing widgets); a vision-language model, GPT-4o (used with a custom "visual prompt" to translate ambiguous natural-language transition descriptions into executable UI actions)
- **platform:** mobile (Android)
- **rationale:** robustness (global layout-semantics-aware widget alignment vs. GVT's brittle relative-position matching, which fails under insertions/deletions/shifts); context-driven (comparing implementation against designer-authored mock-ups without needing accessibility metadata or source code); ease of use (delivered as a web application for practitioners; runs with negligible overhead, ~0.001s per screen match)
- **artifact_type:** full-interface (whole-screen widget-set comparison) combined with temporal/process reasoning (multi-screen transition graphs and action chains)
- **eval_method:** quantitative experiments on 80 top public Android apps with 160 human-authored mock-ups: (RQ1) screen-inconsistency detection against injected mutations (missing/extra/swapped widgets, text/color changes) measured by precision, recall, Jaccard index, classification precision, compared to the GVT baseline and a naive VLM-only baseline; (RQ2) process-inconsistency detection on 100 mutated design-mock-up transitions executed live on virtual Android devices (Waydroid + UiAutomator2/ADB), measured by precision/recall; (RQ3) component ablations: widget detector mAP/mAR against ground truth and against alternative detector architectures, and VLM action-completion success rate over 1–3 trials, broken down by screen complexity; plus a qualitative industrial case study with a trading app (32M users) that surfaced 9 real, expert-confirmed bugs
- **challenges:** authors explicitly discuss threats to validity: dependency on a third-party VLM API (OpenAI) introduces latency/availability risk; the evaluation mock-ups were simulated from real screenshots rather than genuine designer-authored mock-ups (external validity); the widget detector struggles with visually similar classes (input boxes vs. text buttons) and with charts lacking clear boundaries; false positives/negatives arise under large layout perturbations, overlapping widgets after swaps, or missed detections; the paper also raises a broader process concern that design mock-ups drift out of sync with implementations over time, since (unlike code) they are not maintained under CI/CD-like discipline.

## Summary

GUIPilot targets a specific, under-served flavor of mobile GUI testing: validating that an implemented app conforms to its design mock-ups, rather than merely hunting for crashes. It formalizes two complementary consistency problems. Screen inconsistency treats each screen as a set of typed, positioned widgets (detected via a fine-tuned YOLOv8 model, with OCR extracting text content) and casts widget matching between a mock-up screen and its implementation as an optimizable alignment problem: a partial ordering (top-to-bottom, then left-to-right) turns each screen into a sequence, a composite similarity score (position, area, aspect-ratio, type) scores all widget pairs, and a Longest-Common-Subsequence dynamic-programming algorithm finds the globally optimal alignment, from which missing widgets, extra widgets, and semantic changes (text/color/type edits) are reported. Process inconsistency addresses screen-to-screen navigation: ambiguous natural-language transition descriptions in mock-ups (e.g., "Buy 100 shares") are converted into concrete, executable UI actions (click, long-press, send-keys, scroll, swipe, drag-and-drop, go-back) by a vision-language model (GPT-4o) guided by a carefully engineered "visual prompt" that highlights only interactable widgets with IDs and constrains the model's action vocabulary and output format to curb hallucination. Evaluated on 80 popular Android apps and 160 mock-ups, GUIPilot substantially outperforms the prior state of the art (GVT) on layout-type violations (up to 66% precision, 57% recall improvement) while matching it on in-place semantic edits, achieves perfect precision/recall on injected process inconsistencies, and runs essentially in real time (sub-millisecond screen comparisons). A notable detail is the industrial deployment: applied to a financial trading app with 32 million users using the company's own (imperfect, sometimes stale) mock-ups, GUIPilot surfaced 9 real inconsistencies, all confirmed by the app's own designers/engineers, and the paper uses this deployment to argue that design mock-ups themselves need CI/CD-like maintenance discipline as software evolves.
