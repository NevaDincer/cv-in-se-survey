# AutoTestUI: Automated Test Case Generation from UI Screenshots

- **Year:** 2025
- **Venue/Source:** 2025 9th International Conference on Electronics, Communication and Aerospace Technology (ICECA)
- **DOI:** 10.1109/ICECA66444.2025.11383091

## Metadata

- **se_area:** Testing
- **se_task:** Automated generation of executable UI/functional test cases (QA and User Acceptance Testing scripts) directly from static UI screenshots, without access to source code
- **cv_technique:** YOLOv8n (UI component/object detection); EasyOCR (text extraction from UI elements); Gemini AI (multimodal/LLM-based semantic interpretation and test-case scenario generation); per the paper's own description, the detection stage as actually implemented in the described system is a "mock detection system" that simulates bounding boxes and element types rather than running true CV inference, though the results/evaluation section states YOLOv8n and EasyOCR were integrated and run on the UIED dataset
- **platform:** General (explicitly targets both web and mobile UI screenshots)
- **rationale:** Ease of use (code-independent; works from a screenshot alone, requiring no source-code access or complex test-framework configuration, lowering the barrier to adopting UI test automation); Context-driven (the pipeline is explicitly meant to work early in design/prototype stages, before source code exists, and to generalize across diverse web/mobile screens); Robustness is claimed via reduced manual/fragile scripting and a fallback rule-based generator when the Gemini API is unavailable, but this is asserted rather than rigorously demonstrated
- **artifact_type:** Full-interface (the whole UI screenshot is processed as a single image, and all detected components on it are analyzed together to produce a set of test cases covering the interface as a whole)
- **eval_method:** Experiments reportedly used the UIED dataset (diverse web and mobile UI screenshots annotated with element labels), with YOLOv8n at confidence threshold 0.6 and input size 640×640, average processing time ~5 seconds per screenshot. Reported metrics: 70% reduction in testing time (manual testing of sample web/mobile apps: ~2-3 hours vs. ~40 minutes with AutoTestUI) and 88% average accuracy in UI element detection (Fig. 7 "accuracy graph"). A comparative table (Table 1) qualitatively contrasts AutoTestUI with existing UI testing approaches, and Table 2 is described as a quantitative performance comparison; neither table's contents nor precise measurement methodology, sample size, or statistical detail is given in the text extracted. No baseline CV models are benchmarked against YOLOv8n, no ablation is reported, and no independent user study is described; the "manual vs. automated" comparison appears based on internal team testing of unspecified sample apps rather than a controlled study with external participants.

## Scope note

The paper's own system description states the UI element detection module is a "mock detection system" that simulates detections with generated bounding boxes rather than performing real computer-vision inference, while the results section separately claims YOLOv8n/EasyOCR were used on the UIED dataset. This is an internal contradiction that makes the actual extent of real CV usage and the validity of the reported 88% accuracy figure unclear.

## Summary

AutoTestUI is a proposed framework that generates executable QA/UAT test cases directly from static UI screenshots, aiming to remove the need for source-code access when automating interface testing. The pipeline first accepts a user-uploaded screenshot (web or mobile), detects UI components (buttons, text fields, dropdowns, checkboxes, links) via a CV-based detector reported as YOLOv8n, extracts on-screen text with EasyOCR, and then feeds the detected element data into Gemini AI (a large language model) prompted to act as an "expert QA engineer." Gemini derives each element's functional purpose from its text and context, and produces positive, negative, and UI/UX test scenarios with actionable steps, expected results, and priority levels (High/Medium/Low based on business-critical elements like Login or Payment). A rule-based fallback generates test cases locally if the Gemini API is unavailable. Users can then review, edit, and export the generated cases as PDF, plain text, JSON, or persist them via a Flask backend. The main contribution is a code-independent, screenshot-driven test-generation workflow spanning CV, OCR, and NLP/LLM stages, evaluated (per the authors) on the UIED dataset with a claimed 70% reduction in testing time and 88% detection accuracy. A distinctive and noteworthy detail is that the methodology section explicitly describes the detection stage as a "mock detection system" that simulates plausible bounding boxes and element types rather than performing genuine inference, which sits uneasily alongside the later claim of YOLOv8n-based detection results, raising questions about how much of the reported pipeline was actually implemented versus illustrated as a design concept.
