# A Compatibility Test Method for Android Applications Based on Multimodal Large Models in Crowdsourcing Scenarios

- **Year:** 2025
- **Venue/Source:** 5th International Conference on Computer Network Security and Software Engineering (CNSSE 2025)
- **DOI:** 10.1145/3732365.3732402

## Metadata

- **se_area:** Testing (compatibility testing)
- **se_task:** Automated generation of executable test scripts from GUI screenshots, and cross-device compatibility testing / fault detection
- **cv_technique:** Multimodal large language model (Qwen2-VL-7B-Instruct) performing vision-language understanding of Android GUI screenshots, fine-tuned via LoRA to output an intermediate scripting language; downstream device-level test execution via DroidBot (not itself vision-based)
- **platform:** Mobile (Android), crowdsourcing-based multi-device testing
- **rationale:** Ease of use (removes the need for testers to hand-write scripts in Espresso/Robotium/UIAutomator/Appium), context-driven (script generation is grounded directly in the visual layout of the GUI screenshot), and robustness (aims to generalize across heterogeneous device/OS/screen-size configurations)
- **artifact_type:** Full-interface (screenshots of complete Android app pages/screens)
- **eval_method:** Comparative accuracy/recall/F1 against three commercial multimodal LLMs (Doubao, Kimi, Yiyan/Wenxin Yiyan) on 100 prepared Android screenshots, each scored on whether generated test code matched the intended AppCheck intermediate-scripting-language syntax and screen content; qualitative description of UI Transition Graph (UTG) generation via DroidBot for multi-device coverage
- **challenges:** Model relies solely on image/video input and cannot directly extract XPath or other resource identifiers from the screenshot (falls back to generating placeholder resource IDs); accuracy and robustness degrade on extremely complex or custom-designed UIs; no support yet for non-visual interface elements (audio, haptic feedback); requires repeated prompting for some baseline MLLMs to reliably emit the target script syntax

## Scope note

The "vision" component here is an off-the-shelf multimodal large language model (Qwen2-VL), fine-tuned with LoRA, not a dedicated or classical CV pipeline. Visual grounding (screenshot → test script) is nonetheless central to the approach, so it plausibly fits a CV-for-SE survey, but note that the technique is essentially "prompt/fine-tune a general-purpose vision-language model" and not a bespoke computer-vision method; flagging in case the survey's inclusion criteria are stricter about what counts as a "CV technique."

## Summary

This paper proposes STLLM (Stateful Test Language Model), a system that fine-tunes the open-source multimodal large model Qwen2-VL-7B-Instruct via LoRA to automatically generate Android UI test scripts from screenshots, aiming to reduce the manual-coding burden of existing frameworks (Espresso, Robotium, UIAutomator, Appium) and support simultaneous testing across multiple physical/virtual devices for compatibility testing. The approach first teaches the model an intermediate, platform-agnostic scripting language derived from the crowdsourcing record/replay tool AppCheck (covering actions like Click, LongClick, SwipeType and UI-locator schemes such as resource-id/XPath), feeding both the language specification and screenshots as multimodal training signal. After LoRA fine-tuning (batch size 32, learning rate 5e-5, with data augmentation via randomly perturbing operation order/count), STLLM is combined with the lightweight automated-testing framework DroidBot, which drives multiple physical phones simultaneously and produces UI Transition Graphs (UTGs) to visualize test coverage and help identify untested paths. In a comparison against three commercial Chinese MLLMs (Doubao, Kimi, Wenxin Yiyan) on 100 Android screenshots, STLLM achieved the best F1 score (83%) and tied for the best recall (92%), and notably was the only model that did not need its intermediate scripting language re-explained via repeated prompting, since the syntax was baked in via fine-tuning instead of in-context instruction.
