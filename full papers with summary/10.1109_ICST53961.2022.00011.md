# GUI Test Transfer from Web to Android

> **SCOPE WARNING**: Likely out of scope for this survey. TRANSDROID's widget/screen matching pipeline is built entirely on NLP techniques (Word2Vec cosine similarity over tokenized widget text, screen titles/headers, and action labels) plus static and dynamic program analysis (Soot-based decompiled-APK analysis, Navigation Graph extraction, a greedy model-based test-generation algorithm). No image-based or visual CV technique (OCR, image matching, object/UI-element detection from screenshots, embeddings from pixels, VLMs, etc.) appears anywhere in the approach. Matching relies solely on textual/structural widget attributes (id, class, text, href, placeholder) and DOM/Activity-level context. Recommend excluding unless the survey's scope is broadened beyond image-based CV to include general "visual"-adjacent GUI-structure techniques.

- **Year:** 2022
- **Venue/Source:** ICST 2022 (IEEE Conference on Software Testing, Verification and Validation)
- **DOI:** 10.1109/ICST53961.2022.00011

## Metadata

- **se_area:** Testing (GUI/usage-based test generation and cross-platform test reuse)
- **se_task:** Cross-platform GUI test transfer: automatically converting an existing usage-based GUI test suite written for a web application into an executable, semantically equivalent GUI test suite for the corresponding Android application
- **cv_technique:** None used. The tool (TRANSDROID) relies on: (1) Word2Vec (pretrained neural word-embedding model) to compute NLP-based cosine-similarity scores between tokenized widget text/attributes, screen titles/headers (`<title>`, `<h1>` tags vs. Android Activity names), and action labels; (2) static analysis via Soot (decompiled APK bytecode analysis) to extract a target-app Navigation Graph of Activities, widgets, and transitions; (3) dynamic analysis/execution (via Appium/ChromeDriver) to verify widget/screen reachability and update the Navigation Graph at runtime; (4) a rule-based Action Transformation step (reuse/merge/conversion/removal) to convert web-specific actions (mouseOver, jumpByURL, doubleClick, keyDown) into Android-compatible actions; (5) a greedy, iterative model-based Test Generation algorithm. No component processes screenshots, renders, or pixel/image data.
- **platform:** Cross-platform, web (source) to mobile/Android (target)
- **rationale:** Not applicable (no CV rationale). The paper's design rationale for using NLP/Word2Vec over vision-based matching is implicit: web and Android GUI widgets expose rich textual/structural metadata via DOM attributes and Android resource/layout files, making text- and structure-based matching sufficient without needing pixel-level visual comparison).
- **artifact_type:** Not applicable in the CV sense. The "artifacts" being compared are structured widget/screen metadata (attributes, text, hierarchy position in a Navigation Graph), not rendered images.
- **eval_method:** Empirical evaluation on 10 real-world web/Android app pairs (20 apps total: BuzzFeed, DokuWiki, Etsy, Fox News, GitLab, Groupon, Hacker News, OwnCloud, Wikipedia, WordPress) with 110 existing/reconstructed web test cases comprising 561 GUI and oracle events. Measured via: widget-mapping Precision/Recall against manually-constructed ground-truth Android tests (overall 82% GUI-event precision / 99% recall, 85% oracle-event precision / 99% recall); successful-transfer rate (77%, 85/110, judged by manual executability/meaningfulness checks); effort-reduction via Levenshtein/edit-distance between generated and ground-truth tests (82% average manual-effort reduction); and execution-time efficiency (average ~349 seconds per transfer, compared to ~1.5 hours average reported for prior intra-platform transfer work).
- **challenges:** Authors explicitly report several transfer-failure causes: (1) insufficient widget context: Android widgets using identical generic identifiers (e.g., repeated `edit-text` IDs) or icon-only buttons (e.g., GitLab's hamburger menu) lack textual information for the Word2Vec-based matching to work; (2) missing features, the target app lacking a feature present in the source (e.g., OwnCloud's Android app lacking a "restore from recycle bin" feature, Hacker News Android lacking an "unvote" feature); (3) radically different interaction flows between platforms for the same feature (e.g., DokuWiki's web search-then-click-generated-link flow vs. Android's direct "Create page" button) that the current widget/screen-matching approach cannot bridge; (4) the current action-transformation rule set does not support some web-specific actions like drag-and-drop, nor external communications such as file uploads or OAuth login flows in the source test; (5) reachability-checking (isReachable) is the dominant time cost in the longest transfers because it repeatedly restarts and re-executes the target app to validate candidate paths.

## Summary

TRANSDROID is an automated tool for transferring existing usage-based GUI test suites from a web application to its Android counterpart, addressing the common real-world scenario where an organization maintains functionally overlapping web and mobile apps (e.g., WordPress, Wikipedia, Twitter) but must currently hand-write separate test suites for each platform. The paper frames two novel challenges specific to cross-platform (as opposed to intra-platform) test transfer that prior work had not addressed: incompatible actions (e.g., web-only `mouseOver`/`jumpByURL`/`doubleClick` events with no direct Android equivalent) and unclear widget context (e.g., a generic HTML `<span>` tag whose behavior is ambiguous until combined with additional context). TRANSDROID's pipeline has four components. Context Extraction instruments and executes the source web test to capture three types of contextual information per event: widget context (HTML attributes and enclosed text), screen context (page `<title>`/`<h1>`), and action context (the performed action). This extends prior test-transfer work, which used only widget context. Action Transformation applies a rule-based mapping (reuse, merge, conversion, or removal) to normalize web-specific actions into Android-compatible ones, e.g., merging a `mouseOver`+`click` combo into a single Android `click`, or converting `jumpByURL` into an intermediate `navigateToActivity` action. NavGraph Extraction statically analyzes the decompiled target Android APK (via Soot) to build a Navigation Graph of Activities, their associated widgets, and transitions. Test Generation then applies a greedy, iterative algorithm that, for each transformed source event, uses Word2Vec-based cosine similarity over widget/screen/action context to rank and select the most similar reachable target widget or screen, appending any "leading events" needed to reach it, and dynamically updates the Navigation Graph with runtime-observed reachability information across iterations until a fitness threshold or timeout is reached. Evaluated on 10 real-world web/Android app pairs and 110 test cases (561 events), TRANSDROID achieved a 77% successful-transfer rate, 82%/99% precision/recall for GUI events (85%/99% for oracle events), an average 82% reduction in manual test-authoring effort compared to writing ground-truth Android tests from scratch, and an average transfer time of about 6 minutes, substantially faster than the ~1.5 hours reported for prior intra-platform transfer techniques. Despite the strong empirical results, the entire matching and generation pipeline is grounded in textual/structural (NLP and static/dynamic program analysis) techniques rather than any image-based computer vision method.
