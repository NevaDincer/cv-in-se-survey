# Visual Sketching: From Image Sketches to Code

- **Year:** 2020
- **Venue/Source:** ICSE-NIER 2020
- **DOI:** 10.1145/3377816.3381745

## Metadata

- **se_area:** Development
- **se_task:** Sketch/image-to-code synthesis for data-wrangling scripts and neural-network architecture definitions, via image-similarity matching against a reference-image database of code templates with developer-fillable 'holes'
- **cv_technique:** Document image thresholding/binarization (Howe's DIBCO-winning algorithm); flood fill (gap closing); morphological closing; connected-component analysis; vertical projection profiling for structural (multi-region) analysis; dilation for text-region bounding-box extraction; (proposed, not implemented) deep-learning-based handwritten text recognition
- **platform:** General (data-science/code-notebook workflows and neural-net architecture sketches; not GUI-specific)
- **rationale:** Ease of use (low/no-code intent expression via hand-drawn images); Context-driven (visual layout pattern is treated as a direct proxy for code intent)
- **artifact_type:** Hand-drawn sketch / document image (treated as a document with textual + structural regions)
- **eval_method:** None. This is a vision/position paper (ICSE-NIER track). No implementation, no empirical evaluation. Only two illustrative worked examples (CSV column projection, CSV file merge) and one design-only example (Keras neural net architecture from a sketch) are shown; text recognition is explicitly stated as 'still under development' with no working prototype.
- **challenges:** Authors explicitly flag: (1) tension between simplicity and expressiveness of the visual sketch language: too general risks re-inventing a Turing-complete language, too specific pushes developers back to searching the web; (2) selection of the right CV algorithms/efficiency trade-offs is unresolved and left for future work; (3) approach only produces code from a fixed template database matched via structural similarity, not full specification synthesis; (4) assumes developers can easily digitize a sketch (photo/pen) into their dev environment

## Scope note

## Summary

Proposes "Visual Sketching," a low/no-code program-synthesis technique: a developer first defines a *transformation*, a function mapping a reference image to a code template with unfilled "holes" (e.g., file names, column names). At use time, a user draws or photographs a sketch of their intent; the tool matches it against the reference-image database via structural/visual similarity and returns the associated template, with the user then filling in the holes. The technique is explicitly inspired by educational "coding cards" and is positioned as the inverse of Program Sketching (where a human writes code with holes for a synthesizer to fill; here the human draws a picture and the code is the pre-existing template).

The CV pipeline described (not implemented as a full system) has three conceptual stages: (1) **Structural Analysis**, thresholding the sketch image to black-and-white via Howe's DIBCO-2013-winning binarization algorithm, a flood-fill pass to close character gaps, a morphological closing operation to merge stroke groups into single objects, and a vertical projection profile to segment the sketch into structural text/no-text column regions (e.g., recognizing the CSV-projection sketch as a 3-column structure: source data / arrow delimiter / target text); (2) **Document Image Segmentation**, using dilation with a 20-pixel disk structural element plus bounding-box extraction to isolate specific sub-regions of interest (e.g., extracting just the "Name" label); (3) **Text Recognition**, explicitly stated as future work relying on external handwriting-recognition literature, not yet implemented in their prototype. The paper is candid that it is "not yet supported by solid results, but rather by preliminary results and a strong intuition," making it a bold-vision NIER contribution rather than an empirical study.
