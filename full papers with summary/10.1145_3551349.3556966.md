# Accelerating OCR-Based Widget Localization for Test Automation of GUI Applications

- **Year:** 2022
- **Venue/Source:** ASE 2022 (37th IEEE/ACM International Conference on Automated Software Engineering)
- **DOI:** 10.1145/3551349.3556966

## Metadata

- **se_area:** Testing (GUI test automation infrastructure/tooling)
- **se_task:** Speeding up OCR-based widget/label-text localization used for locating GUI elements by their on-screen text during test script execution (widget localization for test automation)
- **cv_technique:** OCR (used as a black-box wrapped by the new technique; compared against/built atop Tesseract, PaddleOCR, EasyOCR); custom lightweight text detection (LTS) based on traditional/classical edge-based, bottom-up character/text-phrase detection (not deep learning); text shape matching/ranking algorithm using abstract text shape features (character width/height distribution) rather than full text recognition, to rank candidate regions before invoking full OCR recognition
- **platform:** General (GUI applications; evaluated on mobile app screenshots via RICO dataset and desktop/web screenshots via a custom DOWL dataset)
- **rationale:** Efficiency/speed (primary rationale: the paper's whole contribution is accelerating existing OCR pipelines, not improving accuracy); ease of use (compatible with and reusable on top of existing/off-the-shelf OCR engines without requiring retraining); robustness across resolutions (1080p, 2k, 4k) and platforms (RICO mobile screens, DOWL desktop/web screens)
- **artifact_type:** Localized (finds and ranks specific label-text regions/widgets on a GUI screen rather than whole-screen classification)
- **eval_method:** Empirical performance benchmarking (RQ1: detection recall/precision at varying resolutions; RQ2: label-text localization ranking accuracy, top-1/top-5/top-10 position hit rates; RQ3: text matching/ranking runtime; overall wall-clock speed comparisons vs. black-box PaddleOCR/EasyOCR/Tesseract baselines) on two datasets: RICO (mobile) and a custom "DOWL" dataset (desktop/web screenshots at multiple resolutions)
- **challenges:** LTS-accelerated approach loses 5-8% detection precision compared to full PaddleOCR/EasyOCR pipelines on RICO (some recall/precision trade-off for speed); currently only supports localization of English text; acceleration does not help when the specified label text does not actually exist on the screen (reversion mechanism needed, negating speed gains in that case); does not work well for label texts on complex/textured image backgrounds since only a simple text detector is used, requiring fallback to full OCR engines in such cases

## Summary

This paper targets a practical bottleneck in GUI test automation: widget localization via OCR (matching test-script-specified label text, e.g., "Login", to its on-screen coordinates) is accurate but slow when using full off-the-shelf OCR engines (Tesseract, PaddleOCR, EasyOCR) on every screen during test execution. The authors propose LTS (Lightweight Text detection and Shape-matching), a technique that sits in front of existing black-box OCR engines: it first performs a fast, traditional (non-deep-learning) edge-based text-phrase detection pass to find candidate text regions, then uses abstract text "shape" features (character width/height sequences, not actual recognized characters) to rank candidate regions by their likelihood of matching the target label text, and only invokes full OCR recognition on the highest-ranked candidates, with a reversion mechanism to fall back to exhaustive OCR if the initial candidates fail to match. Evaluated on the RICO mobile-app dataset and a custom desktop/web dataset ("DOWL") across multiple resolutions, LTS achieves up to 84% speed improvement in label text localization compared to plain OCR pipelines, while incurring only a modest 5-8% precision loss on RICO (essentially no loss on DOWL) and successfully ranking target text within the top-10 candidates in roughly 80% of cases where base detection recall is high. The work is notable as a systems/efficiency contribution and not an accuracy contribution to OCR-in-SE. It explicitly frames itself as complementary to (not a replacement for) existing OCR-based GUI test automation approaches, useful particularly on devices lacking powerful GPUs, and explicitly surveys and discusses prior work applying OCR to software engineering tasks (GUI structure recognition, test case creation, defect/smell detection, bug report analysis).
