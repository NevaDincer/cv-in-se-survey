# Design of an Automatic Testing System for Camera UI Test

- **Year:** 2020
- **Venue/Source:** Proceedings of the 39th Chinese Control Conference (CCC 2020)
- **DOI:** 10.23919/CCC50068.2020.9189199

## Metadata

- **se_area:** Testing (functional/UI regression testing of an embedded device interface)
- **se_task:** Automated functional UI testing / test-oracle verification for a camera's on-screen display (state transitions, e.g., detecting STBY→REC icon/text changes, network-signal icon changes)
- **cv_technique:** Global color histogram similarity (image split into 4×4 blocks of 64×64 to partially address histogram's lack of spatial locality); difference hash (dHash, 9×8 pixel downscale + grayscale + adjacent-pixel brightness comparison producing a 64-bit hash, compared via Hamming distance); perceptual hash (pHash, via Discrete Cosine Transform (DCT) on grayscale image, retaining upper-left low-frequency k×k coefficient block, thresholding against the block's mean to produce a binary hash, compared via Hamming distance); template/contour-based recognition for letters, numbers, and icons (image binarization + contour recognition + comparison against a character/icon library).
- **platform:** General / embedded device (a physical camera's UI, captured via HDMI/SDI video-capture hardware and processed on a PC), not a standard mobile/web/desktop app platform
- **rationale:** Robustness (comparing captured video frames against expected reference images to reliably judge pass/fail without disturbing the system under test); ease of use / practicability (keyword-driven test scripts abstract away the need to hand-code each test case; non-intrusive video-capture avoids instrumenting the camera firmware).
- **artifact_type:** Full-interface (each captured video frame is compared as a whole image against a reference frame using histogram/hash similarity) combined with Localized recognition (specific regions are analyzed for letters, numbers, and icon templates, e.g., the STBY/REC indicator or network-signal icon)
- **eval_method:** (1) Test-efficiency comparison: automated vs. manual testing execution time/frequency count over a 60-minute session (Fig. 7), showing automated testing efficiency is more stable while manual testing throughput degrades over time. (2) Three simulated test scenarios (script-command failure / correct pass / bug-occurrence cases) with visual inspection of grayscale histograms (Figs. 8–10). (3) Comparative accuracy of the three algorithms (histogram, dHash, pHash) across the three scenarios, reported as similarity percentages (e.g., 54–100%, 58–100%, 86–98%). (4) Execution-time-vs-image-count scaling curves for each algorithm at 50/150/200/300/500 executions (Figs. 12–14), used to compare speed.
- **challenges:** Authors explicitly state each algorithm has trade-offs: histogram similarity has the best precision but is not the fastest; dHash is fastest but less precise than histogram; pHash "has no obvious advantage in this design content" despite theoretically high precision reported in cited work, so its applicability to this context remains only "further verified" in future work. The global histogram approach alone cannot capture local color distribution/location, requiring the 4×4 block workaround. The authors also list explicit future-work limitations: no distributed/parallel operation support, limited script-function complexity, and insufficient speed/precision in image recognition, plus a stated intent to extend testing to brightness/color-saturation quality factors not yet covered.

## Scope note

The system under test here is a physical camera device's on-screen UI, captured via an external video-capture card, rather than a mobile, web, or desktop software application running standard OS-level UI toolkits, and the paper comes from a controls and automation venue, the Chinese Control Conference, rather than an SE venue. The CV usage, histogram, dHash, and pHash image-similarity comparison for oracle and result verification, is genuinely CV-for-testing, so it is kept here as an example of visual-oracle techniques in GUI test automation despite the embedded-hardware context and non-SE venue sitting at the edge of the survey's usual scope.

## Summary

This paper presents a hardware-in-the-loop automatic testing system for verifying a physical camera's on-screen UI, motivated by the tedium and low repeatability of manual camera-inspection testing. The system architecture connects the camera-under-test, a monitor, a video-capture card, and a PC: a keyword-driven test-script engine (with keywords for Serial Number, Function, Address, Execute Time, Wait Time, and Count, stored in CSV-like test-case templates) drives the camera via serial communication (e.g., open/initialize/read-write/close port) while the PC continuously captures the camera's live HDMI/SDI video output using OpenCV, without instrumenting or disturbing the device itself. To judge whether an executed test action produced the expected UI change (the test oracle), the system performs image recognition on captured frames across three object types, letters, numbers, and icons, using binarization, contour extraction, and comparison against a pre-built character/icon library (e.g., recognizing a UI transition from "STBY" to "REC" text/icon). For overall frame-level similarity judgment, the paper evaluates and compares three classical image-similarity algorithms: block-based color histogram comparison (chosen to partially fix histogram's lack of spatial awareness by dividing images into 4×4 blocks), difference hashing (dHash), and perceptual hashing (pHash, via DCT). Experiments across three simulated test scenarios (no-response bug, correct-pass, and incorrect/bug-triggering cases) found histogram-based similarity most accurate, dHash fastest, and pHash offering no clear advantage in this setting despite literature claims of high precision, leading the authors to select dHash as their production choice given the precision/speed trade-off. A separate efficiency comparison versus fully manual testing showed automated testing throughput remains stable over a 60-minute session while manual testing throughput degrades, supporting the system's practical value for large-scale, repetitive camera UI regression testing.
