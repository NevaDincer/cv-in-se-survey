# MotorEase: Automated Detection of Motor Impairment Accessibility Issues in Mobile App UIs

- **Year:** 2024
- **Venue/Source:** ICSE 2024 (46th IEEE/ACM International Conference on Software Engineering), Lisbon, Portugal
- **DOI:** 10.1145/3597503.3639167

## Metadata

- **se_area:** Testing (accessibility testing), with a maintenance/design-improvement dimension (generates developer-facing accessibility reports)
- **se_task:** Automatically detecting violations of four previously untargeted motor-impairment accessibility design guidelines in Android app UIs: visual touch target size, persisting element location, expanding section closure, and adjacent icon visual distance, to support developers building apps usable via switch-based assistive input as well as touch input by users with tremors or limited motor control
- **cv_technique:** A multi-detector pipeline combining a custom-trained Faster R-CNN object detector (torchvision, trained on a synthetically constructed dataset of 7,291 images built by superimposing FontAwesome/Flaticon closure icons onto Rico screenshots, achieving >95% test accuracy) for closure-icon detection; the UIED tool (combining neural object detection and unsupervised edge detection) for deriving true visual bounding boxes of clickable UI elements versus their (often larger/inaccurate) reported touchable XML bounds; Google OCR (EAST-based) plus GloVe-embedding-expanded lexical/semantic text matching for detecting closure-related text; and pixel-based mean-squared-error visual similarity comparison for matching persisting elements across screens, combined with UI metadata (uiautomator XML) analysis for a hybrid vision+structure approach
- **platform:** Mobile (Android)
- **rationale:** Context-driven (grounded in a systematic literature review of 20 primary studies plus Apple/Google accessibility guidelines, explicitly identifying an underserved user population, motor-impaired users, relative to the disproportionate prior focus on visual/hearing impairments) and robustness (explicitly designed to catch the discrepancy between an element's reported/touchable XML bounds and its true visual bounds, which purely metadata-based tools cannot detect, and to work regardless of UI design/format variation without relying on pre-existing test cases)
- **artifact_type:** Localized (per-element/per-icon visual bounding-box extraction and comparison) combined with full-interface analysis (whole-screen expanding-section and cross-screen persisting-element detection)
- **eval_method:** Construction of a novel manually-annotated benchmark, MotorCheck (555 real violation examples plus 1,044 non-violation examples across 1,599 screens from 70 popular Android apps, collected via the CrashScope automated input generation tool, with objective/low-conflict manual labeling by multiple authors); per-detector evaluation using precision, recall, accuracy, and F1 against ground truth (Visual Touch-Target: 1.0 precision/0.85 accuracy; Expanding Section: 0.90 precision/0.91 accuracy; Persisting Element: 0.82 precision/0.88 accuracy; Icon Distance: 0.71 precision/1.0 recall/0.96 accuracy; overall average accuracy ≈90%); direct comparison against two existing baseline tools (Google Accessibility Scanner for touch-target size, and Groundhog for expanding-section closure) on the same benchmark, with MotorEase outperforming both; additional false-positive/false-negative rate analysis and confusion-matrix inspection per detector to assess practical developer utility
- **challenges:** Author-reported detector-specific failure modes: the expanding-section detector produces false positives when closure-implying "X" icons appear in unrelated contexts (e.g., a text-field delete icon mistaken for a section-closer), an issue traced to synthetic training-data limitations; the visual touch-target detector misses elements not explicitly marked "clickable" in the XML (a metadata completeness limitation inherited from dynamically generated screenshots); the persisting-element detector can misclassify elements whose XML entries persist even when not visually rendered on screen, causing false violations; the icon-distance detector's accuracy is bottlenecked by imperfect UIED bounding-box estimation, producing false positives when overlapping elements are measured as zero distance; more broadly, all four detectors depend on the coverage and metadata fidelity of the underlying Android input-generation tool (CrashScope), and the guidelines targeted were deliberately limited to four (of 18 identified in the literature review) chosen for being both unaddressed by prior tools and technically tractable with current CV/screen-understanding techniques.

## Summary

This paper addresses a notable gap in software accessibility tooling: prior automated accessibility research has focused heavily on visual and hearing impairments, largely neglecting motor-impaired users who rely on switch-based scanning input or touch with physical constraints like tremors. Grounded in a systematic literature review (20 primary studies plus Apple and Google's accessibility guidelines) that catalogued 18 accessibility design guidelines, the authors select four previously untooled guidelines: visual touch target size, persisting element location across screens, expanding section closure availability, and adjacent icon visual distance, and build MotorEase, an automated detector for violations of each. MotorEase operates on screenshots and uiautomator XML metadata collected via an existing Android input-generation tool (CrashScope), requiring no pre-existing test cases. Its core technical innovation is combining computer vision (a custom Faster R-CNN closure-icon detector trained on a synthetically augmented Rico-derived dataset, plus the UIED edge-detection tool for computing an element's true visual bounding box) with text/semantic processing (OCR plus GloVe-embedding-expanded lexical matching) to detect discrepancies invisible to purely metadata-based analysis, most notably cases where an element's visually rendered size is smaller than its reported touchable area, which would fool XML-only accessibility checkers. The authors also construct and release MotorCheck, the first benchmark for these four guidelines (555 real, manually annotated violations plus 1,044 compliant examples across 1,599 screens from 70 apps), on which MotorEase achieves roughly 90% average accuracy and under 9% false positive rate, outperforming the two applicable existing baseline tools (Google Accessibility Scanner and Groundhog) on their respective overlapping guideline. A notable detail is the paper's explicit framing of its contribution as complementary to and extending prior tools like Groundhog, directly addressing two issue classes (counterintuitive navigation and inoperative actions) that the Groundhog authors themselves flagged as important open problems.
