# Understanding Screen Relationships from Screenshots of Smartphone Applications

- **Year:** 2022
- **Venue/Source:** IUI '22 (27th International Conference on Intelligent User Interfaces), Helsinki, Finland, pp. 447-458
- **DOI:** 10.1145/3490099.3511109

## Metadata

- **se_area:** Testing / Maintenance (supports automated GUI/app testing infrastructure: automated app crawling, replay of recorded UI action macros, and large-scale UI dataset analysis)
- **se_task:** (1) Screen similarity detection: determining whether two screenshots from the same app depict the same underlying screen despite visual/content variation; (2) screen transition classification: given two consecutive screenshots from an interaction trace, detecting which of several common UI events occurred (scrolling; appearance/disappearance of system dialogs, app dialogs, bottom dialogs, notifications, keyboard)
- **cv_technique:** Two separate models, both operating purely on pixel/screenshot input (no view hierarchy/DOM access): (1) Screen Similarity model = a pretrained Faster-RCNN-based UI object detector (from prior "Screen Recognition" work, trained on ~77k annotated iOS screenshots) that extracts per-element position, class label, and RCNN visual-appearance feature vectors, feeding a Transformer encoder (self-attention, BERT-style [CLS] token + masked-prediction auxiliary objective) that jointly encodes both screens and classifies same/different; (2) Screen Transition model = a Siamese network with a ResNet-18 CNN encoder producing whole-screenshot embeddings, trained with a pairwise contrastive loss plus a feed-forward transition classifier on the embedding difference vector; baselines compared include classical image-hashing (perceptual/wavelet/difference hash) and a heuristic UI-element-bounding-box-matching method
- **platform:** Mobile (iOS)
- **rationale:** Robustness / generality (pixel-only approach works regardless of underlying UI toolkit or view-hierarchy availability, unlike prior Android-view-hierarchy-based methods, so it generalizes across toolkits including non-standard ones like Flutter); context-driven (screen similarity must tolerate legitimate content variation (e.g., a shopping cart screen with different item counts) while distinguishing genuinely different screens, requiring semantic rather than purely pixel-similarity judgments)
- **artifact_type:** Full-interface (whole-screen classification/comparison) for the Screen Transition model; localized (object-level, per-UI-element bounding boxes and features feeding into cross-screen relational reasoning) for the Screen Similarity Transformer
- **eval_method:** Binary classification metrics (Precision/Recall/F1) on held-out train/val/test (70/15/15) splits of a custom-collected dataset of 77,655 screenshots from 1,110 iPhone apps (~15 min of crowd-worker exploration per app), annotated via a card-sorting grouping task (with inter-annotator QA: within-group accuracy >98%, between-group accuracy 34.32%) for screen similarity, and a separate before/after pairwise annotation task (avg. label accuracy 95.33%) for the 6 transition event types; compared against image-hashing (P/W/D-Hash), heuristic UI-element matching, and TensorFlow Similarity baselines; screen similarity model achieves F1=0.83 (best baseline: TensorFlow Similarity F1=0.69); screen transition model achieves average F1=0.65 across 11 classes (6 event types x open/close) or F1=0.71 on a reduced 5-class set, plus F1=0.80 for same-screen detection within the transition dataset
- **challenges:** Dataset limited to 1,110 apps (vs. millions available in the App Store), likely causing imbalance across app types/crawl depths; annotation disagreement between QA team and original annotators was substantial (34.32% between-group accuracy), forcing the authors to drop disputed screenshot pairs and use a smaller, higher-confidence dataset than originally collected; some transition event types (scrolling, notifications) are rare in the data; the Screen Similarity Transformer, because it featurizes screens as discrete UI elements, cannot capture transition cues that manifest outside element boundaries (e.g., screen dimming), requiring a wholly separate whole-image model (Screen Transition) for that sub-task; screen similarity is empirically harder than screen transition because within-sequence transitions are more constrained than arbitrary same-screen grouping (e.g., matching an initial screen to itself after scrolling several pages down can show very different visible content)

## Summary

This paper addresses two related but distinct pixel-only problems for understanding relationships between smartphone app screenshots, motivated by applications such as automated app crawling, UI-action-macro replay, and large-scale UI dataset analysis. Unlike most prior work, which relies on Android view hierarchies (unavailable or non-standard-toolkit-incompatible), the authors work entirely from screenshot pixels, making their approach applicable across UI toolkits. They collect a new dataset of 77,655 screenshots from 1,110 iPhone apps via 15-minute crowd-worker exploration sessions, with two custom annotation tasks: a card-sorting grouping task for "screen similarity" (are two screenshots the same underlying screen despite content/scroll/dialog differences?) and a before/after pairwise task for "screen transition" (given consecutive screenshots in an interaction trace, did any of 6 common events occur: scrolling, or the appearance/disappearance of app dialogs, system dialogs, bottom dialogs, notifications, or the keyboard?). For screen similarity, they combine a pretrained Faster-RCNN UI element detector with a Transformer that jointly encodes both screens' detected elements (position, class, RCNN visual features, screen-of-origin) via a BERT-style [CLS] token and a masked-element-prediction auxiliary loss, achieving F1=0.83 and outperforming image-hashing, heuristic element-matching, and TensorFlow Similarity baselines (best baseline F1=0.69). For screen transition, because element-level featurization missed whole-screen visual cues like dimming, they instead train a separate Siamese ResNet-18 network on whole screenshots with a contrastive similarity loss plus a transition-type classifier on the embedding difference vector, reaching F1=0.65 across 11 fine-grained transition classes (F1=0.71 on a coarser 5-class grouping that merges all dialog types). The paper's most notable methodological finding is the asymmetric transfer between the two tasks: a model trained on the (harder) screen similarity task generalizes well to the transition task, but not vice versa, suggesting the two problems, while related, require different data collection and modeling strategies.
